Build a proper server MSI via CPack's WIX generator, replacing the manual
`New-Service`/`sc.exe`/`New-NetFirewallRule` calls in
`Install-VaporWault.ps1` (kept as-is for the manual/advanced path — not
removed, per `TASK-145`).

Scope:

1. `CPACK_GENERATOR "WIX"` invocation for the `server` component (Windows
   only — gate in `cmake/Packaging.cmake` or pass at `cpack` invocation
   time, whichever keeps the Linux path untouched by WiX-specific
   variables).
2. `CPACK_WIX_*` variables: `CPACK_WIX_UPGRADE_GUID` (fixed, stable GUID —
   **must never change** between releases, or upgrades stop detecting the
   prior install; generate once and record it in this task's notes),
   `CPACK_WIX_PRODUCT_ICON`, license/branding as available.
3. A custom WiX fragment (`CPACK_WIX_EXTRA_SOURCES` /
   `CPACK_WIX_PATCH_FILE`) declaring:
   - `<ServiceInstall>` for `vapourwaultd.exe` (`Type="ownProcess"`,
     `Start="auto"`, `ErrorControl="normal"`) + `<ServiceControl>` to
     start on install and stop/remove on uninstall — this is what
     participates correctly in the MSI's own transaction, unlike the
     PowerShell script's post-hoc `New-Service` call.
   - A firewall rule via `WixFirewallExtension` for the TLS listen port
     (matching `Install-VaporWault.ps1`'s `New-NetFirewallRule` behavior).
   - Config template installed to `%ProgramData%\VaporWault\server.conf`
     if absent (matching the "don't overwrite an existing config" rule
     every other install path already follows) — MSI's `CreateFolder`/
     component-with-`KeyPath` "install file only if missing" idiom, or a
     small custom action if that idiom doesn't map cleanly; whichever is
     chosen must not overwrite an operator's edited config on upgrade.
4. This package **requires elevation** (`MSIINSTALLPERUSER=0`/per-machine),
   matching the existing script's own Administrator requirement — no
   per-user fallback needed for the server.

## Acceptance criteria

- `cpack -G WIX` (component `server`) produces a `.msi` that `light.exe`
  compiles without ICE-validation errors.
- Built and verified in this session (WEB.09/BLD.05 note below) — NOT
  installed on a real machine (installing a Windows Service + firewall
  rule is a system-mutating action outside this task's verification
  scope); real install/uninstall/upgrade verification is `TASK-152`'s job,
  ideally in a disposable VM/container.
- `CPACK_WIX_UPGRADE_GUID` is fixed and recorded here — confirmed not
  regenerated by re-running `cpack`.

**Key implementation decision not in the original filing**: CPack's WIX
generator does not natively split multiple components into separate MSIs
the way DEB/RPM do (unlike the ARCHIVE generator, which `TASK-146` got to
split via `CPACK_COMPONENTS_GROUPING IGNORE`). The working approach,
verified empirically: invoke `cpack` **once per component**, overriding
`CPACK_COMPONENTS_ALL`, `CPACK_WIX_UPGRADE_GUID`, `CPACK_WIX_PATCH_FILE`,
and `CPACK_WIX_EXTENSIONS` via `-D` on the command line rather than baking
component-specific WIX variables into `cmake/Packaging.cmake` (which is
shared, generator-and-component-agnostic config). This is why
`CPACK_WIX_UPGRADE_GUID`/`_PATCH_FILE` are NOT set in `Packaging.cmake` —
`TASK-151` (CI wiring) must invoke `cpack` twice with different overrides,
once per component. Exact command that works (verified this session):

```
cpack -G WIX \
  -D CPACK_COMPONENTS_ALL=server \
  -D CPACK_WIX_UPGRADE_GUID=5ADE0205-57FF-4286-849A-C112AF550215 \
  -D CPACK_WIX_PATCH_FILE="<repo>/packaging/windows/wix/server-patch.xml" \
  -D CPACK_WIX_EXTENSIONS=WixFirewallExtension
```

`CPACK_WIX_UPGRADE_GUID=5ADE0205-57FF-4286-849A-C112AF550215` is now the
**permanently fixed** server product upgrade GUID — recorded here and must
never be regenerated in a future release (a stable `CPACK_WIX_PRODUCT_GUID`
is auto-derived per-build by CPack from name+version+upgrade-code, which is
correct and expected to change per version; only the *upgrade* GUID must
stay fixed forever).

`packaging/windows/wix/server-patch.xml` injects `<ServiceInstall>` +
`<ServiceControl>` + `<fire:FirewallException>` into the CPack-generated
`<Component>` that carries `vapourwaultd.exe`, matched by its
mechanically-derived id (`CM_CP_server.bin.vapourwaultd.exe` — derived from
`COMPONENT server` + `RUNTIME DESTINATION bin`; see the fragility note in
the patch file itself). Service name/display name/description match
`Install-VaporWault.ps1`'s existing values exactly (`VaporWault` /
"VaporWault Cloud File Server" / "VaporWault self-hosted file sync
server") for consistency between the manual-script and MSI install paths.
Firewall rule matches the script's `VaporWault-TLS` name and port `4430`.

**Verified, not just written**:
1. `cpack -G WIX` with the invocation above completes with no `candle`/
   `light` errors (WiX v3.11.2 toolset, fetched as a portable NuGet
   package in this session since no system-wide WiX install was available
   and installing one via Chocolatey hit a sandbox permission error — see

2. Inspected the intermediate `files.wxs` before compilation — confirmed
   the patch's `<ServiceInstall>`/`<ServiceControl>`/`<fire:FirewallException>`
   landed as children of exactly the right `<Component>`, alongside (not

3. **Non-mutating structural verification**: ran `msiexec /a
