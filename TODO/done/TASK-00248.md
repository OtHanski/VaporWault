Found during `TASK-00152`'s real install/uninstall/upgrade verification, while
attempting to actually start the `VaporWault` Windows Service for the first time
this project has ever registered a real one.

`src/server/vw_winsvc.c`'s `svc_main()`:

```c
report_status(SERVICE_START_PENDING, NO_ERROR, 3000);
int rc = vw_server_main_run(g_argc, g_argv);   /* blocks until shutdown */
report_status(SERVICE_STOPPED, ..., 0);
```

`report_status(SERVICE_RUNNING, ...)` is never called anywhere in the file.
`vw_server_main_run()` blocks for the server's entire lifetime (config load,
store open, GC thread start, then the accept loop) and only returns at shutdown.
So the Service Control Manager sees `START_PENDING` once, then nothing, and
times out waiting for `RUNNING` — it will *always* fail to start the service,
on any machine, independent of config/cert/environment correctness. This is a
plain code-reading finding (the absence is unambiguous), not an inference from
a single failed test run.

Confirmed on this session's real install (server MSI, fixed config + cert in
place — the server binary itself starts and listens fine when run directly as a
console process with the identical config): `Start-Service` failed, and
`sc query` never showed `RUNNING`. (This session's machine also has a Microsoft
Defender Exploit Guard ASR policy blocking `services.exe`-launched processes
outright — a separate, machine-specific, IT-managed restriction, *not* this bug
— so the two failure modes are stacked here; this bug would still block a
successful start on an unrestricted machine even with Defender out of the way,
per the code reading above.)

Fixing this correctly needs `vw_server_main_run()` (shared, cross-platform) to
signal "initialization complete, about to enter the accept loop" back to the
caller — e.g. an optional ready-callback parameter, or a thread-safe flag/event
`vw_winsvc.c` can poll — rather than reporting `RUNNING` optimistically before
config/listen actually succeed (which would misreport a config or bind failure
as a successfully running service). Left to `SRV.01` to design given
`vw_server_main_run()`'s existing structure and Linux-side constraints; not
attempted here since it touches shared server-startup code outside this
finding's own scope.

## Acceptance criteria

- `Start-Service VaporWault` (or `net start`) succeeds and `sc query` reports
  `RUNNING` once the server has actually bound its listen socket, on a real
  Windows install — not just structurally reasoned through.
- A genuine startup failure (bad config, listen bind failure, etc.) still
  reports a stopped/error state to SCM rather than falsely claiming `RUNNING`.
- Regression test or manual verification note added confirming the fix, per
  standing QA.06 policy for bugs found during verification.

QA.06 [2026-09-07]: **Fixed and verified for real.** Added
`vw_server_main_set_ready_callback(void (*cb)(void))` to
`vw_server_main.h`/`.c` — a static function-pointer setter, called by
`vw_server_main_run()` exactly once, right after the listen socket is
bound and the worker pool has started (i.e. genuinely ready to serve),
and before entering the accept loop. Any earlier startup failure (bad
config, bind failure, thread-pool allocation failure, etc.) still takes
its existing `goto shutdown` path and never reaches this call, so a real
failure can't be misreported as `RUNNING`. `vw_winsvc.c`'s `svc_main()`
registers this callback (`on_server_ready`, calling
`report_status(SERVICE_RUNNING, NO_ERROR, 0)`) before calling
`vw_server_main_run()`.

Built clean on Windows (`vapourwaultd.exe` via the existing
`build-msvc-105` MSVC/Ninja config, zero warnings). Console-mode
operation re-verified unaffected (`vapourwaultd --config ...` still
starts, logs, and listens normally — the callback is simply unset/no-op
outside the Windows-service path).

CQR.08 [2026-09-07]: Reviewed `vw_server_main.c`/`.h` and `vw_winsvc.c`
directly.

- The new `g_ready_cb` static function pointer follows the exact same
  pattern as the existing `g_running`/`g_net_ctx` globals in the same
  file — no new concurrency concern introduced: it's set once (by
  `vw_winsvc.c`, on the same thread, before `vw_server_main_run()` is
  called) and read once (from within `vw_server_main_run()` itself,
  single-threaded at that point in startup), never mutated concurrently.
- The call site is correctly placed *after* every fallible startup step
  (`vw_net_listen`, thread-pool allocation/worker creation) and *before*
  the accept loop — confirmed by re-reading every `goto shutdown` path
  above it: none of them can be reached after the callback fires, so a
  real startup failure still can't be misreported as `SERVICE_RUNNING`.
  This was the exact correctness property the original finding flagged
  as necessary.
- `on_server_ready()` in `vw_winsvc.c` does the minimum correct thing
  (`report_status(SERVICE_RUNNING, NO_ERROR, 0)`); doesn't touch
  `g_svc_status` fields outside what `report_status()` already manages.
- Console-mode (non-Windows-service) operation is unaffected by
  construction: `g_ready_cb` defaults `NULL` and the call site is
  guarded, and this was independently confirmed by an actual console run
  after the fix (this task's own notes above), not just reasoned through.
- No dead code, no unused parameters, naming consistent with the file's
  existing conventions (`g_` prefix, `vw_server_main_` function prefix).

Only naming nit, not blocking: `vw_server_main_set_ready_callback`'s
single-callback (last-writer-wins, no unregister) design is a reasonable
match for this file's single-server-instance-per-process model, same as
`vw_server_main_request_stop`'s own no-context design — not flagging as
a defect, just noting it's intentionally minimal, matching the rest of
this file's API shape.

No blocking findings. Sign-off: `CQR.08` requirement satisfied. Ready for
`done`.
