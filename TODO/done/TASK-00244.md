Filed while fixing `TASK-00241` (`LoginActivity`'s `connectButton` becoming
completely unreachable once enough saved profiles accumulated). Root cause
there: a `RecyclerView` with `android:layout_height="wrap_content"` nested
inside a plain `ScrollView` only reliably auto-measures up to roughly one
screenful of content — past that, the `ScrollView`'s total scrollable
height gets capped at approximately the `RecyclerView`'s own height, and
every sibling view declared after it in the `LinearLayout` is dropped from
layout entirely (not merely scrolled off-screen — confirmed via
`uiautomator` being unable to find `connectButton` at all, even off-screen,
with 10 saved profiles present). Fixed there by giving `profileList` a
fixed height (`240dp`) instead of `wrap_content`, so its own scrolling is
internal/nested rather than relying on the outer `ScrollView`'s wrap-content
auto-measure.

The exact same pattern (a `wrap_content`-height `RecyclerView` inside a
`ScrollView`, with more content below it in the same `LinearLayout`) exists
in two other screens, found while checking whether this was an isolated
layout or a repeated one:

- `activity_shares.xml`: `shareList` and `linkList`, both `wrap_content`,
  each followed by more content (an empty-state `TextView`, a divider, the
  next section, and — after both lists — `statusText`).
- `activity_vaults.xml`: `vaultList`, `wrap_content`, followed by an
  empty-state `TextView`, a divider, the create-vault form, and
  `createVaultButton`/`statusText`.

Neither has been confirmed to actually exhibit the failure (that requires
enough shares/links/vaults accumulated to exceed one screenful, the same
way `TASK-00241`'s bug needed ~10 profiles) — this is a "same shape, worth
checking" finding, not a confirmed second occurrence. Not fixed here:
out of `TASK-00241`'s scope (LoginActivity only) and not confirmed as a
live bug yet.

## Acceptance criteria

- Confirm (or rule out) the same failure mode in `SharesActivity` (enough
  shares/links to exceed one screen) and `VaultActivity` (enough vaults).
- If confirmed, apply the same fix (a fixed/bounded height instead of
  `wrap_content`, or another approach that avoids the underlying
  `RecyclerView`-in-`ScrollView` auto-measure hazard) to whichever
  `RecyclerView`(s) actually reproduce it.
- A regression test (matching `TASK-00241`'s `LoginProfileScaleTest`
  pattern) for whichever screen(s) turn out to need the fix.

## Notes

MOB.10, 2026-09-04: Both confirmed, both fixed.

**Confirmed via new regression tests** (efficient seeding, matching
`LoginProfileScaleTest`'s own approach: seed directly via `VwClient`/
`VwVault` API calls — real server round trips, but no slow UI-driven
dialog interaction needed 10 times over):

- `android/app/src/androidTest/java/com/vaporwault/client/SharesScaleTest.kt`
  — seeds 10 folders each shared once (`client.shareGrant`), then asserts
  `linkList`'s own section header ("Public links you've created", declared
  after `shareList` in `activity_shares.xml`'s `LinearLayout`) is still
  reachable. Failed exactly as predicted before the fix; passes after.
- `android/app/src/androidTest/java/com/vaporwault/client/VaultsScaleTest.kt`
  — seeds 10 vaults (`VwVault.setup`), then asserts `createVaultButton`
  (declared after `vaultList`) is still reachable. Same result.

**Fix**: identical to `TASK-00241`'s — `activity_shares.xml`'s `shareList`
and `linkList`, and `activity_vaults.xml`'s `vaultList`, all changed from
`android:layout_height="wrap_content"` to a fixed `240dp`, matching the
exact value `TASK-00241` used. Not extended to the empty-state visibility
toggle `TASK-00241`'s own review added for `LoginActivity` — unlike
`profileList` (which had no empty-state indication at all before that
fix), `SharesActivity`/`VaultActivity` already show `emptySharesText`/
`emptyLinksText`/`emptyVaultsText` below an empty list, so the fixed
240dp box next to that text is acceptable, not the same "purely blank
space, no indication anything's supposed to be there" regression — judged
not worth the added scope here.

**A real, separate bug found while re-verifying `TASK-00243`'s
`VaultFlowTest` against `VaultsScaleTest`'s own seeded data**: there is no
`VAULT_DELETE` wire message at all (checked `docs/PROTOCOL.md` and
`src/core/vw_proto.h` — genuinely absent, not just unexposed in this UI),
so `VaultsScaleTest`'s 10 seeded vaults can never be cleaned up — only
their underlying folders can be deleted, leaving 10 permanently-orphaned
vault records in the test account. `VaultFlowTest`'s own
`waitForAll("vaultUnlockButton").last()` silently assumed the newest vault
always sorts last, which broke for real once those orphans existed.
Fixed in `TASK-00246`'s own notes (landed in the same session) by
selecting the vault row by its actual (monotonically-assigned) ID instead
of list position — see that task for the fix; flagged here since it was
this task's own new seed data that exposed it.

**Acceptance criteria met**: both screens confirmed and fixed, both with
a dedicated regression test extending the same pattern this project
already uses.

## Review

CQR.08, 2026-09-04: Independent review of this task's own changes
(`activity_shares.xml`, `activity_vaults.xml`, `SharesScaleTest.kt`,
`VaultsScaleTest.kt`) found no issues specific to it — the fix is a
mechanical, low-risk repeat of `TASK-00241`'s already-reviewed pattern
(fixed `240dp` height instead of `wrap_content`), and both new tests were
independently confirmed in this session to fail before the fix and pass
after, for both screens.

The one real finding from this task's own work — `VaultsScaleTest`
permanently orphaning vault records with no way to delete them, breaking
`VaultFlowTest`'s `.last()` assumption — was correctly not fixed by
adding cleanup that can't exist (there is no `VAULT_DELETE` message);
instead fixed at the actual point of fragility (`VaultFlowTest`'s
selection logic), landed and reviewed under `TASK-00246` since that's
where the fix lives. Cross-referenced correctly in both directions.

No blocking findings. **Status: done.**
