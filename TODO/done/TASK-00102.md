Two small, pre-existing findings surfaced by SEC.07's review of `TASK-00092`
(granular admin capability bits) — neither introduced or worsened by that
task, both low-severity, filed as their own cleanup rather than blocking
TASK-00092's closure.

1. Five of the six admin-only handlers in `src/server/vw_file_handlers.c`
   (`handle_user_quota_set`, `handle_user_list`, `handle_user_suspend`,
   `handle_audit_query`, `handle_invite_create`) fetch a
   `vw_user_record_t urec` (which carries `password_hash`/`password_salt`,
   even though those specific fields are zeroed by the store layer before
   return) but never `secure_zero`/`memset` the local copy before it goes
   out of scope. `handle_cluster_status` already does this correctly —
   bring the other five in line with it.
2. `handle_cluster_status`'s "caller is not an admin at all" branch returns
   `VW_ERR_PERMISSION`, while every other admin handler returns
   `VW_ERR_AUTH_REQUIRED` for that same case (reserving `VW_ERR_PERMISSION`
   for "admin, but lacking the specific capability" per `TASK-00092`). Fix
   `handle_cluster_status` to match: `VW_ERR_AUTH_REQUIRED` for "not admin",
   `VW_ERR_PERMISSION` for "admin, lacks `VW_CAP_CLUSTER_MGMT`".

## Acceptance criteria

- All six admin handlers zero any fetched `vw_user_record_t` before it goes
  out of scope.
- `handle_cluster_status` distinguishes "not admin" from "admin, wrong
  capability" using the same error-code convention as the other five
  handlers.
- No behavior change beyond the error code returned in (2) — confirm no
  existing test or documented client behavior depends on
  `CLUSTER_STATUS`'s current (inconsistent) "not admin" code.
