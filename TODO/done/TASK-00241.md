Discovered while writing `TASK-00235`'s instrumented tests, which (as a test
hygiene bug, not intentionally) created a fresh saved profile on every run
without cleaning up the previous one. With **6** accumulated saved profiles
in `LoginActivity`'s `profileList`, the `connectButton` (and the rest of
the add-profile form below it) stopped appearing in the view hierarchy
entirely — confirmed via `uiautomator dump`: zero matches for
`connectButton` or "CONNECT" anywhere in the dump with 6 profiles present,
and it reappeared immediately after removing profiles back down to 0.

Root cause not fully diagnosed — `activity_login.xml`'s outer container is
a plain `ScrollView` wrapping a `LinearLayout` with `wrap_content` height
for both the `profileList` `RecyclerView` and the form below it, so this
isn't an obviously-bounded layout. Whether this is a `RecyclerView`
inside `ScrollView` measurement pathology, an Android canvas/view height
limit, or something else wasn't pinned down under this task's time budget
— worth root-causing properly rather than guessing at a fix.

A real user is unlikely to accumulate 6 profiles casually, but it's not an
unreasonable number for someone using this app across several personal
servers/accounts, and the failure mode (the entire "add a new profile" form
becomes completely unreachable, not just visually cramped) is severe enough
to be worth fixing rather than dismissing as a pathological edge case.

## Acceptance criteria

- Root cause identified (not just worked around).
- `LoginActivity` remains fully usable (all form fields and the Connect
  button reachable) with at least 10 saved profiles.
- A regression test exists (can extend `TASK-00235`'s instrumented suite)
  that seeds N saved profiles and asserts `connectButton` is still
  discoverable.

MOB.10, 2026-09-03: Root-caused and fixed, verified against a real emulator
(`vw_test` AVD), not just reasoned about.

**Root cause**: `activity_login.xml`'s `profileList` `RecyclerView` had
`android:layout_height="wrap_content"` nested inside a plain `ScrollView`.
Empirically confirmed (screenshots + `uiautomator` dumps + logcat lifecycle
tracing, on a freshly wiped AVD to rule out any leftover-install
confusion — an earlier pass of this investigation chased a red herring
from a stale APK signature on a not-fully-clean emulator instance before
that wipe) that a `RecyclerView`'s `wrap_content` auto-measure inside a
`ScrollView` only reliably works up to roughly one screenful of content.
Past that point, the `ScrollView`'s total scrollable height gets capped at
approximately the `RecyclerView`'s own height, and every sibling declared
after it in the `LinearLayout` — the entire add-profile form, including
`connectButton` — is dropped from layout entirely, not merely scrolled
off-screen: confirmed via a new instrumented test
(`LoginProfileScaleTest`) where `uiautomator`'s accessibility-tree search
for `connectButton` timed out after the full 20s wait with 10 saved
profiles present, while the identical search succeeded in ~1s with 0
profiles. The originally-reported "~6 profiles" threshold is a function of
item height vs. that reporter's device screen metrics, not a fixed
item-count limit — this build's emulator (411dpi, 1080x2340) needed 10 to
reproduce it reliably.

**Fix**: `profileList` now has a fixed `android:layout_height="240dp"`
instead of `wrap_content` (`activity_login.xml`). This makes its own
`MeasureSpec` `EXACT` instead of `UNSPECIFIED`, so it scrolls its own
content internally (nested scrolling, enabled by default) regardless of
profile count, while every view below it stays reachable in the outer
`ScrollView` no matter how many profiles exist. Verified: rebuilt, wiped
the AVD to a clean slate, reinstalled, and reran `LoginProfileScaleTest`
with 10 seeded profiles — passes in ~5.4s (matching the 0-profile
baseline's speed), vs. timing out entirely before the fix.

**Regression test**: `android/app/src/androidTest/java/com/vaporwault/client/LoginProfileScaleTest.kt`
— seeds 10 profiles directly via `ProfileStore` (no live server needed,
matching the acceptance criteria's "at least 10"), launches
`LoginActivity`, asserts `connectButton` is discoverable.

**Discovered while fixing this** (not fixed here, out of this task's
scope): the identical `RecyclerView`-in-`ScrollView` pattern exists in
`activity_shares.xml` (`shareList`, `linkList`) and `activity_vaults.xml`
(`vaultList`) — filed as `TASK-00244` to confirm/fix if those screens can
actually accumulate enough items to reproduce it.

## Review

CQR.08, 2026-09-04: Found one real regression while reviewing the
`activity_login.xml` change — fixed here rather than filed separately,
since it's small and directly caused by this task's own fix:

- **Fixed**: giving `profileList` a fixed `240dp` height closes the
  original bug, but with **zero** saved profiles (the common case — every
  fresh install) it now always reserved that 240dp as blank space above
  the add-profile form, since nothing conditioned the RecyclerView's
  visibility on whether it had anything to show. `LoginActivity.kt` now
  hides both `profileList` and `savedProfilesLabel` (`View.GONE`) when
  the profile list is empty, re-checked after every removal, matching
  this app's existing empty-state convention elsewhere (`emptyVaultsText`,
  `emptySharesText`, `emptyLinksText`). `LoginProfileScaleTest`'s own
  0-profile baseline case would not have caught this (it only asserts
  `connectButton` is reachable, not that `profileList` is hidden) — not
  extended to assert visibility, since that's a cosmetic property this
  task's own scope (profile-count reachability) doesn't need to pin down
  further.

No other findings. The root-cause analysis and fix for the actual filed
bug (RecyclerView-in-ScrollView breaking past ~1 screenful) are sound and
verified against a real emulator, not just reasoned about.
