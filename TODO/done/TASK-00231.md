Surface the existing sharing/public-link wire messages (already reachable
via `VwClient` per TASK-00226: `share_grant`/`_revoke`/`_list`,
`link_create`/`_revoke`/`_list`) in the UI, matching the feature parity the
web frontend already has (grant/revoke user shares, create/revoke/list
public links including password-protected and expiring links).

## Acceptance criteria

- A file/folder can be shared with another user and the grant later revoked,
  entirely through the UI.
- A public link (optionally password-protected, optionally expiring) can be
  created, listed, and revoked through the UI.

## Notes

MOB.10, 2026-09-02: Added `action_share`/`action_get_link` to the per-entry
overflow menu (`file_entry_actions.xml`), each opening a small dialog
(`dialog_share.xml`/`dialog_link.xml`: username-or-nothing, permission
radio group, optional expiry-in-days) that calls the existing
`VwClient.shareGrant`/`linkCreate`. A new `SharesActivity` (reachable from
`FileBrowserActivity`'s top bar in both plaintext and vault mode — sharing
is account-wide, not folder-scoped) lists share grants and public links
(`listShares(0)`/`listLinks()`) with a Revoke button each.

**Runtime verification**, through the UI only, against a real
`vapourwaultd`: shared `TestFolder` with a second account (view
permission), confirmed it appeared in `SharesActivity`, revoked it,
confirmed it disappeared. Created a public link with a password + 7-day
expiry (link token shown once, 64 hex chars as the wire protocol
specifies), confirmed it appeared in `SharesActivity`, revoked it,
confirmed it disappeared.

**Real bug found and fixed**: `SharesActivity` initially showed revoked
shares/links right alongside active ones — `SHARE_LIST`/`LINK_LIST` return
revoked entries too (they're history, not filtered server-side; see
`ShareEntry`/`LinkEntry`'s own `revoked` field), and the screen wasn't
filtering on it. Tapping Revoke appeared to silently do nothing (the row
just stayed, with a still-live-looking Revoke button) even though the
revoke had actually succeeded. Fixed by filtering `!it.revoked` when
loading both lists — this is a "what's currently active" management view,
not a full history, so hiding revoked entries rather than labeling them is
the right UX here.

**Also fixed before it ever shipped**: three fresh instances of the
`lastError()`-on-the-wrong-thread bug already documented in TASK-229/230
(one in `AccountActivity`, none actually in this task's own new code —
`promptShare`/`promptGetLink` were written correctly the first time by
copying the by-then-established fixed pattern directly).

**Observed, not a bug**: a `Get link` attempt failed with
`vw_err_t=102` (`VW_ERR_NET_CLOSED`) after several minutes of idle UI
testing between requests — the underlying TCP connection had gone stale.
Force-stopping and relaunching the app (fresh session resume) fixed it
immediately. This is expected behavior for a single-persistent-connection
client with no reconnect-on-stale-socket logic (Android has no daemon
process to own that resilience the way the desktop client's daemon does)
— not something this task's scope covers, noting it for awareness rather
than as a finding to act on here.

No blocking findings on self-review beyond the one already fixed above.
