## Work

- Gateway API: passthrough of `NOTIFY_PREFS_GET`/`_SET` into HTTP/JSON,
  per `docs/PROTOCOL.md` (consumed as-is).
- Frontend: a "Notifications" section in account settings, same category
  list and semantics as `TASK-00210`'s GUI version.

## Security note (`security-sensitive`)

Standard posture for any new gateway-exposed, account-scoped endpoint
per `ARCHITECTURE.md`'s Risk table entry on the gateway — confirm the
endpoint only ever operates on the calling session's own account, never
accepts a caller-supplied user id.

## Acceptance criteria

- End-to-end through the actual browser frontend: toggling a preference
  changes real server-side state, confirmed by a subsequent fetch.

WEB.09 [2026-08-27]: Implemented.

- Gateway API: `POST /api/notify/prefs` (GET-equivalent — this file
  routes every endpoint through POST, including reads, e.g. `/api/search`;
  no body needed) and `POST /api/notify/prefs/set` (`{"prefs": <uint32>}`
  → `{"prefs": <uint32>}`, the stored value echoed back). True thin
  passthrough as directed — the gateway never decodes the bitmask into
  named fields; both handlers are ~20 lines calling
  `vw_client_notify_prefs_get/_set` directly (the gateway is its own
  authenticated `vw/1` client per `CLAUDE.md`'s charter, same as every
  other endpoint in this file — no daemon IPC hop).
- **Security note satisfied by construction**: both handlers derive the
  account entirely from `require_session()` (the caller's own session
  cookie) — neither request body has a user_id/account_id field anywhere,
  so there is no way to address any account but the caller's own. Same
  pattern as every other endpoint in this file.
- Frontend: new `#settings-view` section (`web/index.html`) — this
  frontend had no account-settings area at all before this task, so this
  is a new minimal container, not an addition to an existing one — with
  a "Settings" button in the browser view's header (matching the
  share/history views' own back-button navigation pattern) and one
  checkbox per category with a description, built from a local
  `NOTIFY_CATEGORIES` table (`web/src/main.ts`) mirroring
  `vapourwault-cli`'s and the desktop GUI's own copies exactly (name/bit/
  description) so all three surfaces describe the same four categories
  identically. `web/src/api.ts`: `getNotifyPrefs()`/`setNotifyPrefs()`,
  following `search()`'s exact `apiPost` pattern.
- Toggling a checkbox does the same read-current → flip-one-bit →
  send-complete-bitmask dance as the CLI/GUI (§7.13's documented
  contract), reverting the checkbox optimistically on any failure and
  always re-rendering from the SET response's echoed value on success
  (never assumes the write applied) — same defensive shape `TASK-00210`'s
  GUI panel uses.
