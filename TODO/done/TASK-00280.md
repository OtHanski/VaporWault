`TASK-00275` implemented the server side of `VAULT_DELETE`
(`docs/PROTOCOL.md` §7.11.4, revision 33). The web gateway
(`vapourwault-web-gateway`) and browser frontend (`web/`) have no way to
reach it yet.

## Acceptance criteria

- Gateway HTTP/JSON endpoint (`vw_gateway_api.c`) wrapping `VAULT_DELETE`,
  matching the existing vault-create/list endpoint pattern.
- Frontend (`web/src/api.ts` + the vault UI) gains a delete action, gated
  behind confirmation, surfacing `VW_ERR_VAULT_NOT_EMPTY` as an actionable
  message rather than a raw error code.
- Consumes `docs/PROTOCOL.md` as-is per this role's constraint (`CLAUDE.md`
  — WEB.09 never reinterprets the wire protocol unilaterally).

## Notes

ARCH.00 [2026-09-10]: Filed from the full-project review (`TASK-00269`),
blocking on `TASK-00275`'s server implementation per `CLAUDE.md` routing

WEB.09 [2026-09-11]: Implemented.

- `src/gateway/vw_gateway_api.c`: new `handle_vault_delete()` (same
  shape as `handle_share_revoke`/`handle_link_revoke` — read `vault_id`,
  call the client-core wrapper, `send_json_status(conn, 200, "ok", NULL)`
  on success), routed at `POST /api/vault/delete`. Reuses
  `vw_client_vault_delete()` from `TASK-00278` directly — no new
  client-core code needed, since the gateway already links
  `vw_client_core.c` as its own authenticated `vw/1` client.
- `send_file_op_error()` needed a new `case VW_ERR_VAULT_NOT_EMPTY:` →
  `409 vault_not_empty`. Without it, this ordinary business-logic outcome
  would have fallen through to the default branch, which evicts the
  session and returns a generic 500 — caught by the new gateway
  integration test below, not by inspection.
- `web/src/api.ts`: `vaultDelete(vaultId)` → `POST /api/vault/delete`,
  matching `revokeShare`/`revokeLink`'s pattern.
- `web/index.html` + `web/src/main.ts`: a "Delete vault" button in the
  existing vault banner (shown when browsing a vault's registered
  folder, alongside the existing Lock/Unlock buttons — there is no
  separate all-vaults management view in this frontend to add it to
  instead). Gated behind `window.confirm`, matching `handleDelete`
  (file delete)'s existing convention for genuinely destructive actions
  — unlike share/link revoke, which this frontend doesn't confirm.
  Surfaces `vault_not_empty` as a specific actionable message rather than
  the generic `${status}` fallback every other handler here uses.
- `tests/integration/test_gateway.py`: `vault_delete()` client helper
  plus three new tests — basic delete + list, non-owner gets 403, and a
  vault with a live version gets 409 `vault_not_empty` (not 500).

**Found and fixed a real bug in `TASK-00275`'s server implementation**
while writing the third test above — see the correction note now on
`TASK-00275` for the full mechanism (`send_error`'s `VW_MSG_ERROR` used
an 8-byte payload where `vw_client_core.c`'s `revoke_common()` expected
4, so the not-empty rejection was received as `VW_ERR_PROTO_TOO_LARGE`
instead of `VW_ERR_VAULT_NOT_EMPTY`, and the gateway's own missing switch
case then evicted the session and returned a generic 500 on top of that).
Both bugs are fixed together; this is exactly why this task's own
end-to-end gateway test — not the unit tests or the wire-level Python
test, both of which passed throughout — is what actually caught it.

-DVW_WERROR=ON`) rebuilds `vapourwaultd`/`vapourwault-web-gateway` clean;

CQR.08 [2026-09-11]: Found a real bug in `handleDeleteVault()`
(`web/src/main.ts`): it called `lockVault()` unconditionally on a
successful delete, even when the deleted vault was not the one currently
unlocked in memory — browsing to and deleting an unrelated empty vault
while a different vault was unlocked would silently wipe that unrelated
vault's still-valid VK, forcing an unnecessary re-unlock. Fixed: only
locks when `unlockedVault?.vaultId === currentFolderVaultId`. Re-verified:
`tsc -p tsconfig.json` compiles clean, full `test_gateway.py` (40/40) and
`test_vault.py` (18/18, including the ownership-ordering regression test
added during `TASK-00275`'s review) still pass. No other blocking
findings. Sign-off: `CQR.08` requirement satisfied. Moving to `done`.
