Dedicated security pass across the whole Android client, since it's new
externally-reachable-credential surface (mirrors the review rigor the web
gateway got in `TASK-00127`'s wave).

Scope:
- TLS verification/pinning strategy on Android — confirm the JNI bridge
  never allows `VW_CERT_VERIFY_NONE`-equivalent behavior in a release build,
  matching the gateway's own hardened requirement.
- `AndroidKeyStore` usage correctness (TASK-00227): key generation parameters,
  behavior when hardware backing is unavailable, exportability guarantees.
- Vault crypto parity (TASK-00230): confirm the KDF parameter floor and
  per-chunk nonce derivation match the desktop/web implementations exactly,
  and that passphrase material never persists or logs.
- SAF fd-handling (TASK-00228): confirm no path-traversal-equivalent issue is
  possible through a maliciously-named SAF document, and that only
  user-explicitly-granted URIs are ever touched.
- Auth token transport: confirm the Android client's `AUTH_REQUEST.auth_token`
  derivation matches what the live server actually expects — `docs/PROTOCOL.md`
  §8.1 and `src/client/vw_client_core.c`'s comment disagree about whether this
  is Argon2id or `SHA-256(password)`; verify against the real server code path
  (`vw_auth.c`) before shipping, don't trust either comment.

## Acceptance criteria

- Every finding is tagged `blocking` or `advisory` per the routing rules;
  `blocking` findings resolved (with MOB.10) before this closes.
- Findings feed TASK-00235's regression test list.

- SEC.07, 2026-09-02: Full pass across all five scoped areas.

  **BLOCKING, found and fixed**: the Android app had **no way, anywhere in
  the UI, to supply a CA certificate** — `LoginActivity`/
  `VwAccountRegistry.addProfile` always passed the default empty
  `caCertPemPath`, meaning `vw_jni_bridge.c` always configured
  `VW_CERT_VERIFY_NONE` for *every real connection*, not just testing.
  This silently defeated the entire point of `docs/PROTOCOL.md`'s TLS 1.3
  requirement for this client. Fixed: `LoginActivity` gained an "Import
  server CA certificate" button (SAF picker → copies the PEM into the
  app's private storage, since `vw_net.c` needs a real filesystem path,
  not a `content://` URI — same reason `VaultTransferer` stages through
  cache) and a persistent on-screen warning
  (`⚠ No CA certificate imported — the server's TLS certificate will NOT
  be verified...`) when none is imported, so the insecure state is visible
  rather than silent. **Verified end-to-end, not just code-reviewed**:
  imported the real test server's `test.crt` (confirmed via
  `server.conf`'s `cert_pem_path` that it's the exact cert in actual use),
  connected, and reached `FileBrowserActivity` — a real
  `VW_CERT_VERIFY_REQUIRED` handshake succeeded against a matching cert,
  not just "the code compiles."

  **AndroidKeyStore (TASK-227), re-reviewed, no new findings**:
  AES-256-GCM, `PURPOSE_ENCRYPT|DECRYPT`, 128-bit GCM tag, StrongBox-first
  with an explicit SDK-gated TEE fallback, hardware-backing checked and
  logged (not silently assumed) at key-creation time via
  `KeyInfo.securityLevel`/`isInsideSecureHardware`. Exportability: a
  symmetric AndroidKeyStore key has no export path at all by construction
  (unlike an asymmetric key pair's public half) — satisfied structurally,
  nothing to add. Secrets zeroed after use on both the write and read path
  in `ProfileStore`.

  **Vault crypto parity (TASK-230), re-reviewed, no new findings**:
  Android cross-compiles `vw_vault.c`/`vw_crypto.c` **unmodified** — the
  KDF floor and per-chunk nonce derivation are byte-identical to
  desktop/web *by construction*, not something to independently re-derive
  and compare (unlike the web frontend's `vault-crypto.ts`
  reimplementation, which genuinely needs that kind of check). Confirmed
  zero `Log`/`LOGE` call sites anywhere near passphrase handling, Kotlin
  or native. Real cross-client interop is still not empirically verified
  (already disclosed in TASK-230's own Notes; not re-litigated here,
  logical confidence stays high given unmodified shared C code).

  **SAF fd-handling (TASK-228), reviewed, no new findings**: every local
  staging path (`FileTransferer`, `VaultTransferer`) uses
  `File.createTempFile` with a random name in the app's own private
  `cacheDir` — no externally-controlled string ever forms a local
  filesystem path. User-visible read/write destinations are chosen
  through Android's own SAF picker UI (opaque `content://` URIs mediated
  by the system, not app-constructed paths) — architecturally not
  vulnerable to a "maliciously-named document" the way a naive
  `File(userSuppliedName)` would be. A remote leaf name (from a picked
  local document's display name, or a server-returned entry name) is
  validated server-side by the pre-existing `vw_leaf_name_validate`
  (`vw_file_handlers.c`, called from both the rename and create-file
  paths) — shared by every client, so Android introduces no new attack
  surface here beyond what desktop/web already have.

  **Auth token derivation, ADVISORY (not blocking) — filed for PRT.04**:
  `docs/PROTOCOL.md` §8.1's own text is internally ambiguous, offering
  "Argon2id locally" as an alternative to "`SHA-256(password)`" — but
  client-side Argon2id is structurally impossible here: `AUTH_REQUEST` is
  single-round-trip, so the client has no way to learn the server's
  per-account salt before computing `auth_token`. Verified against
  `src/server/vw_auth.c`'s actual verification path
  (`vw_crypto_argon2id_verify(real_hash, real_salt, password, ...)`,
  where `password` is whatever the wire sent) that the real, consistently
  implemented scheme — matching `vw_client_core.c`'s own comment and
  Android's identical usage — is client-side `SHA-256(password)`, verified
  server-side via Argon2id against the stored hash. The code is correct
  and consistent everywhere; the doc's stale "Phase 1 will define a proper
  SRP" framing (the project is now at Phase 21) and the misleading
  "Argon2id locally" alternative should be cleaned up, but that's a
  documentation fix to a document `PRT.04` owns per `CLAUDE.md` — not
  something to edit unilaterally here even though the fix itself is small.
  Not filing this out-of-domain issue as fixed in place, per this
  project's own routing rule; flagging it in this task's Notes and
  expecting a follow-up task for PRT.04.

  No other blocking findings. TASK-235's regression coverage should
  include: a negative TLS test (connect with a deliberately wrong/absent
  CA cert against a server requiring verification, confirm it's rejected
  — the positive case is verified above, the negative case wasn't
  separately exercised this pass since the underlying TLS verification
  logic itself is pre-existing, already-covered C code, not new Android
  logic).
