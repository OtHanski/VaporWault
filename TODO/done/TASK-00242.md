`TASK-00233`'s `build-android` CI job validates that the app compiles
(`assembleDebug`) but never boots an emulator or runs anything under
`androidTest`. `TASK-00235` wrote a real instrumented suite
(`CoreFlowTest`, in `android/app/src/androidTest/`) that has only ever been
run manually against a locally-hosted `vapourwaultd`; nothing in CI exercises
it.

Wire an emulator-backed CI job (e.g. via
`reactivecircus/android-emulator-runner` or an equivalent GitHub Actions
action) that:
- Boots an x86_64 emulator on the runner (check KVM/HAXM availability on
  `ubuntu-latest`/`macos-latest` — this needs actual verification, not an
  assumption, the same way `TASK-00233` confirmed the NDK-caching claim via
  a real `runner-images` doc fetch rather than guessing).
- Starts a real `vapourwaultd` reachable from the emulator (matching the
  local dev pattern: a throwaway TLS cert via
  `tests/integration/gen_test_cert.sh`, `adb reverse` for loopback).
- Runs `./gradlew connectedDebugAndroidTest` (or the equivalent
  `am instrument` invocation `TASK-00235` used manually) and fails the job
  on any test failure.

Coordinate with `TASK-00233`'s existing `build-android` job — this can be a
new job in the same workflow file, or a separate one; either way avoid
duplicating the SDK/NDK install steps unnecessarily.

## Acceptance criteria

- A CI job boots an emulator, starts a real server, and runs
  `CoreFlowTest` (or its CI-invoked equivalent) automatically on every
  relevant push/PR.
- The job fails visibly if the instrumented test suite fails.
- Emulator boot time / flakiness is documented if it turns out to make this
  job unreliable enough to need a retry policy.

**KVM verified, not assumed**: fetched
`reactivecircus/android-emulator-runner`'s own README rather than relying
on the `actions/runner-images` repo's Ubuntu image docs alone (those don't
mention KVM by name at all, which would have been inconclusive on its
own) — confirmed hardware-accelerated Android emulation has been
available on stock GitHub-hosted `ubuntu-latest` runners (not only paid
"larger" runners) since the Feb 2023 rollout. Pinned the action to a real
resolved commit SHA (`a421e43855164a8197daf9d8d40fe71c6996bb0d`, tag
`v2.38.0`, resolved via `gh api repos/ReactiveCircus/android-emulator-runner/tags`),
matching this workflow's existing pin-by-SHA-with-tag-comment convention
— not a guessed/fabricated hash.

**Job design**: checkout → enable KVM group perms → JDK 17 → the same
SDK/NDK/CMake component install `build-android` already uses → a minimal
server build (`vapourwaultd` + `vapourwault-server-cli` only,
`VW_BUILD_CLIENT/GUI/TOOLS/TESTS=OFF`, since those are always built
together per `CMakeLists.txt` whenever `VW_BUILD_SERVER=ON`) → a fresh
self-signed test cert (matching `tests/integration/gen_test_cert.sh`'s own
approach) → start `vapourwaultd` in the background with host/port/username/
password matching `TestServerConfig`'s defaults exactly (127.0.0.1:4430,
`androidtest2`/`TestPass456!`) so neither `CoreFlowTest` nor
`LoginProfileScaleTest` need any instrumentation-argument override → wait
for the admin socket → create the test user via `vapourwault-server-cli` →
`reactivecircus/android-emulator-runner` boots the emulator (api 34,
`default`, x86_64 — matching this project's own local dev toolchain) and
its `script:` runs `adb reverse tcp:4430 tcp:4430` (the same WSL2→Windows→
`adb reverse` pattern this project's local dev setup already uses) then
`./gradlew connectedDebugAndroidTest`. Two `if: failure()` steps dump the
server log and the HTML/XML instrumented-test reports so a CI failure is
debuggable from the Actions log alone, not just "tests failed."

**Verified end-to-end against a real local server** (not just reasoned
about) — WSL2 `vapourwaultd` + this machine's own `vw_test` AVD emulator,
`adb reverse`, then `./gradlew connectedDebugAndroidTest` exactly as the
CI job's `script:` step does:

- `LoginProfileScaleTest` (`TASK-00241`) passed twice, reliably, in ~4.5s
  both times — confirms the actual mechanics (server start, user-create,
  `adb reverse`, instrumentation invocation) are sound.
- `CoreFlowTest` (`TASK-00235`) did **not** pass in this local validation
  — but for two reasons specific to this ad-hoc local environment, neither
  of which implicates this job's design:
  1. The first attempt's server was killed outright by a stray
     `Test-NetConnection` probe I ran against its port while debugging —
     this surfaced a real, separate, serious server bug (a single failed/
     incomplete TLS handshake shuts down the *entire* `vapourwaultd`
     process, not just that one connection) — filed as `TASK-00245`
     (critical, SRV.01, security-sensitive) rather than fixed here
     (out of MOB.10's domain). A clean GitHub-hosted runner has no
     equivalent stray traffic hitting the test server's loopback-only
     port, so this specific trigger shouldn't recur there — but
     `TASK-00245` being unfixed is a latent flakiness risk for *this* job
     if anything ever does send it a malformed connection.
  2. The second (clean) attempt got much further — login, browse, and the
     new-folder dialog all worked — then timed out waiting for the new
     folder to appear, because the server logged `unhandled msg type
     0x0211` (`FILE_MKDIR`). Root-caused: my local WSL build directory's
     `vapourwaultd` binary predates `FILE_MKDIR`'s implementation (added
     revision 11, 2026-07-31; my binary was built Jul 30) — a **stale
     local binary artifact**, not a real regression. This job's own CI
     steps always build the server fresh from the checked-out revision,
     so this specific staleness can't occur there.
- Not independently re-verified: the actual GitHub-hosted runner's KVM
  behavior itself (confirmed via documentation citation above, not by
  running this exact workflow on `github.com` yet — that only happens
  once this is merged and a real workflow run executes).

**Emulator boot time / flakiness**: not exercised enough real CI runs to
have real-world data on this yet (per the acceptance criteria's own
"document if it turns out to make this job unreliable enough to need a
retry policy" — no retry policy added; revisit once this has run for
real and shown whether it needs one).

## Review

CQR.08, 2026-09-04: Found one real blocking bug while reviewing this
against `TASK-00243`'s (landed afterward, same session) test additions —
fixed here since it's this job's own gap, not a separate follow-up:

- **Fixed (blocking)**: the "Start vapourwaultd" step only created
  `androidtest2` — but `TASK-00243`'s `SharingFlowTest.grantListAndRevokeShare`
  grants a share to `TestServerConfig.shareTargetUsername` (`androidtest3`
  by default), and `SHARE_GRANT` rejects an unknown target username
  (`vw_file_handlers.c`'s `handle_share_grant`). As written, this job would
  have failed deterministically on every real run once `TASK-00243`'s
  suite landed, for a reason that has nothing to do with what the job is
  actually validating. Added a second `user-create` call for
  `androidtest3` alongside the existing one.

**Advisory, not blocking** (same note left on `TASK-00239`'s review, which
shares the pattern): the SDK/NDK/CMake install step is duplicated across
three job definitions now (`ci.yml`'s `build-android` and this job,
`release.yml`'s new `build-android`). Each already explains why in its own
comments rather than silently copying; worth a shared composite action if
a fourth job ever needs it, not worth the churn for three.

**Status: done.** The one blocking finding is fixed; the CI mechanics
themselves (server startup, `adb reverse`, instrumentation invocation)
were already verified against a real server in this session per the notes
above.
