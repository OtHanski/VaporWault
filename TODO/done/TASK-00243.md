`TASK-00235`'s `CoreFlowTest` automates login → browse → upload → download →
delete only. `TASK-00235`'s own acceptance criteria called for coverage of
the full "login→browse→transfer→vault→share path," but vault
(`VaultActivity`: create/unlock/browse/upload/download) and sharing/link
management (`SharesActivity` and the share/link dialogs added in
`TASK-00231`) ended up with zero instrumented coverage — disclosed as a gap
in `TASK-00235`'s closing notes rather than claimed as done.

Extend `android/app/src/androidTest/java/com/vaporwault/client/` with
additional test classes (reusing `TestServerConfig`/`UiTestHelpers` from
`TASK-00235`) covering:
- Vault: create a vault with a passphrase, upload a file into it, exit and
  re-unlock with the correct passphrase, verify the file is still there and
  byte-identical; a negative case with a wrong passphrase asserting it's
  cleanly rejected (matching the manual verification already done in
  `TASK-00230`, now automated).
- Sharing: grant a share to another account, verify it appears in
  `SharesActivity`'s share list, revoke it, verify it disappears (or is
  filtered — matching the existing revoked-share bug fix from `TASK-00231`).
- Public links: create a link (with and without a password/expiry), verify
  it appears in `SharesActivity`'s link list, revoke it.

This will also need a second real test account (or account state) for the
share-grant target, since `TestServerConfig` currently only configures one
account.

## Acceptance criteria

- Vault create/unlock/upload/download, including a wrong-passphrase negative
  case, is covered by an instrumented test.
- Share grant/list/revoke and link create/list/revoke are each covered by an
  instrumented test.
- All new tests pass against a real `vapourwaultd`, verified via server-log
  cross-reference the same way `TASK-00235`'s original suite was.

## Review

CQR.08, 2026-09-04: Independent review surfaced several real issues in
this task's own changes. Two were genuine regressions in the
`FileBrowserActivity` permission fixes, fixed here; the rest are noted
below.

**Fixed (would have been blocking)**:

- `takePersistableUriPermission` in `openDocument`/`createDocument` was
  unguarded. A document provider that rejects a persistable grant outright
  (some third-party/cloud SAF providers do) would throw `SecurityException`
  synchronously in the picker callback, crashing `FileBrowserActivity`
  before the transfer this fix was meant to protect even started — worse
  than the bug it fixed. Now wrapped in try/catch; a rejected persist
  request no longer blocks the transfer that would otherwise have worked
  fine without it.
- Every picked document now took a persisted grant with nothing ever
  releasing it. Android caps an app at 128 persisted URI grants total; a
  long-lived install doing enough distinct uploads/downloads (each
  `OpenDocument`/`CreateDocument` result is one-shot, never reused) would
  eventually hit the cap and start failing on *every* subsequent transfer.
  `awaitAndRefresh` now releases the grant once the transfer completes
  (success or failure) — a persisted grant is only needed long enough to
  survive to the background job actually running, not forever.
- `UiTestHelpers.grantNotificationPermission()` had no SDK-version guard,
  unlike the production request it mirrors (`FileBrowserActivity` gates
  its own request on API 33+). `minSdk` is 26; running this suite against
  a pre-33 emulator/device — a real, supported configuration, just not
  what the CI job's pinned api-34 emulator uses — would throw granting a
  permission name the platform doesn't recognize, failing `@Before` for
  every test class that calls it. Now returns early below API 33.

**Accepted as-is, already disclosed**:

- `revokeLastAndConfirmGone`'s correctness depends on an unenforced
  invariant (at most one of `shareList`/`linkList` has an entry at a time)
  — already called out in its own doc comment, and every flow in this
  file fully revokes and confirms disappearance before the next one
  starts, so it holds in practice for this suite as written.

**Advisory, not blocking**:

- Login/launch/purge-stale-folders/dialog-button helper logic is
  independently reimplemented (with small drift — e.g. differing poll
  intervals) across `CoreFlowTest.kt`, `VaultFlowTest.kt`, and
  `SharingFlowTest.kt` rather than consolidated in `UiTestHelpers.kt`.
  This isn't hypothetical: `SharingFlowTest`'s own `purgeStaleTestFolders`
  needed a manual, easy-to-forget edit mid-session (adding
  `VaultFlowTest`'s folder prefix) after hitting real cross-test
  pollution. Worth consolidating into shared helpers as a follow-up, not
  blocking this task — `CoreFlowTest` already established the
  per-file-private-method convention this follows.

**On `TASK-00246`'s dependency**: not treated as a blocking finding on
*this* task, matching how `TASK-00241` handled `TASK-00244` (a real,
separately-tracked follow-up bug, filed with its own severity and
acceptance criteria, rather than held over this task's own close). The
test code delivered here is correct and was confirmed against a real
server; `TASK-00246` is a genuine pre-existing app bug this task's own
`VaultFlowTest` surfaced, not a defect in the test itself. `blocks:
[TASK-00243]` added on `TASK-00246`'s own front matter (rather than a
`depends_on` here) keeps that relationship visible in the graph without
implying this task was blocked from starting.

**Status: done.** All three fixable findings landed; the remaining

both tracked, not silently dropped.
