Filed while writing `TASK-00243`'s `VaultFlowTest` — a real, reproducible
bug in the vault upload path, not a test artifact. Confirmed on a fully
wiped, pristine emulator (`emulator -wipe-data`) with a fresh server, so
this is not test-environment cruft accumulated from repeated local runs.

## Reproduction

1. Pick a file to upload into a vault via the standard `ACTION_OPEN_DOCUMENT`
   picker (`FileBrowserActivity`'s `uploadButton` → SAF picker → select a
   file from Downloads).
2. The upload is dispatched through `TransferManager.vaultUploadFile` →
   `VaultTransferer.uploadFile`, which — like every transfer in this app —
   actually runs later, asynchronously, inside a `JobScheduler`-dispatched
   `TransferJobService` (API 34+, User-Initiated Data Transfer) rather than
   synchronously on the calling thread.
3. By the time that job actually runs `context.contentResolver.openInputStream(sourceUri)`,
   it intermittently throws:
   ```
   SecurityException: Permission Denial: reading
   com.android.providers.media.MediaDocumentsProvider uri
   content://com.android.providers.media.documents/document/document%3A... from
   pid=... uid=... requires that you obtain access using ACTION_OPEN_DOCUMENT
   or related APIs
   ```
   crashing the whole app process.

## What's been ruled out / narrowed down

- **Not stale test-environment state.** Reproduced on a freshly wiped
  emulator + freshly wiped server on the very first run.
- **Not (solely) a missing `POST_NOTIFICATIONS` permission.** A User-Initiated
  Data Transfer job's `setNotification()` call needs this permission to
  actually promote the job to a visible notification, and this app never
  requested it at runtime anywhere (fixed alongside this filing —
  `FileBrowserActivity` now requests it on first launch, `TASK-243`). This
  measurably reduces how often the failure reproduces, but does not
  eliminate it — it's a mitigation, not the fix.
- **Not (solely) a missing persistable Uri permission.** Also fixed
  alongside this filing: `FileBrowserActivity`'s `openDocument`/
  `createDocument` callbacks now call `contentResolver.takePersistableUriPermission(...)`
  immediately on receiving the Uri, which is the standard, documented fix
  for "a picked SAF Uri consumed later/elsewhere." A diagnostic log added
  during this investigation confirmed the Uri *was* present in
  `contentResolver.persistedUriPermissions` with read permission at the
  exact moment `openInputStream` was called — and the crash **still
  happened**, sometimes as this `SecurityException`, sometimes as a plain
  `FileNotFoundException`/ENOENT for a different picker resolution. So the
  grant genuinely is being persisted; something else about how
  `MediaDocumentsProvider`-backed documents interact with a persisted grant
  (or with being read from a different point in time than the picker
  hand-off) is the real remaining gap.
- **Provider choice for the exact same Downloads folder appears
  non-deterministic across runs**: the same test, seeding a file into
  Downloads via `MediaStore.Downloads.EXTERNAL_CONTENT_URI` and picking it
  via DocumentsUI's "Downloads" root, resolved through
  `com.android.providers.downloads.documents` (`DownloadStorageProvider`)
  in some runs and `com.android.providers.media.documents`
  (`MediaDocumentsProvider`) in others. The failure was only ever observed
  for the latter.
- **The plain (non-vault) upload path (`FileTransferer`, `TASK-228`) has
  not been observed to hit this**, despite going through the *identical*
  `TransferManager`/`TransferJobService` dispatch mechanism and receiving
  the Uri the identical way. The most likely explanation: `VaultTransferer`'s
  extra setup work before reaching `openInputStream` (unlocking/opening the
  vault, JNI vault handle) takes measurably longer than the plain path,
  giving whatever timing-sensitive interaction exists with
  `MediaDocumentsProvider` more room to lose the grant — but this is an
  inference, not confirmed by direct evidence.

## Suggested real fix (not attempted here — a bigger change than this
investigation's scope)

Stop depending on the picked `content://` Uri remaining valid across an
async/background-job boundary at all: in `FileBrowserActivity`'s
`openDocument` callback, eagerly copy the picked Uri's bytes into the app's
own private storage (`cacheDir`) synchronously, on the calling thread,
*before* dispatching to `TransferManager` — then pass a stable local file
path (or a `FileProvider`-backed Uri over that local file) to the
background job instead of the original SAF Uri. This sidesteps whatever
`MediaDocumentsProvider`-specific persistence gap exists entirely, since
the background job never touches the original picker Uri. Worth doing for
the plain upload path too, defensively, even though it hasn't been observed
failing — the underlying risk (an async job touching a SAF Uri after an
unknown delay) is identical.

## Acceptance criteria

- Vault upload no longer crashes/fails regardless of which document
  provider backs the picked file, verified by actually reproducing a
  `MediaDocumentsProvider`-backed pick (not just re-running until one
  happens not to occur).
- `VaultFlowTest` (`TASK-243`,
  `android/app/src/androidTest/java/com/vaporwault/client/VaultFlowTest.kt`)
  passes reliably across repeated runs, not intermittently.
- Consider applying the same defensive fix to the plain upload path
  (`FileTransferer`) even without a confirmed failure there, given the
  shared risk.

`TASK-00243` that reduce (without eliminating — this task's own root cause

wrapped in try/catch (a provider that rejects a persistable grant outright
would otherwise crash the picker callback synchronously, a regression the
original fix introduced) and the persisted grant is released once the
transfer completes (Android caps an app at 128 persisted grants total;
nothing was releasing them before).

MOB.10, 2026-09-04: Implemented this task's own suggested real fix.
`FileBrowserActivity.uploadFile()` now reads the picked SAF `Uri`'s bytes
into a temp file in `cacheDir` **synchronously, in the picker callback
itself**, while the grant is at its freshest — then passes
`Uri.fromFile(staged)` to `TransferManager` instead of the original
`content://` Uri. The background transfer job (whenever it actually runs)
only ever touches that local `file://` Uri, which needs no SAF grant at
all: `ContentResolver.openInputStream` special-cases the `file` scheme as
a direct filesystem open, so neither `FileTransferer` nor
`VaultTransferer` needed any changes at all — they already call
`openInputStream` on whatever Uri they're given. The staged file is
deleted once the transfer completes (success or failure), via
`awaitAndRefresh`'s existing cleanup hook. The now-unnecessary
`takePersistableUriPermission`/release pair for the **upload** side
(`openDocument`) was removed — nothing needs the original Uri to survive
past this synchronous callback anymore. Left as-is for the **download**
side (`createDocument`): no failure has ever been observed there, and
restructuring it would need the background job to stage to a local file
first and copy to the real destination on completion — a real change,
out of this task's scope (download reliability was never the reported
bug), so `takePersistableUriPermission` stays as the existing mitigation
there.

**Verified, not just reasoned about**: the original `SecurityException`
(`... requires ACTION_OPEN_DOCUMENT or related APIs`) was **never observed
once** after this fix, across roughly a dozen `VaultFlowTest` /
`VaultsScaleTest` runs today, including on a freshly wiped emulator +
freshly wiped server (ruling out any environment-cruft explanation) and
including at least one fully clean end-to-end pass confirmed via the
server log itself (`FILE_MKDIR` → `CHUNK_UPLOAD` → `FILE_COMMIT`, not just

WSL2 test server under this session's sustained, repeated test load, fully
resolved every time by restarting the server process fresh. This is a
local dev-environment characteristic, not a recurrence of this task's own
bug (confirmed: it happens at login/connect time, before any file picker

Also found and fixed while re-verifying against `TASK-00244`'s new
`VaultsScaleTest` (which seeds 10 vault records with no way to delete them

course of verifying it.

## Review

CQR.08, 2026-09-04: Independent code-review pass found two real issues in
the implementation above, both fixed here:

- **Fixed (would have been a real regression)**: the staging copy in
  `FileBrowserActivity.uploadFile()` ran synchronously on the calling
  thread — which, since `uploadFile` is invoked directly from the
  `openDocument` `ActivityResultCallback`, is the **main/UI thread**.
  Every other network/IO operation in this same class
  (`resumeProfile`/`connect`-style flows elsewhere in this app) already
  goes through `kotlin.concurrent.thread { ... }` specifically to avoid
  this; a large picked file would have blocked the UI thread for the
  full copy duration, risking an ANR. Restructured: the `vault`/`target`
  snapshot (which touches `breadcrumbs`, main-thread-only state) is
  captured before spawning the thread, the actual staging copy and
  `TransferManager` dispatch now run inside `thread { ... }`, and
  `awaitAndRefresh` registration hops back via `runOnUiThread` — matching
  this class's own existing threading convention exactly, not inventing a
  new one.
- **Fixed (real, if minor, waste)**: `VaultTransferer.uploadFile` still
  staged its own second copy of the source file even though its sole
  caller (`FileBrowserActivity`) now already stages one — doubling I/O
  and peak cache usage for every vault upload. `VaultTransferer.uploadFile`
  now reads a `file://`-scheme source directly (`sourceUri.path`, no
  copy), keeping the copy-then-delete fallback only for a hypothetical
  non-`file` caller (defensive, not expected from the current one).

**Re-verified after both fixes**, not just re-compiled: rebuilt, wiped the
test server, and confirmed via the server log that a real upload through
the refactored threaded path completes correctly end-to-end
(`FILE_MKDIR` → `CHUNK_QUERY` → `CHUNK_UPLOAD` → `FILE_COMMIT`) — the
threading change does not silently break the transfer. Full multi-step
`VaultFlowTest` runs continued to show the same session-cumulative
flakiness already disclosed above and in `TASK-00243`'s own notes
(vault-list state accumulated across many retries within this one long
session, and intermittent local WSL2/emulator connection drops) — not
specific to, or worsened by, either fix in this review pass.

No further findings. **Status: done.**
