## Acceptance criteria

- Corrupt-then-repair end-to-end test: corrupt a chunk with an intact
  parity group on a real running server, trigger `scrub run` via the admin
  CLI, confirm the chunk is repaired in place (bytes now hash-verify
  again) with no replica involved.
- Corrupt-then-replica-repair end-to-end test: corrupt enough chunks in
  one parity group to exceed local redundancy, with a live paired replica
  available, confirm repair comes from the replica instead (verify via the
  replica's own access log or a similar observable signal, not just "it
  worked").
- Unrepairable case: corrupt beyond both local and replica recovery (e.g.
  no replica configured, group over-corrupted), confirm the
  `chunk_unrepairable` alert (`TASK-00261`) fires and the chunk still
  returns `VW_ERR_CHUNK_CORRUPT` rather than bad bytes or a crash.
- Fuzz target for the Reed-Solomon decode path (`vw_ecc`), following the
  existing `tests/fuzz/` conventions (e.g. `fuzz_proto_recv.c`'s harness
  shape).
- Sign-off note added to `TASK-00253` (the design task) once this closes,
  matching Step 7/8 of `CLAUDE.md`'s Coordination Workflow.

**Real bug found and fixed while writing the replica-repair test — not
by inspection**: `test_replica_repair_when_local_reconstruction_impossible`
initially hung forever (never repaired even after the replica reconnected
and reproved reachable). Root cause, confirmed via temporary debug
logging in `vw_repair.c` (added, exercised, then removed — not left in
product code): `vw_cluster_repair_fetch`'s timeout path marks a slot
`REPAIR_SLOT_CANCELLED` when the caller gives up, on the documented
assumption that "whichever of [the caller or `primary_repl_loop`]
finishes it next frees `result_data` itself and resets the slot to
FREE" (`TASK-00259`'s own comment). That assumption silently breaks when
the connection dies *before* `primary_repl_loop` ever gets back around to
servicing the request at all (exactly what stopping the replica mid-test
does): the dead connection's loop already exited on its own `recv`
failure, so nothing is left to ever visit that slot's cleanup code —
it stays `CANCELLED` forever. Since `vw_cluster_repair_fetch`'s queuing
check treats *any* non-`FREE` slot for a `node_id` as "one already
outstanding" (`VW_ERR_ALREADY_EXISTS`), this permanently blocks every
future repair-fetch to that `node_id`, even across a brand-new
reconnection — a genuine resilience gap in `TASK-00259`'s repair-fetch
pipeline that no existing test happened to exercise (every prior test —
`test_cluster_repair_fetch.c`, `test_repair_pipeline.c` — used a replica
that stayed connected for the test's whole duration; only a genuine
disconnect/reconnect cycle surfaces this).

Fixed in `src/server/vw_cluster.c`'s `handle_cluster_conn`: right after a
fresh connection completes `NODE_HELLO` for a given `node_id` (proof the
previous connection for that `node_id`, and whatever thread was
servicing it, is definitively gone), reclaim any leftover `CANCELLED`
slot for that `node_id` — free `result_data` defensively and reset to
`FREE`. Deliberately scoped to `CANCELLED` only, never `PENDING`: a
`PENDING` slot can still have a live caller polling it on this same
primary process, and resetting it out from under that caller would open
a real second bug (a later, unrelated request reusing the freed slot
index while the original caller is still watching it). `CANCELLED`
specifically means "no live caller remains" per the state machine's own
existing invariant, so reclaiming it here is safe.
