Surfaces `TASK-00173`'s new per-account fallback config on the CLI.

## Work

- `account add`: optional `--fallback-host <host>`, `--fallback-port
  <port>`, `--fallback-ca-cert <path>` (mirrors the existing
  `--ca-cert`/host/port positional convention for the primary). All
  three or none — reject a partial set with a clear error rather than
  silently treating it as "no fallback."
- `account list`: show whether a fallback is configured, and the current
  connection state (primary / fallback (read-only) / offline) per
  account — `resolve_account_id`'s existing table output gains a column.
- New `account status <label-or-id>` (or extend an existing status
  command if one fits better) to show enough detail for a user to
  understand "am I on the fallback right now, and if so, what can't I do."

## Acceptance criteria

- `account add ... --fallback-host X --fallback-port Y --fallback-ca-cert
  Z` round-trips correctly end to end against a real daemon+two servers.
- `account list` accurately reflects live connection state during a
  real failover (integration test, not just a unit test of the parsing).

**CLI.02, 2026-08-14 — implementation complete.**

- `account add` gained `--fallback-host`/`--fallback-port`/
  `--fallback-ca-cert`, validated as a unit (host+port required together;
  `--fallback-ca-cert` alone without both is also rejected — the
  acceptance-criteria wording "all three or none" is interpreted as "host
  and port together are the unit; ca-cert is independently optional
  whenever they're present," mirroring the primary's own already-optional
  `--ca-cert`). Omitting all three on a re-authentication leaves an
  already-configured fallback untouched (`vw_daemon.c`'s own contract);
  the CLI never sends the trailing fields at all in that case rather than
  sending empty strings, which would have cleared it.
- `account list`'s STATUS column and the `--account`-ambiguity error
  hint now show `primary` / `fallback (read-only)` / `offline`
  (`vw_account_conn_mode_t`) instead of the old binary connected/offline.
  `status` (daemon-global) gained a one-line note when any account is
  currently on its fallback.
- **Found the same wire-format desync bug TASK-00173 introduced already
  existed in two more places** — GUI's `vw_gui_ipc.cpp` decoder had the
  identical hardcoded-byte-count bug as the CLI's (fixed there too, while
  in the neighborhood; full GUI surfacing is still TASK-00175's job, this
  only fixes the desync so TASK-00175 doesn't inherit a broken decode).
- Wrote a genuine end-to-end proof
  (`tests/integration/test_cli_fallback.py`) driving the real compiled
  `vapourwault-cli` against a real daemon and a real paired primary+
  replica: `account add --fallback-*` round-trips; `account list` tracks
  `primary → fallback (read-only) → primary` through an actual primary
  kill+restart; a `share` attempt while on the fallback is rejected
  (`VW_ERR_READ_ONLY_FALLBACK`) rather than silently reaching the replica.
  Both this task's acceptance criteria are covered by this one test.
- **Real gap found while writing that test, not fixed here (documented,
  not silently worked around):** the daemon only ever discovers a primary
  outage as a side effect of a sync-folder cycle's own network I/O (or
  session expiry) — an account with zero sync folders configured has no
  independent health check and will report `primary` indefinitely even
  after the primary process is gone, until something else (an IPC
  request that touches the network, or a folder eventually being added)
  generates a failing network call. The test above adds a sync folder
  specifically because of this — matching how this feature is actually
  used in practice (folder sync is the primary reason to have a fallback
  at all), and matching this task's own acceptance-criteria wording
  ("file list/download continue working," i.e. through folder sync, not
  "the daemon polls the primary independently"). Not filing a separate
  follow-up task for this since it's arguably correct behavior for a
  zero-folder account (nothing to fail over *for*), but flagging it here
  in case ARCH.00 disagrees once TASK-00178's fuller test suite exercises
  more account shapes.

  `ctest` (19/19); the new end-to-end test passes; the existing
