Filed while validating `TASK-00242`'s new CI job (an emulator-backed
Android instrumented-test job that needs a real `vapourwaultd` to connect
to) against a real local server. Discovered by accident, then confirmed
deliberately — this is a trivial, remote, single-packet denial of service
against the whole server process, not a maybe.

**Reproduction** (confirmed twice, once by accident via a stray
`Test-NetConnection` probe against the listen port, once deliberately via
a raw TCP connect+immediate-close with no TLS handshake attempted at all —
e.g. `exec 3<>/dev/tcp/127.0.0.1/<port>; exec 3<&-` from bash):

1. Start `vapourwaultd` normally, listening for real client connections.
2. Open a TCP connection to its listen port and close it immediately,
   without sending any TLS ClientHello (or send a malformed one — same
   code path).
3. Server log shows:
   ```
   [vw_net] vw_net_accept FAIL step=2 rc=-29312 (SSL - The connection indicated an EOF)
   [...] INFO  shutting down — draining N worker(s)
   ```
4. The entire `vapourwaultd` process exits. Every other in-flight and
   future connection — including completely unrelated, legitimate
   clients — is dropped. Confirmed via `ss -ltnp`/`ps` immediately after:
   the listen port is no longer bound and the process is gone.

**Root cause**: `src/server/vw_server_main.c`'s main accept loop
(around line 992):

```c
while (g_running) {
    ...
    vw_conn_t *conn = NULL;
    if (vw_net_accept(net_ctx, &conn) != VW_OK) break;
    ...
}
```

`vw_net_accept` (`src/core/vw_net.c`) legitimately returns
`VW_ERR_NET_TLS` for an ordinary, expected, routine failure mode — a
single client's TLS handshake not completing (EOF, malformed
ClientHello, protocol/cipher mismatch, etc.) — and cleanly frees that one
connection's resources before returning (confirmed by reading
`vw_net_accept`'s `fail:` label: it does not corrupt or leak any shared
state). The accept loop, however, treats **any** non-`VW_OK` return —
whether "the listening socket itself is broken" (which should legitimately
stop the loop) or "one individual client's handshake failed" (which
should just be logged, with the loop continuing to accept the next
connection) — identically: `break`, then a full, orderly shutdown of every
worker and the whole process. There is no code path here that
distinguishes a fatal listener-level error from a per-connection,
completely expected/routine failure.

**Impact**: any single client — a misconfigured client, a port
scanner, a load balancer health check that doesn't speak TLS, or a
deliberate attacker — that opens a TCP connection to the server's port
without completing a valid TLS handshake takes the entire server offline
for every user, with a single packet and no authentication. This is as
severe a remote DoS as this codebase can have on its public listener.

**Also worth checking while fixing this** (found while reading the same
function, not confirmed as separately broken): `src/server/vw_cluster.c`
has the identical `if (vw_net_accept(...) != VW_OK) break;` pattern twice
(lines 811 and 828) in what appears to be the cluster-channel accept
loop(s) — same question applies there: does a single bad connection to
the cluster port also bring down cluster replication/the whole process?

## Acceptance criteria

- A single failed/incomplete/malformed TLS handshake against the
  client-facing listener logs the failure and the server continues
  accepting subsequent connections — it does **not** shut down.
- The accept loop only breaks (and shuts the server down) for an actual
  fatal condition on the listening socket itself (e.g. the listen fd
  itself becoming invalid), not for a per-connection handshake failure.
  `vw_net_accept` likely needs to distinguish these two cases in its
  return value/signature, since right now both collapse to the same
  non-`VW_OK` result.
- `vw_cluster.c`'s two accept loops are checked against the same failure
  mode and fixed if they have it too.
- A regression test (extend `tests/integration/`, likely a new
  `test_net_hardening.py` or similar) that opens a raw TCP connection to
  a running test server, closes it without completing a TLS handshake,
  and asserts the server is still alive and still accepts a subsequent
  *real* client connection afterward.
- SEC.07 sign-off given the DoS severity; this task cannot move to `done`
  without it (per `CLAUDE.md`'s routing rule for `security-sensitive`
  tasks).

SRV.01, 2026-09-04: Fixed. Root cause was exactly as diagnosed —
`vw_net_accept` (`src/core/vw_net.c`) already returns a distinct error
code for "the listening socket itself is broken" (`VW_ERR_NET_CONNECT`,
from a failed `mbedtls_net_accept`) versus "this one connection's TLS
setup/handshake didn't complete" (`VW_ERR_NET_TLS`, from the `fail:`
label after `mbedtls_ssl_setup`/`mbedtls_ssl_handshake`) — no signature
change needed there. The bug was purely in three call sites treating any
non-`VW_OK` return as fatal:

- `src/server/vw_server_main.c`'s main accept loop (client-facing
  listener).
- `src/server/vw_cluster.c`'s two `cluster_accept_thread` implementations
  (Windows `CreateThread` variant and the POSIX `pthread` variant — same
  bug, same fix, in both) — the cluster-channel accept loop TASK-00245's
  own filing flagged as "worth checking," confirmed to have the identical
  pattern.

All three now `break` only on `VW_ERR_NET_CONNECT`; any other non-`VW_OK`
(`VW_ERR_NET_TLS`, or an out-of-memory `calloc` failure inside
`vw_net_accept`) logs (via `vw_net_accept`'s own existing diagnostic
`fprintf`) and `continue`s the loop instead.

**Verified, not just reasoned about**:
- Reproduced the original bug on a real running server (raw TCP
  connect-then-close via `/dev/tcp`, and a malformed-ClientHello variant)
  — confirmed the server died both ways before the fix.
- New regression suite `tests/integration/test_net_hardening.py` (3
  tests: bare connect+close, malformed ClientHello, 10 repeated bad

  (`git stash` of just the two source files, rebuild, rerun: all 3 fail

- Ran the full existing `tests/integration/` suite (`-m "not cluster"`)

  fix touches) and a different subsystem (client-side daemon session

## Review

SEC.07, 2026-09-04: Threat-modeled the fix itself, not just the bug it
closes. Does treating `VW_ERR_NET_TLS` (and `VW_ERR_OOM`) as non-fatal
open any new attack surface, versus just closing the old one?

- Each failed-handshake connection still costs the attacker nothing to
  send but costs the server a bounded, small amount of work (one
  `calloc`, one `mbedtls_net_accept`, an aborted `mbedtls_ssl_handshake`,
  then a clean teardown — verified `vw_net_accept`'s `fail:` path frees
  the SSL context, net context, platform mutex/critical-section, and the
  `conn` struct itself; no leak). A connection flood (many rapid bad
  connections) is still possible, same as against any bare TCP listener —
  but that is a pre-existing, generic characteristic this fix doesn't
  change either direction; rate-limiting/firewalling a public listener is
  a different, orthogonal concern, not a regression introduced here.
  Concretely: before this fix, blast radius was "the whole server, every
  legitimate connection, indefinitely, from one packet, no auth." After:
  "one wasted connection slot, momentarily." That is a strict reduction
  in severity, not a new vector.
- The cluster-channel accept loops got the identical fix. Cluster channel
  is already documented (`docs/PROTOCOL.md`) as a distinct, more-trusted
  boundary (`vw-cluster/1` ALPN, never the client-facing listener) — a
  misbehaving or compromised peer hitting it with bad connections
  shouldn't be able to kill a primary or replica either, and now can't.
  Consistent, not a new exposure.
- `VW_ERR_OOM`'s 10ms backoff is fixed and unconditional — no attacker
  input controls its duration, so it isn't a usable timing side-channel
  or amplification vector.

No blocking findings. **Sign-off given.**

CQR.08, 2026-09-04: Verified independently — `vw_net_accept`'s two
possible non-`VW_OK` returns (`VW_ERR_NET_CONNECT` for the listen socket
itself, `VW_ERR_NET_TLS` for a per-connection handshake failure, plus the
`VW_ERR_OOM` case from `vw_net_accept`'s own `calloc`) are handled
identically and correctly across all three call sites (the two
`cluster_accept_thread` variants and the main accept loop), each guarded
by a comment explaining the distinction rather than left implicit. The
`VW_ERR_OOM` busy-loop concern (raised during an independent code-review
pass on this session's full diff) is addressed with a small, clearly
-commented, platform-correct (`Sleep`/`nanosleep`) backoff helper, defined
once per translation unit and reused by both accept-loop variants in
`vw_cluster.c` rather than duplicated. Regression coverage
(`tests/integration/test_net_hardening.py`) is real — confirmed in this
session to fail against the pre-fix code and pass against the fix, not
just written and assumed correct. No blocking findings.
