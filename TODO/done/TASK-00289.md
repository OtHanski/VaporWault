`TASK-00287`'s investigation concluded a real, project-specific Android
release keystore is approved, even with no Play Store presence — free to
generate, meaningfully better than every contributor's shared Gradle
debug key. `docs/RELEASE.md`'s APK section already anticipated this
exact follow-up when `TASK-00239` first shipped the debug-signed
release-variant APK.

## Acceptance criteria

- A dedicated release keystore generated for this project (not reused
  from any contributor's local environment).
- `android/app/build.gradle`'s `release` build type switched from
  `signingConfigs.debug` to a new `signingConfigs.release` sourced from
  the keystore.
- Keystore + credentials (store password, key alias, key password) live
  only in GitHub Actions secrets, wired into `release.yml`'s
  `build-android` job — matching how `SDL2_ZIP_SHA256`/`WIX_ZIP_SHA256`-
  style supply-chain-sensitive material is already handled there, per
  `docs/RELEASE.md`'s own existing note.
- `docs/RELEASE.md`'s APK section updated: this is no longer "signed with
  the same debug key every contributor's local install generates" —
  describe the real signing identity (without exposing anything
  sensitive) and note this still doesn't change sideload-only
  distribution (no Play Store presence).
- Verify a real signed release build installs cleanly via `adb install`/
  direct sideload, not just that the build step succeeds.
- SEC.07 review before `done`, per the `security-sensitive` tag: key
  storage, scoping, and a rotation/backup story (an Android release
  keystore, unlike a GPG key, generally can't be rotated without losing
  update continuity for anyone who'd already installed a build signed
  with it — worth being explicit that this doesn't matter today since
  there's no update mechanism at all yet, but recording the tradeoff).

- **Keystore**: dedicated PKCS12 keystore, alias `vaporwault-release`,
  RSA 4096/SHA256withRSA, generated fresh via `keytool` — not reused from
  any contributor's local environment. 30-year validity (2026-09-14 to
  2056-09-06), chosen because there is no safe rotation path (see below),
  so the cert should outlive any plausible project lifetime rather than
  expire and force an incident later. DN uses the same project-only
  pseudonym decision as `TASK-00288`'s GPG UID (`CN=VaporWault Releases,
  OU=VaporWault, O=VaporWault`, no personal identity), per the project
  owner's explicit choice when asked.
  - Alias: `vaporwault-release`. SHA-256 cert fingerprint:
    `C2:47:CD:F2:05:35:08:B7:A4:A8:EF:D1:3E:E6:BB:7B:51:38:90:57:85:F1:F1:75:07:A8:B3:E8:8B:2A:03:2E`.
  - **Real generation bug hit and fixed**: the first attempt used two
    different randomly-generated passwords for the keystore and the key
    entry (`-storepass:file`/`-keypass:file`). `keytool` accepted this
    silently at generation time with no warning, but the resulting
    keystore was actually broken — Gradle's `packageRelease` task failed
    with `KeytoolException: Failed to read key vaporwault-release ...
    Given final block not properly padded`, since PKCS12 keystores
    require the store and key passwords to match and silently coerce the
    key entry to the store password rather than erroring at generation
    time. Only surfaced once actually trying to *use* the keystore, not
    at creation — regenerated with one shared password for both, then
    re-verified end to end (below) before treating it as correct.
- **`android/app/build.gradle`**: new `signingConfigs.release`, sourced
  entirely from four env vars (`ANDROID_RELEASE_KEYSTORE_PATH`/
  `_KEYSTORE_PASSWORD`/`_KEY_ALIAS`/`_KEY_PASSWORD`) — no keystore path or
  password is ever a literal in this file or git history.
  `buildTypes.release.signingConfig` now picks `signingConfigs.release`
  when those env vars resolve to a real, existing keystore file, falling
  back to `signingConfigs.debug` otherwise (unchanged local-dev
  experience — no contributor has, or needs, a copy of the real
  keystore).
- **`release.yml`** (`build-android` job): decodes a new base64
  `ANDROID_RELEASE_KEYSTORE_BASE64` secret into a `$RUNNER_TEMP` file
  before `assembleRelease`, supplies the three password/alias secrets as
  step-scoped env vars, and removes the decoded file in an `if: always()`
  cleanup step regardless of build outcome.
- **Verified end-to-end, not just "the build succeeds"** (acceptance
  criterion #4, and the whole reason this class of bug above was even
  caught): built a real signed release APK locally with the corrected
  keystore (`ANDROID_RELEASE_KEYSTORE_PATH` etc. set by hand, matching
  what CI will do) — `BUILD SUCCESSFUL`. Ran `apksigner verify
  --print-certs` against the output and confirmed it reports the new
  `CN=VaporWault Releases` certificate (fingerprint matching the keytool

  `am start` on a non-exported activity, which correctly fails with a
  `SecurityException` unrelated to signing) — confirmed
  `LoginActivity` displayed with no crash in `logcat`, then killed the
  emulator.
