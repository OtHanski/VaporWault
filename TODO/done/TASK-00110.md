Discovered while verifying TASK-00106 (Task #18, FILE_LIST dir_file_id wire
extension): the legacy TAP integration harness (`tests/integration/run_integration.py`,
run via `ctest -R '^integration$'`) fails IT-7 ("quota enforcement — upload
rejected when quota exceeded") consistently, including in complete isolation
and against a clean pre-TASK-00106 baseline (commit `7d882f8`). This is a
pre-existing issue, not a regression from TASK-00106's changes — confirmed by
stashing all TASK-00106 working-tree changes, rebuilding, and reproducing the
identical failure.

IT-7 sets the test user's quota to 1024 bytes (already exceeded by prior
test steps), writes a 64 KiB file, triggers a sync, sleeps 3 seconds, then
checks the daemon's `status` output for a nonzero error count. It
consistently reports `0 uploads, 0 downloads, 0 errors` instead of a
recorded upload error — i.e. either the client daemon isn't attempting the
over-quota upload within the 3s window, isn't surfacing the resulting
server-side rejection as a status error count, or the server isn't
rejecting the upload as expected. All other 14 sub-tests in this harness
pass reliably.

## Acceptance criteria

- Root-caused: determine whether this is a timing issue (3s window too
  short), a daemon status-reporting gap (errors not counted for this
  rejection path), or an actual server/client quota-enforcement gap.
- `tests/integration/test_quota.py` (the pytest-based quota suite, which
  currently passes) may need a comparison read to confirm whether it
  exercises the same code path — if it does and passes, that narrows the
  bug to the daemon's `status` error-counting or this harness's timing
  assumption rather than server-side enforcement itself.
- IT-7 passes reliably (run at least 3x back-to-back with no failures).
- No regression in the other 14 IT-* sub-tests in this harness.

QA.06 [2026-08-03]: Root-caused. This is neither a 3s-timing issue nor a
server-side quota-enforcement gap — it's an actual client-side error-
surfacing gap.

Comparison read of `tests/integration/test_quota.py` per the acceptance
criteria: `test_upload_fails_when_quota_exceeded` passes reliably and
exercises the identical path (`vw_client_file_upload` against a user whose
quota is already exceeded), confirming the server correctly rejects the
upload with `VW_ERR_QUOTA_EXCEEDED` (`src/server/vw_store.c:1590`,
returned to the client via `MSG_ERROR` — see
`src/server/vw_file_handlers.c:604`). So server-side enforcement is not
the bug.

Traced the client side from there:

- `recv_expect()` (`src/client/vw_client_core.c:320`) correctly decodes a
  `MSG_ERROR` response and returns it as `(vw_err_t)VW_ERR_QUOTA_EXCEEDED`
  from `vw_client_file_upload`.
- `exec_action()`'s `ACT_UPLOAD` case (`src/client/vw_sync.c:690`) receives
  that error correctly — but `is_net_err()` only matches
  `NET_CONNECT/NET_CLOSED/NET_TIMEOUT/NET_TLS`
  (`src/client/vw_sync.c:492`), so a quota rejection takes neither the
  success branch nor the offline-queue branch. It just falls out of the
  switch and is returned from `exec_action`.
- Every call site of `exec_action()` in `sync_one_folder()`
  (`src/client/vw_sync.c:1088`, `:1094`, `:1100`, for uploads/conflicts,
  downloads, and deletes respectively) discards that return value with
  `(void)exec_action(...)`. `sync_one_folder()` itself always `return
  VW_OK;` at the end (`vw_sync.c:1104`) regardless of any individual
  action's outcome.
- `vw_sync_run()` (`vw_sync.c:1157`) only propagates a folder's error when
  `is_net_err()` matches (`vw_sync.c:1178`); everything else is treated as
  "continue with remaining folders" and the overall return is `VW_OK`.
- `vw_daemon.c`'s main loop only increments `error_count` when
  `vw_sync_run()` itself returns non-`VW_OK` (`vw_daemon.c:1310-1318`).

Net result: `vw_sync_ctx_t` (`vw_sync.c:444`) has no per-action error
counter at all — only `bytes_done`/`bytes_total`. There is structurally no
path from "one file's upload was rejected by the server" to the daemon's
`status` error count, for *any* non-network per-action failure, not just
quota. IT-7 cannot pass as written regardless of the sleep duration — the
3s window is a red herring.

This is a real, if narrow, product gap: a user has no way to learn via
`status` that a specific file failed to sync due to quota (or any other
permanent per-file rejection) — it will just retry identically forever
with no visible error. Filed **TASK-00112** (assignee CLI.02) per CLAUDE.md
§4 (out-of-domain discovery — the fix lives in the sync engine/daemon,
not test harness territory) to add per-action error accounting that
reaches `status`. Marking this task `blocked` on TASK-00112: IT-7 as
specified can only pass once the daemon has something real to report.
Once TASK-00112 lands, this task still needs the 3x-clean-back-to-back
re-run and the "no regression in the other 14 IT-* sub-tests" check from
the acceptance criteria before it can close.
