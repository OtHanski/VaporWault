While implementing `TASK-00087` (client-side login), discovered that
`src/client/vw_ipc.c`'s `vw_ipc_server_accept()` had a Linux-specific
peer-UID check using `getsockopt(fd, SOL_SOCKET, SO_PEERCRED, ...)` on the
daemon's IPC socket — but that socket is AF_INET/TCP (`vw_ipc_server_open`
uses `socket(AF_INET, SOCK_STREAM, 0)`), and `SO_PEERCRED` is an AF_UNIX-only
facility. On at least one real Linux kernel (confirmed via direct
instrumentation, not speculation), `getsockopt` for this option on an
AF_INET socket returns **success** (`rc == 0`) with a garbage/sentinel
`cred.uid` (`0xFFFFFFFF`) instead of failing — so the mismatch check
(`cred.uid != getuid()`) always fired, silently rejecting **every single
connection** to the daemon's IPC channel with `VW_ERR_AUTH_REQUIRED`. This
broke every existing `vapourwault-cli` subcommand (`status`, `sync`, `pause`,
`resume`, `add-folder`, `ls`, etc.), not just login — the entire CLI↔daemon
channel had apparently never been exercised end-to-end before.

`TASK-00087` removed the broken check (loopback binding is now the sole trust
boundary on Linux, matching the already-accepted posture for macOS and the
Windows TODO in the same file) to unblock login and restore basic
functionality. This task tracks doing it properly.

Note this is the **exact same bug class** `vw_admin.c`'s history already
documents being fixed once before ("SEC.07 [2026-07-12]: Switched from
AF_INET to AF_UNIX. SO_PEERCRED only works on AF_UNIX sockets; on AF_INET it
always fails (ENODATA)...") — that fix assumed a clean failure mode
(ENODATA) that doesn't hold on every kernel, as this task's discovery shows.
The admin socket sidestepped the whole problem by switching to AF_UNIX; the
daemon IPC channel can't do the same (it needs to work identically on
Windows, which has no AF_UNIX-equivalent story here), so a Linux-specific
real check is needed instead.

## Acceptance criteria

- Real peer-UID verification on Linux for AF_INET loopback connections:
  parse `/proc/net/tcp` (and `/proc/net/tcp6` if IPv6 loopback is ever
  supported) to find the entry matching the accepted connection's local/peer
  port pair, and read its `uid` field directly (this is a well-established
  technique for exactly this problem — `/proc/net/tcp` exposes the owning
  UID per-connection without needing SO_PEERCRED at all).
- Correctness must be adversarially reviewed: `/proc/net/tcp` parsing needs
  to handle the hex address/port format correctly, TCP_ESTABLISHED state
  filtering, and should be reasoned about for TOCTOU risk (the entry could
  theoretically change between accept() and the /proc read, though for a
  freshly-accepted loopback connection this window is very small).
- Equivalent Windows work (`GetExtendedTcpTable`, already TODO'd in the same
  file) can be picked up in the same task or split out — ARCH.00's call.
- A regression test: attempt a connection from a different UID (or simulate
  one) and confirm it's rejected; confirm same-UID connections still work
  (the existing test gap that let the original bug ship unnoticed).

CLI.02 [2026-07-30]: Implemented real peer-UID verification on Linux in
`src/client/vw_ipc.c`/`vw_ipc.h`.

**Design:** added `vw_ipc_linux_proc_net_tcp_uid()` (non-static, guarded by
`#ifdef __linux__`, deliberately not declared in `vw_ipc.h` — internal to
this file but given external linkage so the unit test can call it
directly). It scans a `/proc/net/tcp`-formatted stream for the
`TCP_ESTABLISHED` (state `01`) entry whose local/remote port pair matches
the accepted connection, and returns the owning uid from that line — this
is the same well-established technique the task called for, avoiding
`SO_PEERCRED` entirely (which doesn't apply to this `AF_INET` channel; see
the file's existing header comment on why an earlier attempt at it broke
every connection).

`vw_ipc_server_accept()` now, on Linux only, after `accept()`: reads its own
local port via `getsockname()`, reads the peer's ephemeral port from the
already-populated `client_addr`, opens `/proc/net/tcp`, and looks up the
owning uid via the function above. Decision logic:
- Match found, uid equals `getuid()` → accept (the common case).
- Match found, uid differs → reject (`VW_ERR_AUTH_REQUIRED`), closing the
  socket. This is the actual new protection.
- No matching `ESTABLISHED` entry found (genuine anomaly, or in principle
  the TOCTOU window between `accept()` and the `/proc` read, though for a
  freshly-accepted loopback connection that window is minute) → reject.
  Cheap to retry for a local daemon, so failing closed here costs nothing
  and is the safer default.
- `/proc/net/tcp` itself unreadable (`fopen` fails — e.g. some restricted
  container profiles) → **fall back to trusting loopback binding alone**,
  i.e. accept. This is the one deliberate fail-open path: regressing to
  "reject everything whenever the check can't run" would repeat the exact
  failure mode this task exists to fix (the original `SO_PEERCRED`-on-
  `AF_INET` bug silently rejected every connection). An environment where
  `/proc/net/tcp` is unreadable is not the attack this task defends
  against (a second real local user with their own UID); it's almost
  always a single-user container/namespace oddity.
- Same reasoning applies if `getsockname()` itself fails — falls back to
  accept rather than reject.

**Windows/macOS:** left as-is (loopback-only trust). Windows' own
`GetExtendedTcpTable`-based equivalent is split out to `TASK-00103` per this
task's own acceptance criteria (explicitly permitted the split). macOS
support is deferred project-wide, so not tracked further here.

SEC.07 [2026-07-30]: **BLOCKING finding on the first draft** — the
`/proc/net/tcp` lookup was called with an un-swapped (local_port, peer_port)
pair, which always matches the daemon's *own* accepted-socket row (owned by
the daemon itself, since `accept()` creates that socket in the daemon's own
process regardless of who connected) rather than the connecting client's
row. Net effect: the check was a tautology that always succeeded with
`uid == getuid()` trivially — a genuine cross-uid attacker would never have
been rejected, and the `docs/DEPLOYMENT.md` claim that Linux hosts were "no
longer subject to" the password-oracle risk was false as originally
written. Root cause: a loopback TCP connection produces *two* `/proc/net/tcp`
rows (one per socket); only the swapped pair (local=peer's port,
remote=our port) lands on the client's own row.

CLI.02 [2026-07-30]: Fixed per SEC.07's finding. `vw_ipc_server_accept()`

- Deleted the stale, factually-wrong `#include <sys/un.h> /* struct ucred */`

  it, not a hardcoded endian-specific hex constant) before accepting a
  match, rather than discarding the address fields entirely — defense in

  drifting out of sync.
