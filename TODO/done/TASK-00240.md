Filed during `TASK-00234` (Android security review) — an advisory,
documentation-only finding, not a code defect. The actual implementation is
correct and consistent everywhere; only the spec text is confusing.

`docs/PROTOCOL.md` §8.1 ("Password transport") currently reads:

> 1. Derives a 32-byte value using Argon2id locally (or, in simple
>    implementations, sends `SHA-256(password)` as the token — see
>    Security Note below).
> ...
> **Security Note (Phase 1 issue TASK-009):** For Phase 0 the wire token is
> `SHA-256(password)` sent from client. Phase 1 will define a proper SRP or
> client-side Argon2id derivation so the raw hash is never transmitted.

Two problems with this text as it stands today (the project is now at
Phase 21):

1. **"Argon2id locally" is presented as a live alternative, but it's
   structurally impossible** given `AUTH_REQUEST`'s shape: it's a single
   round trip, so the client has no way to learn the server's per-account
   Argon2id salt before computing `auth_token`. There is no salt-exchange
   message anywhere in the handshake. Client-side Argon2id was never
   implementable as described, not just "not yet implemented."
2. **The "Phase 1 will define a proper SRP or client-side Argon2id
   derivation" note is stale** — that upgrade never happened, and 20
   phases have since shipped on top of the `SHA-256(password)` scheme
   without anyone revisiting this note, leaving it reading as a near-term
   TODO indefinitely.

Verified against `src/server/vw_auth.c`'s actual verification call
(`vw_crypto_argon2id_verify(real_hash, real_salt, password, pw_len)`,
where `password` is exactly whatever `AUTH_REQUEST.auth_token` carried)
and `src/client/vw_client_core.c`'s own implementation/comment
(`vw_crypto_sha256(password, pw_len, auth_token)`) that the real, sole,
consistently-used scheme is: client sends `SHA-256(password)`; server
verifies it via Argon2id against its own stored hash+salt (i.e., the
server's Argon2id input is `SHA-256(password)`, not the raw password).
This is safe and consistent — every client (desktop, web, Android) does
the same thing — it's just not what §8.1's text plainly says.

## Acceptance criteria

- §8.1 states the actual, sole scheme plainly (client sends
  `SHA-256(password)`; server verifies via Argon2id against
  `SHA-256(password)`), with no "or Argon2id locally" alternative
  presented as live.
- The stale "Phase 1 will define..." forward-looking note is either
  removed or explicitly reframed as a known, deliberately-not-yet-planned
  future hardening (SRP or a real salt-exchange round trip), not phrased
  as an imminent upgrade.
