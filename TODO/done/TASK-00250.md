Found while fixing `TASK-00247` (client MSI per-user install scope). Once the
install-scope bug was actually fixed and real `CustomActionData` templating
was replaced with a self-contained script (both TASK-247 fixes), the
`REGISTERCLIENTTASK` custom action's *real* failure became visible for the
first time (it was always failing — TASK-148's original claim of having
"confirmed via the verbose MSI log" that this worked was only checking the
immediate action's property-table dump, which always looks correct, not
what the deferred action's process actually received or did):

```
Register-ScheduledTask : Access is denied.
At ...\register-client-task.ps1:71 char:1
+ Register-ScheduledTask `
    + FullyQualifiedErrorId : HRESULT 0x80070005,Register-ScheduledTask
```

This is **not** the Group-Policy-blocked-ONLOGON-tasks issue `TASK-148`
originally found on a different, managed test machine — it reproduces on an
unrestricted personal session too, and is a different, more fundamental
limitation: **Windows Task Scheduler's registration API requires the caller
to be running inside the user's actual interactive logon session.** An MSI
deferred custom action's `Impersonate="yes"` token, however correctly
impersonated, is still hosted by the `msiexec` *service* process, which has
no interactive session attached — confirmed directly: the identical script,
run manually and interactively as the same user immediately after the failed
install, succeeds and registers the task correctly (`UserId`/`RunLevel`/
`LogonType` all correct). There is no impersonation flag or CustomAction
authoring trick that fixes this; it's an OS-level session boundary.

## Likely fix

Windows' **Active Setup** mechanism
(`HKLM\SOFTWARE\Microsoft\Active Setup\Installed Components\{GUID}` with a
`StubPath` value) is designed for exactly this situation: Windows itself
re-runs the specified command once per user, the *next* time that user
logs on interactively — the one context where `Register-ScheduledTask`
actually works. The MSI would write the Active Setup registry key (a
per-machine `HKLM` write is fine even for this per-user package, since
Active Setup itself is inherently a per-machine "run once per user"
registration mechanism, not per-user state) instead of trying to run
`register-client-task.ps1` synchronously during its own install transaction.

Alternatives worth considering before committing to Active Setup:
- Have the daemon or CLI register (or verify/re-register) its own scheduled
  task on first real run, since by then it's genuinely executing in the
  user's interactive session. Simplest, no registry/Active-Setup plumbing,
  but means "install" alone never starts anything until the user runs
  something once.
- Document the manual fallback more prominently (the existing
  `Install-VaporWaultClient.ps1` path already works fine for this, since it
  runs interactively) and accept that the MSI's automatic path is
  best-effort/may require a manual step — matches this action's existing
  `Return="ignore"` design intent, just made explicit rather than silent.

This needs a real design decision (which approach, and why) before
implementation — flagging for `ARCH.00`/`SEC.07` rather than picking one
unilaterally, since it changes *when* the daemon starts working after
install, a user-facing behavior change, not just a bug fix.

## Acceptance criteria

- A real, verified mechanism exists for the `VaporWaultDaemon` scheduled
  task to actually get registered after a client MSI install, without
  requiring the user to run anything manually — verified via a real
  install followed by an actual interactive logon (not just structural
  authoring), on an unrestricted (non-managed) Windows session.
- Whatever mechanism is chosen is reviewed by `SEC.07` (an Active-Setup
  `StubPath` is itself a per-machine, all-users-visible registry entry
  that runs arbitrary code at every new user's first logon — real attack
  surface if the invoked script/path isn't locked down correctly).
- `TASK-00152`'s item 5 (scheduled task runs in the correct, non-SYSTEM
  security context) re-verified against whatever the final mechanism is.

CLI.02/BLD.05 [2026-09-07]: Implemented and verified for real.

`src/client/main.c` (`vapourwault-daemon`'s entry point) gained a
Windows-only `ensure_scheduled_task_registered()`, called once at startup
right after the state directory is resolved. It finds its own real
on-disk path via `GetModuleFileNameA`, then runs
`register-client-task.ps1` (installed alongside it in the same directory)
via `CreateProcessA`, with a bounded 5s `WaitForSingleObject` and no
handling of the exit code — best-effort, matching the MSI custom
action's own `Return="ignore"` philosophy; a missing scheduled task must
never prevent the daemon itself from starting.

`register-client-task.ps1` (`packaging/windows/wix/`) is now invoked on
*every* daemon startup, not just once at install, so it needed to become
genuinely idempotent rather than always drop-and-recreate: it now checks
whether a task named `VaporWaultDaemon` already exists **and** still
points at this exact daemon path, skipping all work if so. Deliberately
does *not* just skip on "task exists" alone — an in-place upgrade changes
the daemon's own path (the install directory name includes the version),
so a stale task pointing at a previous version's now-removed binary is
detected (path mismatch) and correctly re-registered rather than left
alone.

**Verified for real, not just structurally**, using a layout matching
the actual per-user install (daemon + script copied side by side into a
fresh directory, no MSI, no scheduled task involved):
- First run: `Get-ScheduledTask` afterward showed `VaporWaultDaemon`
  registered with the correct security context
  (`UserId=OttoOlaviHanski`, `RunLevel=Limited`, `LogonType=Interactive`
  — the exact property `TASK-00152`'s item 5 exists to check) and the
  correct `Execute` path (the test daemon's own real location, confirmed
  by inspection, not assumed).
- Simulated upgrade: copied the daemon to a second, different directory
  and ran it again — the existing task's `Execute` path was updated to
  the new location, confirming the "stale path gets re-registered, not
  left alone" behavior actually works, not just reasoned through.
- All test artifacts (the scheduled task, both temp directories) cleaned
  up afterward.

Moving to `review` for `SEC.07`/`CQR.08` per the `security-sensitive`
tag.

SEC.07 [2026-09-07]: Reviewed `ensure_scheduled_task_registered()` in
`src/client/main.c` and the idempotency change in
`register-client-task.ps1` directly, focused on the new attack surface
this adds (the daemon now shells out to `powershell.exe` on every
startup, not just from a one-time install-time custom action).

- `exe_path` (the only interpolated value in the constructed command
  line) comes from `GetModuleFileNameA(NULL, ...)` — this process's own
  real on-disk path, not user input, not an environment variable, not an
  MSI property. The only way to influence it is to control the
  filesystem location the daemon itself was launched from, which
  requires the same access as replacing `vapourwault-daemon.exe` outright
  — a strictly larger capability than anything this feature could add.
  Windows paths cannot contain `"`, so the literal `\"%s\"` wrapping
  cannot be broken out of.
- `cmdline[MAX_PATH + 128]` sized correctly for the fixed
  `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "..."` template
  plus a full `MAX_PATH`-length path; `snprintf` is used (not `sprintf`),
  so even a pathological input truncates safely rather than overflowing.
- Runs with the daemon's own token throughout (no impersonation, no
  elevation change) — whatever context the daemon itself runs in
  (interactive user, whether launched directly or via its own Scheduled
  Task) is exactly what the child process gets. No privilege escalation
  path.
- **Advisory, not blocking**: `CreateProcessA` is called with a bare
  `"powershell.exe"` in the command line and `lpApplicationName=NULL`,
  meaning Win32's module-search order checks the *calling process's own
  directory first* before `%SystemRoot%\System32`. In principle, a file
  literally named `powershell.exe` planted in the daemon's own per-user
  install directory would run instead of the real one. This install is
  per-user with no elevation, so planting it there requires the same
  user's own write access to their own `%LOCALAPPDATA%` — no privilege
  boundary crossed, consistent with this codebase's already-established
  reasoning for this exact install context (`client-extra.wxs`'s own
  custom actions have used a bare `powershell.exe` the same way since
  `TASK-148`, already reviewed and accepted under the same threat model).
  Not fixing here to avoid inconsistently hardening one call site while
  leaving its siblings as-is; worth a future pass across all of them
  (fully-qualified `%SystemRoot%\System32\WindowsPowerShell\v1.0\
  powershell.exe`) rather than piecemeal.
- The idempotency check's "skip only if path matches exactly" logic
  (`register-client-task.ps1`) is the right call from a security
  standpoint too, not just correctness: it means a stale task can't be
  used to keep running an old, possibly-since-patched binary indefinitely
  after an upgrade — re-registration always follows the currently
  running daemon's own real path.

No blocking findings. Sign-off: `SEC.07` requirement satisfied.

CQR.08 [2026-09-07]: Reviewed the same files for code quality.
`ensure_scheduled_task_registered()` correctly handles
`GetModuleFileNameA` failure/truncation (`n == 0 || n >= sizeof(...)`)
and the defensive-but-realistically-unreachable "no backslash found"
case; both `CloseHandle` calls are present (process and thread handles),
no leak. Style is consistent with the file's existing Windows-specific
code (ANSI `*A` APIs throughout, matching `SHGetFolderPathA`). Well
explained inline for *why* this exists (TASK-250 cross-reference), not
just what it does.

One non-blocking nit: the call site is placed before
`vw_daemon_cfg_load()`, so a daemon invocation that's about to fail on
config load still pays the (bounded, ~instant-when-already-registered)
cost of spawning the check subprocess first. Not worth reordering for —
config load failure is not the common path, and the cost when the task
is already correctly registered is a single fast `Get-ScheduledTask`
call before exiting, not the full register/unregister dance.

`register-client-task.ps1`'s new skip-if-matching check correctly reads
`.Actions | Select-Object -First 1` before comparing `.Execute` — handles
the (currently never true, but not assumed-away) case of a task with no
actions gracefully via the `if ($existingExe -and ...)` guard rather than
erroring on a null comparison.

No blocking findings. Sign-off: `CQR.08` requirement satisfied. Ready
for `done`.
