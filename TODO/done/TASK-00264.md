`TASK-00263` narrowed (but did not eliminate) the race where a parity
group's member gets GC'd out from under it before the group seals — see
that task's "residual risk" note. Discussed with the user afterward: if
that race *does* fire today, there is no failsafe at all.

Traced through what actually happens: `seal_group`'s failure is discarded
(`(void)seal_group(...)` in `register_parity_member`) because
`open_group_id` is already advanced past the failing group before the
seal attempt runs (so concurrent uploads aren't blocked on it). The
startup recovery scan in `vw_storage_open` only ever reconstructs the
*current* (highest) group_id's state — it has no way to notice an older
group left stuck once a newer group_id has superseded it. Net effect: a
group that fails to seal this way is stuck at "16 members recorded, no
parity file" **permanently**, and nothing logs or surfaces this
anywhere — `vw_storage_parity_group_is_sealed()` just silently returns 0
for it forever.

What this does *not* affect (so this is not a data-loss bug, just a
silently-lost reliability feature for one group of chunks): corruption
detection (`vw_storage_scrub_run`, `handle_chunk_download`'s hash
re-verify) doesn't depend on parity groups at all, and neither will
replica-based repair once `TASK-259`/`260` land — only *local*
Reed-Solomon reconstruction for that one group's members is lost.

## Design (from discussion with the user)

1. **Detect**: a "stuck" group is one with exactly
   `VW_ECC_MAX_DATA_SHARDS` members recorded in `parity_groups.db`, is
   *not* the store's current open group, and has no parity file
   (`vw_storage_parity_group_is_sealed()` returns 0). Add a small
   `vw_storage` API to enumerate these (walk `parity_groups.db`'s group
   ids, same O(n) scan tradeoff already accepted for
   `vw_storage_parity_group_members`).
2. **Surface**: wire this into `vw_scrub`'s existing periodic pass (same
   cadence, no second background thread) so a stuck group gets logged —
   same visibility `vw_scrub` already gives corrupt chunks, an operator
   watching server logs should see this too.
3. **Self-heal where possible**: each time `vw_scrub` finds a stuck
   group, retry `seal_group` for it. A transient original cause (e.g. a
   momentary I/O hiccup, a full disk that has since freed up) heals
   silently on the next successful retry. A permanent cause (the member
   file is genuinely gone forever, per the residual race) keeps failing
   — but now it's logged on every scrub pass instead of invisible, so an
   operator has a real signal to investigate rather than silent,
   permanent data-protection loss for that group.

## Acceptance criteria

- New `vw_storage` API to enumerate stuck groups (or a single
  "next stuck group" query — implementer's call once the shape of
  `vw_scrub`'s integration is clearer).
- `vw_scrub`'s periodic pass detects and retries sealing stuck groups,
  logging both the detection and the outcome (healed vs. still stuck).
- Unit test: construct a stuck group deliberately (register
  `VW_ECC_MAX_DATA_SHARDS` members, delete one member's chunk file before
  it would seal, confirm the group is reported "stuck"), then confirm a
  retry succeeds once the missing file is restored (simulating a
  transient-cause recovery) and fails cleanly (logged, not crashing) when
  it's genuinely still missing.
- No change to `vw_storage_gc_run`/`vw_gc.c` — this task is explicitly
  the alternative to gating GC on parity-group state, which the user
  already declined once (`TASK-00263`) as more coupling than the
  problem's size warrants.

## Notes

SRV.01 (2026-09-09): implemented exactly the three-part design already
agreed with the user.

- **Detect**: new `vw_storage_parity_stuck_groups(st, out_group_ids,
  max_count, out_count)` (`vw_storage.h`/`.c`). Tallies member counts per
  `group_id` in one pass over the in-memory parity index (`pg_ht`) using
  a plain array indexed by `group_id` (sequential, starting at 1 — no
  hash map needed for this rare, non-hot-path scan), then reports every
  `group_id` with exactly `VW_ECC_MAX_DATA_SHARDS` members, not the
  store's current open group, and with no parity file on disk. Silently
  caps at `max_count` (documented) rather than growing dynamically — a
  pathological volume of stuck groups isn't a case this project expects
  to actually hit.
- **Self-heal**: new `vw_storage_parity_group_reseal(st, group_id)` —
  idempotent (a no-op returning `VW_OK` if already sealed), otherwise
  re-gathers the group's members via the existing
  `vw_storage_parity_group_members` and calls the same internal
  `seal_group` the live-sealing and startup-crash-recovery paths already
  use. Returns `VW_ERR_INVALID_ARG` if the group doesn't actually have a
  full member set (not really stuck), and whatever `seal_group` itself
  returns otherwise (a permanent cause, e.g. a genuinely-missing member
  file, keeps failing every retry — by design, not a bug).
- **Surface**: wired into `vw_scrub_run_once` (`vw_scrub.c`), right after
  the existing corruption-scan logging — same cadence, no second
  background thread. Every stuck group found is logged, then a reseal is
  attempted and the outcome (healed vs. still stuck, with the
  underlying `rc`) is logged too, so an operator watching server logs
  gets real, actionable visibility instead of the silent, permanent loss
  this task was filed to fix.

**Disclosed, benign race, not fixed**: `vw_storage_parity_stuck_groups`
takes only a read lock and briefly could, in theory, see an OLD group
(just superseded) at exactly `VW_ECC_MAX_DATA_SHARDS` members with no
parity file yet — not actually stuck, just mid-flight on
`register_parity_member`'s own deferred `seal_group` call, which runs
unlocked for exactly this reason (see that function's doc comment).
Concurrently calling `vw_storage_parity_group_reseal` on it in that
narrow window would mean two `seal_group` calls racing to write the same
`{group_id}.parity` file — harmless, since both compute byte-identical
output from the same members and `vw_fs_atomic_write` (temp+rename)
means neither writer can ever leave a partial/corrupt file, only a
redundant duplicate write. Not worth adding coordination for a
millisecond-scale window with no possible bad outcome, matching this
project's existing tolerance for benign races of this shape (e.g.
`TASK-00263`'s own accepted residual risk).

Per this task's own acceptance criteria: **no change to
`vw_storage_gc_run`/`vw_gc.c`** — confirmed by inspection, neither file
was touched.

New unit test case in `tests/unit/test_vw_storage_parity.c`
("stuck group is detected and self-heals once the missing member is
restored", 27 new assertions): reproduces the real scenario directly —
registers `VW_ECC_MAX_DATA_SHARDS - 1` members normally, deletes member
0's on-disk chunk file (simulating a GC sweep, without needing to
actually drive `vw_storage_gc_run` through its own ref-count-to-zero
path — this test only needs the file gone, not a fully faithful GC
replay), then registers the last member — which triggers the automatic
seal attempt, which fails because member 0's file is now missing, and
that failure is silently discarded exactly as `register_parity_member`
already documents. Confirms: the group reports stuck (both via
`is_sealed()`  returning 0 and via `vw_storage_parity_stuck_groups`),
a reseal attempt while the cause persists fails cleanly (not a crash,
no fabricated parity file), then restoring member 0's exact original
bytes and retrying succeeds — the group seals, and
`vw_storage_parity_stuck_groups` no longer reports it. A second
`vw_storage_parity_group_reseal` call against the now-sealed group
confirms the idempotent no-op path too.
