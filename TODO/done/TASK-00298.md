New files `src/client/vw_update.c`/`.h`, plus a new standalone helper
executable target `vapourwault-updater`.

## Orchestration (`vw_update.c`)

```c
vw_err_t vw_update_check_trigger(const char *server_advertised_version /* may be NULL */);
vw_err_t vw_update_download_and_verify_asset(const vw_update_manifest_t *m, const char *staging_dir);
vw_err_t vw_update_stage_and_apply(const char *staging_dir, const char *install_dir);
```

- `vw_update_check_trigger`: compares `server_advertised_version` (if given)
  against the compiled `VW_VERSION_STRING` using a narrow 3-integer
  `major.minor.patch` comparison (no semver pre-release/build-metadata
  handling in v1 — document as a known, accepted limitation). **The
  server-advertised version is only ever a trigger hint, never trusted as
  the thing to install** — if it looks newer, goes on to call
  `vw_update_manifest_fetch_and_verify` (`TASK-00297`), the actual
  cryptographically-verified source of truth. This separation is load-bearing:
  a compromised or stale server can at most cause a spurious *check*, never an
  unverified install.
- `vw_update_download_and_verify_asset`: resolves this platform's entry in
  the verified manifest's `assets`, downloads it via `vw_update_net`
  (`TASK-00296`) streamed to a file in `staging_dir` (not buffered in
  memory), hashes with the existing `vw_crypto_sha256_file`, compares to the
  manifest's signed `sha256`. **Fetches from the manifest's own
  `releases/download/v<release_version>/<filename>` URL, never `latest` a
  second time** — using `latest` again would reopen a TOCTOU race against a
  newer release landing between the manifest fetch and the asset fetch.
- `vw_update_stage_and_apply`: extracts the downloaded archive, then hands
  off to the `vapourwault-updater` helper (below).

## Restart mechanism: `vapourwault-updater` helper

New minimal CMake target, no `vw_core` linkage needed (just file
rename/unlink + wait-for-pid + spawn-process):

```
vapourwault-updater --staging <dir> --target <install_dir> --wait-pid <old_pid> --relaunch <exe>
```

- Waits for `old_pid` to exit (Windows: `WaitForSingleObject` on a duplicated
  handle; Linux: poll `/proc/<pid>` or similar).
- For each shipped file: rename current → `<file>.old`, rename staged-new →
  current, then best-effort-delete the `.old` files (a lingering delete
  failure is left as a disclosed, harmless leftover for the next cycle, not
  a correctness issue).
- Used on **both platforms** for one symmetric, single-tested mechanism, even
  though Linux's rename/unlink-while-running semantics don't strictly require
  a separate helper — deliberate, to avoid two divergent restart code paths.
- Relaunches the daemon after the swap.

## Daemon integration (`vw_daemon.c`)

- Every account-connect/resume call site gains a real (non-`NULL`)
  `vw_proto_update_hint_t` pointer (per `TASK-00295`'s threading) and, on
  `hint.present`, calls `vw_update_check_trigger(hint.server_version)` — this
  fires on ordinary reconnect/resume cycles already happening continuously,
  on **both** the success path and the `VW_ERR_PROTO_VERSION` hard-rejection
  path (a client locked out by a protocol bump still gets a chance to
  self-heal).
- New `daemon.conf` keys: `update_policy = notify|auto` (default `notify`),
  `update_last_seen_sequence = <u64>` (the ratchet from `TASK-00297`).
- Headless/`auto`-policy gap: add a low-frequency (daily) independent
  background timer, active **only when `update_policy = auto`**, that calls
  `vw_update_manifest_fetch_and_verify` directly regardless of any server
  connection — otherwise a fresh install with no configured accounts, or one
  whose configured server is never newer, would never actually be
  "automatic." The `notify`-mode default deliberately stays purely reactive
  to the server hint (no scheduled phone-home a notify-mode user didn't ask
  for).
- The daemon's own role in applying an update is minimal by design: verify →
  stage → spawn the detached `vapourwault-updater` helper (passing its own
  PID) → invoke its **existing** graceful-shutdown path (`vw_daemon.c:161`'s
  SIGTERM handling) → exit. No new "is it safe to restart now" logic is
  invented — whatever resumability properties today's daemon restart already
  has apply unchanged; see `TASK-00291`'s disclosed risk on in-flight
  transfers.

## Acceptance criteria

- End-to-end test (can overlap with `TASK-00303`'s QA pass, but author a
  first version here): a verified manifest + matching staged asset actually
  gets applied and the daemon restarts, still authenticated, syncing intact.
- Asset SHA-256 mismatch aborts before any file is staged into the real
  install directory.
- `vapourwault-updater` never runs with a target directory it didn't get
  explicitly told to use; never operates without a valid `--wait-pid`.
- `update_policy=auto` daily check verified to actually fire on a schedule in
  a test harness (don't just trust the timer code by inspection).
- SEC.07 review: the daemon-restart/file-swap logic is exactly the kind of
  thing that's dangerous to get subtly wrong (partial writes, TOCTOU between
  verify and apply, a helper that can be pointed at an arbitrary directory).

**API signature deviation from the original design sketch**: the sketch's
`vw_update_check_trigger(const char *server_advertised_version)` and
`vw_update_download_and_verify_asset(m, staging_dir)` omitted `state_dir`
(needed for the sequence ratchet, per `TASK-00297`) and out-parameters for
the result — implemented instead as documented in `vw_update.h`, matching
what `vw_update_manifest_fetch_and_verify` (`TASK-00297`) actually requires.

**Real bug found and fixed — release-archive nesting**: `release.yml`
archives a *directory* (`tar czf "$STAGE.tar.gz" "$STAGE"` /
`Compress-Archive -Path $stage`), not that directory's contents. The
original `vw_update_stage_and_apply` extracted straight into `extracted/`
and passed THAT as `vapourwault-updater --staging`, ignoring the one extra
level of nesting every real release archive actually has. Undetected, this
would have made every real self-update either silently install NOTHING on
Windows (`swap_all`'s `FILE_ATTRIBUTE_DIRECTORY` check skips the single
top-level directory entry it would have seen) or corrupt the install on
POSIX (renaming that whole directory into place under the wrong name) — a
"successful" update (exit 0, no error surfaced) that either did nothing or
broke the install. Fixed by resolving the archive's own filename (minus
`.tar.gz`/`.zip`) as the expected nested directory name and passing THAT as
`--staging`; `vw_update_stage_and_apply` now returns `VW_ERR_IO` if that
directory isn't present post-extraction rather than silently proceeding
with the wrong path. Covered by `test_update_apply.c` TC-4 (correct
resolution) and TC-5 (rejects a flat archive missing the wrapper).

**Real bug found and fixed — Windows transient rename failure**: while
building `test_updater_main.c`, `vapourwault-updater`'s Windows
`swap_all()` intermittently failed `MoveFileA` on a file written moments
earlier by the same test process (not by the OS being slow — traced with a
temporary per-attempt `GetLastError()` debug build; the actual, reproduced
root cause turned out to be a test-helper bug, see below — but the
underlying risk of a freshly-written file being transiently locked by
Windows Defender/an indexer on a REAL machine is real and specifically
what installers commonly guard against). Added a bounded
retry-with-backoff (`move_with_retry`, 20 attempts × 50ms) around every
`MoveFileA` call in `swap_all()` as a defensive hardening measure, even
though it turned out not to be the actual cause of the flakiness observed
during test development.

**Test-infrastructure bug found while writing the above (not a production
bug)**: `test_updater_main.c`'s original `make_tmpdir()` used `clock()`
(process CPU time, coarse resolution) for uniqueness; two back-to-back
calls within the same test case could return the identical value, making
`staging_dir` collide with `target_dir` outright and corrupting every
downstream assertion. Root-caused via a temporary debug rebuild logging
every `MoveFileA` attempt's actual `from`/`to` paths and `GetLastError()`,
which showed a `staged -> current` call with byte-identical arguments —
only possible if the two directories were literally the same path. Fixed
with a monotonic per-process counter instead of `clock()`. 10/10 clean
reruns after the fix (was 1-3 failures per 5 runs before).

**Sandbox-specific finding (not a production bug, environment-only)**:
this dev sandbox blocks `CreateProcess` on a freshly-copied `.exe` placed
under `%TEMP%` ("Access is denied") — same restriction noted in earlier
tasks' Notes. `test_update_apply.c`'s TC-4 needs to actually spawn the real
`vapourwault-updater` binary from a fake `install_dir`, so its temp
directories are rooted under the build tree (`VW_TEST_SCRATCH_ROOT`,
`${CMAKE_BINARY_DIR}/test_scratch`) instead of `%TEMP%`, where the sandbox
already permits running this project's own binaries from.

**Build-validation findings unrelated to this task's own new code, found
only because this task's own build validation step (Coordination Workflow
Step 4/BLD.05 convention) is the first time these files were actually
built under WSL `-Werror`**: fixed to unblock this task's own POSIX build,
not otherwise touched —
- `tests/unit/test_vw_update_install_kind.c` (`TASK-00295`): a
  `-Wformat-truncation` error building on gcc/WSL (never seen on MSVC,
  which doesn't run this check) from buffer sizes gcc couldn't statically
  prove were safe at each hop. Fixed with strictly-increasing buffer
  capacities per hop (no behavior change).
- `tests/integration/test_update_manifest.c` (`TASK-00297`): missing
  `<unistd.h>`/`<stdlib.h>` includes on POSIX (`getpid`/`strtoull`/`free`
  implicit-declaration errors under `-Werror`) — MSVC's CRT headers happen
  to pull these in transitively, masking the gap.
- `src/core/vw_net.c` (`TASK-00296`)'s `load_system_ca_chain` called
  `mbedtls_x509_crt_parse_file`, which needs `MBEDTLS_FS_IO` — not defined
  in this project's `mbedtls_config.h` (deliberately: see `vw_smtp.c`'s own
  `smtp_load_pem`, this project's established "read into a buffer with
  plain stdio, use the buffer-based mbedTLS parse function" convention,
  chosen specifically to avoid that flag). Fixed by reusing the existing
  buffer-based `load_pem_file` helper already defined later in the same
  file (forward-declared) instead of the file-path variant — this had
  silently never been build-tested on POSIX before now, since
  `build-msvc-105` is this project's usual iteration loop and MSVC's CRT
  doesn't gate on this the same way.

— all four files/functions predate `TASK-00298` and were simply never

**SEC.07 + CQR.08, 2026-09-16**: Full-milestone review pass across

**BLOCKING #1 (SEC.07), fixed** — `vw_update_detect_install_kind()`
(`TASK-00295`'s deliverable — the "portable archives only" self-install
boundary the whole feature's threat model depends on) had zero callers
anywhere in production code. `vw_daemon_apply_update_now()` — the single
choke point for every apply, both the AUTO-policy path today and any
future manual "Update Now" IPC handler (`TASK-00299`) — downloaded,
staged, and applied against `install_dir` with no check that the running
install was actually a portable archive. A `.deb`/`.rpm`/`.msi` install
with `update_policy = auto` (or, later, a manual "Update Now" click) would
have had `vapourwault-updater` rename every top-level file from a
legitimate, validly-signed portable tarball into wherever the package
manager put the daemon (e.g. `/usr/bin`), silently overwriting
package-owned files — exactly what the plan's own risk disclosure
promised would never happen. Fixed: `vw_daemon_apply_update_now()` now
calls `vw_update_detect_install_kind()` first and refuses with the new
`VW_ERR_UPDATE_NOT_PORTABLE` unless the result is `VW_UPDATE_KIND_PORTABLE`
— before any fetch, download, or staging happens.

**BLOCKING #2 (SEC.07), fixed** — the manifest's `filename`/
`release_version` fields were spliced directly into local filesystem
paths (`vw_update_download_and_verify_asset`'s archive path,
`vw_update_stage_and_apply`'s derived staging-directory name) with no
path-traversal validation. Reachable today only through a validly
ECDSA-signed manifest, but `TASK-00301`'s not-yet-built CI generator is
expected to derive `release_version` from a git tag/`workflow_dispatch`
input — this same repository's `release.yml` already has an explicit
comment acknowledging that kind of value is externally-influenceable.
Fixed at the earliest possible point (parse time, in `vw_update_manifest.c`,
so every consumer benefits automatically): both fields are now rejected
with `VW_ERR_UPDATE_MANIFEST_INVALID` if they contain `/`, `\`, or `..`.

Two advisory findings, both fixed:
- **`parse_semver` used `sscanf("%d.%d.%d", ...)`** on untrusted
  server-hint/manifest version strings — a long digit run makes `%d`'s
  overflow UB per the C standard (same class as `TASK-00296`'s `atol`
  finding). Fixed: replaced with a bounded manual digit parser
  (`parse_uint_component`, 9-digit cap, `uint32_t` accumulator that can
  never itself overflow) and widened `vw_semver_t`'s fields to `uint32_t`
  with a sign-safe three-way comparison in `semver_cmp`.
- **`vapourwault-updater`'s POSIX `swap_all()` had no directory-entry
  skip** matching the Windows branch's explicit
  `FILE_ATTRIBUTE_DIRECTORY` check, and neither branch defended its own
  file-swap against a `/`, `\`, or `..`-containing entry name beyond
  trusting `tar`'s own extraction-time defaults. Fixed: added a shared
  `is_safe_entry_name()` check (both platforms) and an explicit
  `stat()`-based directory skip on the POSIX branch, symmetric with
  Windows.

Two CQR.08-only advisory findings, both fixed:
- **`vw_update_download_and_verify_asset` hardcoded `"github.com", 443`**
  instead of following the `VW_UPDATE_GITHUB_HOST`/`VW_UPDATE_PORT`
  override-macro convention `vw_update_manifest.c` had already
  established, forcing `test_update_apply.c` to write an inconsistent
  "ignore the host, redirect anyway" connect hook. Fixed: added the same
  override macros to `vw_update.c`; `test_update_apply.c` simplified to
  the standard host-override + `VW_CERT_VERIFY_NONE` hook pattern, same
  as `test_update_manifest.c`/`test_update_net.c`.
- **Unused `#include <errno.h>`** in `vw_update.c` — removed.
