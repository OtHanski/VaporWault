Discovered while running TASK-00225's Android runtime smoke test (out-of-domain
find, filed here per `CLAUDE.md`'s routing rule 4 rather than fixed in that
task): the server logged `WARN unhandled msg type 0x0107` when the Android
client sent `AUTH_LOGOUT` on its way out.

Checked the current source, not just the test binary — this is real and
current, not stale-binary noise. `vw_client_logout()`
(`src/client/vw_client_core.c:297`) has always sent `AUTH_LOGOUT` on every
client (CLI, daemon, gateway, and now Android), but `vw_server_core.c`'s
dispatch (~line 972-975) only ever handles `VW_MSG_AUTH_REQUEST` and
`VW_MSG_SESSION_RESUME` — there is no case for `VW_MSG_AUTH_LOGOUT`
anywhere in `src/server/`.

Practical effect: a client-initiated "log out" never actually invalidates
the session token server-side. The token simply sits in the sessions table
until it naturally expires (`expires_at`) — anyone who captured that token
before logout (a shared/compromised device, a proxy log, etc.) can keep
using it for the remainder of its natural lifetime, "log out" notwithstanding.
This is exactly the kind of thing §7.1's other invariants (single-use
resume tokens, no username-existence leak, timing-normalized auth failures)
were designed to avoid leaving open.

## Acceptance criteria

- Server dispatch handles `VW_MSG_AUTH_LOGOUT`: invalidates the session
  (matching whatever `vw_auth.c` already uses for expiry/revocation — reuse
  that mechanism, don't invent a second one) so the token is rejected by any
  subsequent request, including a still-open connection using it.
- No response payload is expected (matches the client's fire-and-forget
  send); confirm this against `docs/PROTOCOL.md` §7.1 and update the spec if
  it doesn't already document the server-side behavior precisely.
- Regression test: log out, then attempt a request with the old
  session_token (on a fresh connection, since the original connection is
  usually already closing) — must fail with `VW_ERR_AUTH_SESSION_EXPIRED`
  (or an equally explicit rejection), not succeed.

## Notes

- MOB.10, 2026-09-02: Filed while verifying TASK-00225's Android
  connect+login smoke test — not investigated further, this is SRV.01's
  domain per the routing rules.
- MOB.10, 2026-09-02: A second, related data point from TASK-00226's own
  runtime verification, worth considering while this is being fixed
  (not filed as a separate task — same root shape, not a separate bug):
  an old server binary that also didn't dispatch `FILE_MKDIR` (msg
  `0x0211`, predates `TASK-00104`) didn't send back any error either — the
  client just blocked forever waiting for an ACK that was never coming,
  with no server-side timeout or explicit rejection at all. A *current*
  build handles `FILE_MKDIR` fine, so this isn't itself a live bug, but
  it suggests the server's dispatch fallback for a genuinely unroutable
  message type is "log a warning and do nothing" project-wide, not
  specific to `AUTH_LOGOUT` — worth checking whether the fix here should
  be "handle `AUTH_LOGOUT` specifically" or "give the dispatch table a
  default case that at least sends `ERROR`/`VW_ERR_NOT_IMPL` instead of
  silently dropping the connection into a permanent hang," which would
  also improve every future protocol version's forward-compatibility
  story (an old client sending a message a newer/differently-configured
  server doesn't handle would otherwise hang the same way, indefinitely).
  ARCH.00/SRV.01's call whether that's in-scope here or its own task.

- SRV.01, 2026-09-03: Fixed. `AUTH_LOGOUT` is now handled directly in the
  per-connection request loop (`src/server/vw_server_main.c`'s
  `handle_connection`), not in `vw_server_dispatch_file_op`
  (`src/server/vw_file_handlers.c`) alongside the other Phase 2 file ops —
  unlike every other message, `AUTH_LOGOUT` carries no payload (the client
  sends it fire-and-forget, no session_token in the message), so there is
  no per-message token to validate the way `vw_server_dispatch_file_op`'s
  handlers all do. Instead it revokes `info.session_token` — the token this
  *connection* authenticated with, captured by `vw_server_conn_handle` at
  the top of `handle_connection` — via a new `vw_server_handle_auth_logout()`
  (declared in `vw_server_core.h`, implemented in `vw_server_core.c`, which
  already has direct access to the opaque `vw_auth_ctx_t`), which calls the
  existing `vw_auth_revoke_session()` (already used by `SESSION_RESUME`'s
  own token-rotation — no new revocation mechanism invented). The connection
  is then closed rather than continuing to serve it, matching the client's
  own immediate-close-after-logout behavior.

  Also addressed the second, related question raised in the note above
  ("does the dispatch fallback need a default case that errors instead of
  hanging"): checked the current source and found `vw_server_dispatch_file_op`
  already got exactly that default case at `TASK-105` (see its comment
  citing "an old client sending a message a newer/differently-configured
  server doesn't handle would otherwise hang the same way" — the same
  forward-compatibility concern raised above) — it already sends
  `ERROR`/`VW_ERR_PROTO_INVALID` for anything unrecognized. The "old server
  binary silently hangs" symptom originally observed was from a stale
  pre-`TASK-105` binary, not current source; no further change was needed
  there. `AUTH_LOGOUT` specifically needed its own fix only because it's
  fire-and-forget with no payload, so it can never flow through that
  same default-case path at all (it's handled one level up, before
  `vw_server_dispatch_file_op` is ever called for it).

  Documented the previously-unspecified behavior in `docs/PROTOCOL.md` §7.1
  (`AUTH_LOGOUT payload` section) — including the accurate (not
  aspirational) wire-visible rejection codes for a revoked token: `AUTH_FAIL`/
  `VW_ERR_AUTH_BAD_CREDS` on a later `SESSION_RESUME` (matching the existing
  anti-oracle invariant — this was cross-checked empirically, not assumed;
  an earlier draft of this doc note and of the regression test both
  initially and incorrectly expected `VW_ERR_AUTH_SESSION_EXPIRED` on the
  wire, which is only ever an internal return value, never sent as-is), and
  `ERROR`/`VW_ERR_AUTH_REQUIRED` for a revoked token used mid-session on a
  still-open connection.

  Verified end-to-end against a real `vapourwaultd` (WSL build,
  `build-wsl-fresh`): added `logout()`, `VW_ERR_AUTH_SESSION_EXPIRED`, and
  two new regression tests to `tests/integration/test_auth.py` —
  `test_logout_invalidates_session` (log out, then confirm a fresh
  `SESSION_RESUME` with the same token now fails) and
  `test_logout_does_not_affect_other_sessions` (logging out one session for
  a user must not invalidate a separate, still-active session for the same
  user — confirms the fix revokes exactly the token this connection used,
  not every session for that `user_id`). Both pass; the full non-cluster
  integration suite (67 pre-existing tests across `test_auth.py`,
  `test_dedup.py`, `test_file_ops.py`, `test_gc.py`, `test_link_password.py`,
  `test_notify_alerts.py`, `test_quota.py`, `test_sharing.py`, `test_vault.py`)
  still passes with no regressions from touching the shared per-connection
  loop in `vw_server_main.c`.
