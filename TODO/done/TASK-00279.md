Once `TASK-00278` lands the client-side `VAULT_DELETE` support, the
desktop GUI's vault view (`src/gui/client/views/vw_view_vault.cpp`) needs
a way to actually trigger it — currently there is no UI path to delete a
vault at all (this is the whole reason `TASK-00269`'s review flagged
"vault records accumulate forever" as the top feature gap).

## Acceptance criteria

- A delete action in the vault list/detail view, gated behind a
  confirmation (this is a destructive, hard-to-reverse-from-the-UI's-
  perspective action even though the server-side operation itself is a
  soft-delete).
- Surfaces `VW_ERR_VAULT_NOT_EMPTY` as an actionable message (e.g. "this
  vault still has files in it — delete them first"), not a raw error
  code — consumes whatever the client layer returns per `TASK-00278`.
- Consumes the client library API only, per this project's GUI/client
  boundary rule (`CLAUDE.md`'s GUI.03 constraint) — no protocol or socket
  code added here.

GUI.03 [2026-09-11]: Implemented.

  `active_account_id_`).

  (available whether locked or unlocked — deletion doesn't need the
  unwrapped VK). Gated behind an explicit confirm/cancel step rendered
  above the table, reusing the exact "pending id, 0 = none" convention
  `vw_view_browser.cpp`'s version-restore confirmation already
  established, rather than inventing a second confirmation pattern.
  `VW_ERR_VAULT_NOT_EMPTY` gets its own actionable message ("this vault
  still has files in it — delete them first"); every other error falls
  back to the shared `vw_gui_format_action_error` helper, matching how
  the web frontend also only special-cased this one status locally
  rather than teaching a shared formatter about it project-wide.
  `vw_view_vault_invalidate()` now also clears the pending-delete/status
  state, so a stale confirmation can't survive an account switch.
- Consumes only the client library surface added in `TASK-00278`/here —
  no protocol or socket code in this file, per the GUI/client boundary
  rule.
