Found during `TASK-00152`'s real install/uninstall/upgrade verification.

`TASK-00147`'s original scope (item 3) called for the server MSI to install
`server.conf` from a template "if absent" — matching every other install path's
"don't overwrite an existing config" rule. It was never actually implemented:
`packaging/windows/wix/server-patch.xml` only adds `ServiceInstall`/
`ServiceControl`/`FirewallException`, nothing config-related, and
`CMakeLists.txt`'s `server.conf.example` install rule is Linux-only (destined
for `share/vapourwault`, consumed by the DEB/RPM postinst scripts — never
installed by the Windows `server`/`client` CPack components at all).

Contrast with `packaging/windows/Install-VaporWault.ps1` (the manual/advanced
path, kept alongside the MSI per `TASK-145`'s design): it explicitly copies
`server.conf.example` to `%ProgramData%\VaporWault\server.conf` if the file
doesn't already exist (or writes a minimal inline template if the example is
missing), and only *then* tells the operator to edit it and start the service.

Practical effect, confirmed for real this session: a server MSI-only install
has no config file and no example ever placed on disk anywhere by the package
itself — the operator must know to find `server.conf.example` in a separate
release artifact (the `.zip`) and copy it themselves before the service can
ever be configured, let alone started. Not a crash (missing config is handled
as a graceful warning-and-defaults by `vapourwaultd` itself), just a real,
silent capability gap between the two documented install paths.

## Acceptance criteria

- Server MSI installs `server.conf` from the example template if
  `%ProgramData%\VaporWault\server.conf` doesn't already exist, and never
  overwrites an operator's existing/edited config on upgrade or repair —
  matching the manual script's exact behavior.
- Verified via a real install (fresh + upgrade-with-edited-config), not just
  structural `.wxs` inspection.

QA.06 [2026-09-07]: **Fixed and verified for real, after two false
starts** (both instructive, kept in `packaging/windows/wix/
server-extra.wxs`'s own header comment rather than only here):

1. First tried `Component/@NeverOverwrite="yes"` on a File installed
   directly to `CommonAppDataFolder\VaporWault\server.conf` — WiX's own
   documented mechanism for exactly this "install only if not already
   present" case. Worked for a fresh install and a same-version reinstall
   in isolation, but a real upgrade test (install 1.0.0, edit config,
   install 1.0.1) **deleted the file** rather than preserving it: the new
   version's action-table computation resolved the shared-GUID component
   to `Action=Null` (sees the file already present via the related old
   product, decides nothing to do) while the old version's nested
   `RemoveExistingProducts` removal independently resolved it to
   `Action=Absent` and deleted it — neither side ends up keeping the
   file. `NeverOverwrite`'s real semantics are for components shared
   between *unrelated* products, not one product's file surviving its
   own version upgrades, and don't compose with CPack's default
   `MajorUpgrade Schedule="afterInstallInitialize"`.
2. Replaced it with a single custom action that copies
   `server.conf.example` (now installed as an ordinary, always-refreshed
   reference file next to `vapourwaultd.exe`) to
   `%ProgramData%\VaporWault\server.conf` only if absent — first
   attempted as an **immediate** action using a `[#FileId]` token
   (immediate actions have full table access, so this seemed like the
   simpler option, and there's no per-user impersonation concern here
   since the server install is fully elevated throughout). This also
   failed, for a different reason: real testing showed the action ran
   *before* `InstallFiles`' own actual file copy happened, even scheduled
   `After="InstallFiles"` — `InstallFiles` is itself a deferred standard
   action, so `After=` only orders sequence-table entries, not when the
   real file-system work executes; the token resolved to a path, but
   nothing existed there yet.
3. **Actually fixed**: made it a *deferred* action (matching `TASK-247`'s
   client-side finding) with `Directory="CM_DP_server.bin"` as its
   working directory and a plain relative source filename
   (`server.conf.example`) instead of any token — a `Directory` attribute
   resolves correctly for deferred actions even though `[Property]`/
   `[#FileId]` tokens inside `ExeCommand` don't.

**End-to-end verified for real** (elevated, this package requires
admin either way): fresh 1.0.0 install creates `server.conf`; editing it
and installing 1.0.1 over it (real `CPACK_WIX_UPGRADE_GUID`-driven
upgrade, single product remains registered) leaves the edit fully intact
(confirmed via a marker line, not just "the file still exists"); service
registration, firewall rule, and binary paths all still correct after
the upgrade; full uninstall removes the service/binaries/firewall rule
while `server.conf` (config/data) survives, matching the existing
"keep data" behavior the rest of `TASK-00152` already established for
this package. All test artifacts (registry, `Program Files`,
`%ProgramData%\VaporWault`, built `.msi` scratch files) cleaned up
afterward.
