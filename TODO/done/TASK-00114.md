Surfaced by a 2026-08-04 project-state review. `src/client/vw_sync.c` — the
client sync engine, and by task-count the single most actively-developed
module recently (TASK-00106/00109/00111/00112/00113 all touched it) — has **zero unit
tests**. Its own test file's header comment (`tests/integration/
test_shared_sync.c`) already acknowledges this explicitly: "there is no
standalone unit test for vw_sync.c at all... coverage for this module has
always come from integration-level exercise, not unit tests."

Integration coverage (`test_shared_sync.c`, `test_shared_sync_hardening.c`,
`test_shared_sync_mkdir.c`, the legacy `run_integration.py` harness) is real
and has caught real bugs this session (see TASK-00111/00113's review notes) —
but every one of those requires a live server round-trip to exercise even a
single branch of `compute_actions()`/`exec_action()`/`srv_collect_by_id()`.
That's slow to run and coarse to localize: a regression is caught later, and
pinpointing which of several possible logic branches broke takes more work
than a focused unit test would.

Tagged `security-sensitive` because this module contains the security-
relevant path-traversal guards flagged with `(§SEC.07)` in the module's own
header (`under_root()` checks before any `vw_fs_delete`/download-path use)
— untested security-relevant logic is itself a gap SEC.07 should weigh in
on, separate from correctness testing generally.

## Acceptance criteria

- A real unit-test harness for `vw_sync.c`'s pure/near-pure logic, following
  this project's existing unit-test conventions (`tests/unit/test_vw_*.c`).
  Since `vw_sync.c` currently assumes a live `vw_client_sess_t`/network
  session throughout, this will likely require introducing a minimal
  seam (a fake/mock session, or extracting the currently-network-coupled
  logic — `compute_actions()`, the BFS helpers, `resolve_or_create_dir()`,
  the action-execution dispatch — into a form callable without a real
  socket). Design that seam with CLI.02 rather than unilaterally
  restructuring `vw_sync.c`'s public shape.
- At minimum, unit-level coverage for: `compute_actions()`'s three-pass
  state-transition logic (local-mod/new-local/remote-mod/local-del/
  remote-del/conflict classification), the `under_root()` path-traversal
  guard (SEC.07's specific interest — prove a server-supplied path that
  escapes `local_root` is rejected without ever reaching `vw_fs_delete`),
  and `resolve_or_create_dir()`'s recursion/memoization logic (already
  covered at integration level by TASK-00113's tests, but the recursion edge
  cases — offline/no-session, malformed vpath, sentinel-value handling —
  are cheaper to prove exhaustively at unit level).
- Existing integration tests (`test_shared_sync*.c`, `run_integration.py`)
  continue to pass unchanged — this is additive coverage, not a
  replacement.
- New unit test(s) wired into `ctest` the same way existing
  `tests/unit/test_vw_*.c` targets are.

QA.06 [2026-08-04]: Implemented.

**Seam chosen**: extended the exact `VW_SYNC_TEST_HOOKS` compile-time gate
TASK-00111 already established in `vw_sync.c` (for the BFS race-injection
hook), rather than inventing a second mechanism. New
`src/client/vw_sync_internal.h` holds the type definitions that used to
live inline in `vw_sync.c` (`action_t`, `action_list_t`, `lfile_t`,
`lfiles_t`, `srv_entry_t`, `srv_list_t`, `dir_entry_t`, `dirmap_t`,
`VW_DIRMAP_UNRESOLVABLE`) plus declarations for the functions the test
needs, gated so they only get external linkage
(`VW_SYNC_TESTABLE` → nothing) when `VW_SYNC_TEST_HOOKS` is defined;
every other build (the daemon, `test_shared_sync`, the two other
integration test binaries) still sees them as `static`, unchanged.
`vw_sync.h` — the actual public API — is untouched. New
`tests/unit/test_vw_sync.c` compiles `vw_sync.c` directly with that define
(mirroring `test_shared_sync_hardening`'s existing CMake pattern for the
same macro, for a different purpose — both coexist without conflict since
no two targets link the same compiled `vw_sync.o`).

**What's covered** (92 assertions): `under_root()`'s path-traversal guard
directly (7 cases: child/exact/sibling-prefix-collision/unrelated/
trailing-slash-on-either-side/backslash), and — more importantly —
`exec_action()`'s `ACT_DEL_LOCAL` branch end-to-end with `sess = NULL`,
proving a rejected path never reaches `vw_fs_delete` (not just that
`under_root()` returns the right boolean in isolation) and that an
accepted path really does delete the file. `compute_actions()` gets one
comprehensive owned-folder scenario exercising all six Pass-3 action
kinds (new/local-mod/remote-mod/local-del/remote-del/conflict) from one
realistic multi-file cache+lfiles+srv fixture in a single call, plus a
shared-folder scenario proving the already-resolved-via-dirmap fast path
never touches `sess`. `resolve_or_create_dir()` gets six scenarios all
chosen so `vw_client_file_mkdir` is never reached (fully offline/root
never seeded, intermediate-ancestor memoization, root-already-known,
target-already-known, sentinel short-circuit, and the root-path-
normalization fallback branch for a `vpath` one level below a `"/"`
root) — each confirms `sess = NULL` is safe and, for the offline/
sentinel cases, that nothing gets spuriously counted via
`vw_sync_action_error_count`/`vw_sync_permission_denied_count`.

**Deliberately NOT covered here** (as scoped in this task's own
acceptance criteria): the actual mkdir-outcome classification inside
`resolve_or_create_dir` (success / `VW_ERR_PERMISSION` /
`VW_ERR_ALREADY_EXISTS` / network error) requires a real
`vw_client_file_mkdir` call against a live server — that's
`tests/integration/test_shared_sync_mkdir.c`'s job (TASK-00113) and stays
there.

**A real bug in my own test, caught and fixed before landing**: the
first draft of the `ACT_DEL_LOCAL` rejection test used a
`"<local_root>/../outside.txt"`-shaped path, expecting `under_root()` to
reject it — it doesn't, because `under_root()` is a pure string-prefix
check with no `..` resolution, so that path still has `local_root` as a
literal prefix and was accepted. That's correct behavior, not a bug: `..`
components are rejected earlier, server-side, by `vw_path_validate`
(defense in depth, not the only line of defense) — `under_root()`'s
actual documented job is catching sibling-directory prefix collisions
(e.g. `/sync2` vs. `/sync`) and unrelated paths. Fixed the test to use a
sibling-prefix path instead, which is the scenario `under_root()` is
actually designed to catch, and added a comment explaining why the
`..` shape doesn't apply here.
