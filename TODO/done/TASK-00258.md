Phase 22's local repair path needs a way to reconstruct a corrupted chunk
without a second full copy (replica/backup). Add a small, hand-rolled
Reed-Solomon erasure coding module — treated like the existing vendored
Argon2/mbedTLS: small, audited, no external dependency — grouping chunks
into fixed-size parity groups at write time.

Tagged `security-sensitive`: new low-level buffer/GF(256) arithmetic code
is exactly the class of C code (`vw_storage.c`'s own doc header's list —
buffer overflow, integer overflow) SEC.07 audits by default.

## Design (from TASK-00253)

- New `parity_groups.db` flat-file (same style as `refcounts.db`): maps
  each written chunk hash → `(group_id, slot_index)`, and `group_id` →
  parity shard location under a new `{data_dir}/chunks/parity/` directory.
- Groups are formed from chunks in **write order** at commit time
  (`vw_storage_chunk_put`), sealed at a fixed size — MVP: 16 data shards +
  1 parity shard (~6.25% overhead, single-fault tolerance per group).
- Parity group header carries a version byte so a later task can move to
  2+ parity shards without a format break.
- Tombstone handling: a group member can legitimately disappear via dedup
  GC (`ref_count` reaching 0). Reconstruction logic must check
  `refcounts.db` before attempting reconstruction — `ref_count == 0` means
  intentional tombstone (skip, don't try to "reconstruct" it), not
  corruption.

## Acceptance criteria

- New `vw_ecc.c`/`.h`: systematic Reed-Solomon encode (given N data shards,
  produce parity shard(s)) and decode (given N-1 data shards + parity,
  reconstruct the missing one), operating on fixed 4 MiB shard buffers (no
  dynamic shard-size negotiation needed — chunks are already fixed-size).
- Parity group formation wired into `vw_storage_chunk_put`'s commit path.
- Unit tests covering: correct reconstruction of exactly one missing shard
  per group, correct rejection/no-op when more shards are missing than the
  group's redundancy can cover, and a fuzz/property test over the GF(256)
  arithmetic itself (buffer bounds, no OOB reads/writes).
- SEC.07 review of the new buffer-handling code before this closes.

## Notes

SRV.01 (2026-09-09): implemented as designed, in two parts.

**`vw_ecc.c`/`.h`** — pure GF(256) primitives (log/exp tables, poly 0x11D,
generator 2 — the standard RS field) plus `vw_ecc_encode`/
`vw_ecc_decode_single` for the single-parity MVP (coefficient row = all
1s, a genuine degenerate systematic RS code, not a disguised XOR — see
the header comment for why). `decode_single` also handles reconstructing
the parity shard itself (`missing_index == k`, just a re-encode) and
rejects any second simultaneous gap with `VW_ERR_INVALID_ARG` — single
redundancy can't cover two faults. `parity_row_coeff()` is a function, not
a fixed-size array literal — an array sized `[VW_ECC_MAX_DATA_SHARDS]`
with a 16-element initializer broke the moment a unit test overrode that
macro to 4 for speed (`error C2078: too many initializers`, caught by
actually building the override, not just reading the code).

**`vw_storage.c`/`.h`** — new `parity_groups.db` (64-byte records, same
guard-slot/scan-on-open convention as `refcounts.db`) plus
`{chunks_dir}/parity/{group_id}.parity` shard files (1-byte format
version + 4 MiB payload; the file's mere existence is the group's
"sealed" flag, no separate header index needed). Group formation hooks
into `chunk_put_impl`'s one "truly new chunk" branch only (not the
dedup-hit or same-request re-put branches) — verified by test that a
dedup'd re-upload never consumes a second slot. Live sealing uses a fast
in-memory per-store accumulator (`open_group_hashes`/`_lens`) to avoid an
O(n) scan on every 16th upload; the general `vw_storage_parity_group_members`
scan (O(chunks ever grouped)) is reserved for the rare paths — startup
crash-recovery and future `TASK-260` lookups — where that cost doesn't
compound. `vw_storage_open` finishes sealing any group a prior crash left
at exactly 16 members with no parity file yet, before returning.

New tests: `test_vw_ecc.c` (2846 assertions — GF(256) field properties
including zero-operand edge cases, encode/decode round trips for every
shard position including the parity shard itself, double-fault rejection,
invalid-arg handling, and a 200-trial randomized property test — this
task's own "fuzz/property test" criterion; a dedicated persistent
libFuzzer-style harness under `tests/fuzz/` is `TASK-00262`'s separate,
broader pass, not duplicated here) and `test_vw_storage_parity.c` (105
assertions against a real on-disk chunk store, compiled with
`VW_ECC_MAX_DATA_SHARDS=4` for speed: group sealing, dedup
slot-non-consumption, member enumeration, parity-shard read, and —
the acceptance criterion that actually matters — reconstructing every
real chunk in a sealed group from its genuine on-disk siblings via
`vw_storage_chunk_get` + `vw_ecc_decode_single`, byte-for-byte). Verified
clean on both MSVC (`build-msvc-105`) and Linux/GCC
`-Wall -Wextra -Wpedantic -Werror` (`build-wsl-werror`) — the pedantic
build caught a real portability bug plain MSVC didn't: passing a non-const
local array where `seal_group` took `const uint8_t (*)[32]` parameters is
pre-C2X-invalid ISO C (fixed by dropping the unneeded `const`, since
neither call site needs the immutability guarantee and both already pass
non-const locals). Full existing `ctest` suite (23/23, including the
whole Python integration collection) passes with no regressions from
hooking this into the chunk-upload hot path.

**Disclosed limitations, not fixed here (in scope for later tasks or
accepted as-is):**
- No test exercises `vw_storage_open`'s crash-mid-seal recovery path
  specifically (a group left at exactly 16 members with no parity file
  from a prior process crash) — `seal_group` and the recovery scan are
  both `static`, and reaching this from a separate test file would mean
  hand-constructing `parity_groups.db`'s binary record layout there,
  fragile to keep in sync with the real struct. Verified by code review
  only; flagged rather than silently uncovered.
- A narrow, *pre-existing* race (not introduced by this task — already
  accepted for GC-vs-upload timing generally, per `vw_gc.c`'s own
  comments) can leave a group permanently unable to seal: if
  `vw_storage_gc_run` deletes a freshly-uploaded, not-yet-`FILE_COMMIT`'d
  member (legitimately `ref_count == 0` in that window, per `TASK-180`)
  before its group seals, `seal_group`'s read of that member's now-gone
  file fails every time, including on every future restart's recovery
  attempt — that one group simply never gets parity coverage. Bounded to
  a single group (16 chunks) and requires GC's default 1800s interval to
  land inside an upload's normally-sub-second upload-to-commit window;
  not fixed here (would need skip-and-reseal-with-fewer-members logic,
  more complexity than this task's scope), disclosed for `TASK-260` or a
  future hardening pass to pick up if it matters in practice.
- Existing chunks uploaded before this feature existed are never
  retroactively grouped — parity coverage only ever applies going
  forward from whenever a store first runs this code.
- No wire/protocol change and no admin visibility into parity-group state
  yet (no `scrub`-status-style report of "N groups sealed, M chunks still
  in an open/uncovered group") — out of this task's scope; could be a
  small follow-up if useful once `TASK-260` makes group state something
  an operator would want to check.

CQR.08 (2026-09-09): reviewed `register_parity_member`'s locking
discipline specifically (write lock held for bookkeeping, released before
`seal_group`'s multi-MB I/O, reacquired before returning to the caller,
which unconditionally unlocks once more) — correct on every path,
including the two "already covered, nothing to do" early-return points.
`seal_group`'s buffer lifecycle (calloc'd per-member buffers, `parity`,
`out_buf`) frees correctly on every early-`break` path via the
unconditional cleanup loop at the end (freeing a still-NULL entry is a
safe no-op). No blocking findings.

SEC.07 (2026-09-09, security-sensitive): audited the new buffer handling
specifically for the class of bug this tag exists to catch. GF(256)
table indexing (`g_gf_exp`/`g_gf_log`) is either a direct `uint8_t` index
(always 0-255, always in-bounds against the 256-entry log table) or a
computed index reduced via `% 255` (always 0-254, always in-bounds
against the 255-entry exp table) — verified no path reaches either table
with an unreduced sum/product. `seal_group`'s per-member `memcpy` into a
`calloc`'d `VW_CHUNK_SIZE_DEFAULT` buffer is preceded by an explicit
`filelen > VW_CHUNK_SIZE_DEFAULT` bounds check that `break`s before the
copy, not after. `vw_storage_parity_shard_read` checks the file's exact
expected size (`1 + VW_CHUNK_SIZE_DEFAULT`) before touching
`bytes[0]`/`bytes+1`, so a truncated or corrupted parity file is rejected
(`VW_ERR_STORE_CORRUPT`) before any read past its real length, not after.
`vw_storage_parity_group_members` bounds-checks a record's `slot_index`
against `VW_ECC_MAX_DATA_SHARDS` before using it to index the caller's
output arrays — defensive against a corrupted on-disk record claiming an
out-of-range slot. No blocking findings. Advisory, not blocking: this
module has no fuzz corpus persisted under `tests/fuzz/` yet (only the
unit-suite's randomized property test) — `TASK-00262` already commits to
that as its own deliverable, so not duplicated or re-flagged as a gap
here beyond this note.

SRV.01 (2026-09-09, follow-up): the GC-race item in this task's own
"disclosed limitations" above was raised with the user and fixed the same

upload now happens at `vw_storage_chunk_addref` (first genuine reference,
i.e. `FILE_COMMIT`), not at `vw_storage_chunk_put` (upload) — closing the
window where an abandoned, never-committed upload could be GC'd out from

registers at write time, correctly — see `TASK-00263` for why). The
other three disclosed items in this task (no direct crash-recovery test,
no retroactive grouping of pre-existing chunks, no admin visibility into
group state) were not raised and remain open/accepted as originally
noted.
