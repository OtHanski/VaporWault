Two advisory (non-blocking) findings from TASK-00106's independent SEC.07/
CQR.08 review, deliberately not fixed as part of that task's closure since
neither is exploitable beyond what a legitimate share owner could already
do directly, but both are worth hardening.

## 1. Revocation-detection is coarser than "revocation," with a narrow
   delete-race false trigger

`sync_one_folder` (`src/client/vw_sync.c`) treats *any*
`VW_ERR_NOT_FOUND`/`VW_ERR_PERMISSION` from `srv_collect_by_id` — at any
BFS level, not just the root — as a revocation signal and permanently
pauses the whole sync folder. `vw_share_resolve_permission` is a pure
"max over all matching active grants" (permission can only be equal-or-
higher moving down an inherited subtree, never selectively restricted),
so there's no way for a *valid* share to have an inaccessible subtree
today — but there is a genuine TOCTOU: a subdirectory is enqueued using
the `file_id` discovered a moment earlier in the *same* BFS pass. If the
owner deletes exactly that subdirectory between discovery and the
subsequent `FILE_LIST_BY_ID` call on it, the resulting `NOT_FOUND` is
indistinguishable from a real revocation and pauses the entire folder for
an ordinary delete, not a grant change.

Fix: only treat a `NOT_FOUND`/`PERMISSION` from the **root** id (stable
across the whole cycle, resolved from the persisted `remote_dir_id`) as a
revocation signal; a same-cycle subdirectory disappearing should be
treated the way `srv_collect` already treats it for owned folders (skip
that branch, not fatal for the whole folder).

## 2. Unbounded client-side resource use walking an owner-shaped tree

`srv_collect_by_id`'s `dirmap_t`/`srv_list_t` (`src/client/vw_sync.c`)
have no cap on total directories or entries across the whole BFS — each
individual `FILE_LIST_BY_ID` call is capped server-side at 65535 entries,
but the number of *calls* (i.e. directories) is unbounded. Shared-folder
sync is the first feature where a client's sync engine walks a tree shape
it did not itself author: a folder owner who shares even at VIEW can grow
an arbitrarily large/deep tree under the shared root and force the
grantee's daemon into unbounded allocation/CPU/bandwidth on every sync
cycle once the grantee adds that share as a sync target.

Fix: a sane ceiling (total dirs/entries, or depth) that auto-pauses (with
a distinct status/reason, not conflated with revocation) rather than
growing without bound — mirroring the 65535-entry philosophy already
applied per-call server-side.

## Acceptance criteria

- Revocation auto-pause only fires on a root-id NOT_FOUND/PERMISSION; a
  same-cycle subdirectory deletion during the BFS no longer pauses the
  whole folder.
- A regression test proving the above: a subdirectory deleted between
  BFS discovery and its own listing call does not pause the folder,
  while an actual revocation still does.
- A configurable (or reasonably-chosen fixed) ceiling on total shared-
  folder BFS size, with a distinct pause reason/status when hit, and a
  regression test exercising it.

CLI.02 [2026-08-03]: Implemented both findings.

**Finding #1 (revocation-detection too coarse).** `srv_collect_by_id()`
(`src/client/vw_sync.c`) now only treats a `VW_ERR_NOT_FOUND`/
`VW_ERR_PERMISSION` from the BFS **root** id (`cur.dir_id == dir_root`) as
a revocation signal. A non-root occurrence (a subdirectory discovered
earlier in the same walk, now gone) does `continue` — skips that branch,
keeps walking the rest of the tree — matching how `srv_collect` already
treats a missing directory for an owned folder.

**Finding #2 (unbounded BFS size).** Added a cumulative cap
(`VW_SHARED_TREE_MAX_ITEMS_DEFAULT = 65535`, mirroring the server's
per-call 65535-entry cap) on total entries observed across the whole walk.
Exceeding it aborts with a new client-local error code
(`VW_ERR_SYNC_TREE_TOO_LARGE`, `src/core/vw_proto.h`) and auto-pauses the
folder with a **distinct** reason. Overridable via `VW_SHARED_TREE_MAX_ITEMS`
for cheap testing, but only in builds that define `VW_SYNC_TEST_HOOKS` —
gated the same way as the BFS test hook below, so no production binary
ever reads this env var at all (SEC.07 finding, see review note below).

**Distinct pause reasons, not conflated:** added `pause_reason` to
`vw_sync_folder_t` (`src/client/vw_cache.h` — repurposes a byte of
existing padding, on-disk size unchanged, still 1040 bytes) with
`VW_PAUSE_REASON_NONE/REVOKED/TREE_TOO_LARGE`, a new
`vw_cache_folder_set_pause_reason()`, and `vw_cache_folder_set_paused()`
(the manual pause/resume path) now always resets the reason to NONE. Wired
through to `vapourwault-cli list-folders` (new REASON column) via a new
byte in the daemon's `FOLDER_LIST_RESP` IPC message
(`src/client/vw_daemon.c`, `vw_ipc.h` updated) — inserted rather than
appended, safe since client and daemon always ship from the same build
(same precedent as the existing `remote_dir_id` field).

**Regression tests:**
- Extended `tests/integration/test_shared_sync.c`'s existing revocation
  check to also assert `pause_reason == VW_PAUSE_REASON_REVOKED`.
- New `tests/integration/test_shared_sync_hardening.c` (+ `.py` wrapper):
  proves finding #1 by deterministically reproducing the actual TOCTOU
  race — rather than racing real threads against real network timing
  (which would itself be flaky, exactly what TODO/TASK-00110.md was about),
  added a compile-time-gated hook (`vw_sync_test_before_list_dir`, only
  under `#ifdef VW_SYNC_TEST_HOOKS`, which is defined for NO production
  target — only this test's own dedicated CMake target) that lets the
  test synchronously delete a real subdirectory via a real
  `vw_client_file_delete_by_id` call at the exact instant the BFS is
  about to list it. Genuine server behavior, zero mocking, zero timing
  dependency. Proves finding #2 with `VW_SHARED_TREE_MAX_ITEMS=5` +
  8 real uploaded files.
- **Verified the test actually catches the bug**: temporarily reverted
  the root-vs-non-root fix, rebuilt, confirmed check #12 ("folder NOT
  paused after a benign subdirectory delete race") fails as expected,
  then restored the fix and re-verified the full suite green.

CQR.08 + SEC.07 [2026-08-03]: Reviewed jointly. No blocking findings. Four
advisory items, all addressed before sign-off:

1. (CQR.08) The race test's `vw_client_file_delete_by_id` result in the
   hook callback was discarded (`(void)...`) — if that delete ever
   silently failed, the "folder NOT paused" assertion would pass
   vacuously (no real NOT_FOUND would ever have been produced, so even
   the pre-fix code wouldn't have paused either). Fixed: capture the
   result in `g_hook_delete_err` and assert `== VW_OK` explicitly.
2. (CQR.08) `shared_tree_max_items()` used `atol()` on an env var —
   undefined behavior on an out-of-range value, not just a bad cast, per
   the C standard. Fixed: `strtoul` with explicit `endptr`/range
   validation.
3. (SEC.07) The `VW_SHARED_TREE_MAX_ITEMS` override was unconditionally
   compiled into every production binary, inconsistent with this same
   diff's own pattern of gating test escape hatches behind
   `VW_SYNC_TEST_HOOKS` — a stray/forgotten env var could silently defeat
   the BFS ceiling for a real user with no signal. Fixed: the `getenv`
   read is now inside `#ifdef VW_SYNC_TEST_HOOKS` too; production binaries
   never read this env var at all.
4. (QA.06, via the same review pass) The tree-size regression test only
   covered a single oversized `FILE_LIST_BY_ID` call (8 files, one
   directory). Added a third scenario (`multi_root/{sub_a,sub_b}`, 3
   files each) proving the ceiling also catches cumulative growth across
   three separate calls (root: 2, +sub_a: 3 → 5, +sub_b: 3 → 8), not just
   a single call's entry count.

Everything else reviewed clean: the root-vs-non-root distinction is
reliable (`srv_collect_by_id` has exactly one call site, only reachable
when `remote_dir_id != 0`, so `dir_root` can never be 0 here); the BFS cap
has no off-by-one and no unbounded-directory-count path independent of
the entry cap; the test hook is compiled into no production target
