Found incidentally while verifying `TASK-00248`'s fix (Windows service
`SERVICE_RUNNING` reporting) on a real Windows Service registered via
`sc create`/`sc start`. Test config left `cluster_port` at its default
(nonzero — 9010), so the server logged
`cluster accept thread started on port 9010` alongside the normal startup
lines. `sc stop` correctly transitioned the service to `STOP_PENDING`
(`vw_server_main_request_stop()`/`SERVICE_CONTROL_STOP` handling in
`vw_winsvc.c` fired as expected), but the underlying `vapourwaultd.exe`
process was still alive and holding an open handle on its oplog file more
than 10 seconds later (confirmed via `tasklist` and a failed `rm` on
`data/oplog/...` reporting "Device or resource busy") — had to be
force-killed (`taskkill /F`) to actually stop. Not yet isolated to
confirm the cluster listener thread specifically is what's not joining
cleanly on shutdown (`vw_cluster_close`/the cluster accept thread in
`vw_cluster.c`) versus something else in the shutdown sequence — this is
a lead from what was actually enabled in the test config, not a confirmed
root cause.

This is unrelated to `TASK-00248`'s own fix (which only touches the
*startup*/`SERVICE_RUNNING`-reporting path) — filed separately since it's
a different part of the lifecycle, but in the same file family
(`vw_server_main.c`/`vw_cluster.c`) and was only discovered because
`TASK-00248` made it possible to actually stop a *running* service for
the first time.

## Acceptance criteria

- `vapourwaultd` (with a cluster listener enabled, i.e. `cluster_port` not
  0) exits promptly after `SIGTERM`/`SERVICE_CONTROL_STOP`/`Ctrl+C` — no
  force-kill needed, verified with a real timed wait, not just "the
  request was sent."
- If the cluster accept thread is the cause, confirm it actually observes
  the shutdown flag (or gets interrupted out of a blocking accept/select
  call) rather than blocking `pthread_join` forever.

QA.06 [2026-09-07]: Filed as a side-finding while verifying `TASK-00248`

investigated further this session — see repro above for what's actually

SRV.01 [2026-09-07]: **Root cause found — this title's own premise was
wrong. Cluster was a red herring, not the cause.** Reproduced with
`cluster_port = 0` (cluster fully disabled) on a fresh test service: the
process still didn't exit after 12+ seconds of `STOP_PENDING`. The real
cause is `vw_net_accept()` (`src/core/vw_net.c`) calling
`mbedtls_net_accept()` with no timeout — a genuinely blocking `accept()`
on the main listen socket. `vw_server_main_run()`'s accept loop only
re-checks `g_running` *after* `vw_net_accept()` returns, so with no
client actively connecting, the thread sits blocked forever regardless
of what set `g_running = 0`. Confirmed directly: a single bare TCP
connect attempt to the listen port immediately unblocked the stuck
shutdown and the process exited cleanly right after — proof the thread
really was parked in `accept()`, not stuck in cluster/GC/admin-server
teardown or anywhere else.

**Fixed**: added `vw_net_ctx_interrupt_listener()` (`vw_net.h`/`.c`) —
closes the listening socket's underlying fd directly
(`shutdown()`+`close()`/`closesocket()`, the standard technique for
interrupting a peer thread blocked in `accept()` on that same socket),
then sets `ctx->listen_net.fd = -1` so the later `mbedtls_net_free()`
(via the existing `vw_net_ctx_close()` shutdown path) safely no-ops for
this listener instead of operating on an already-closed fd number.
`vw_server_main_request_stop()` now calls this (guarded on `g_net_ctx`
being non-NULL, matching how every other global in this file is already
shared between the signal/service-control thread and the main thread —
no new locking introduced, consistent with existing convention) right
alongside setting `g_running = 0`. No new shutdown path was needed: the
interrupted `accept()` call fails with `VW_ERR_NET_CONNECT`, which the
accept loop's existing `if (accept_err == VW_ERR_NET_CONNECT) break;`
already handled correctly — it just never used to actually fire on a
deliberate shutdown.

**Verified for real**, both with `cluster_port = 0` and `cluster_port =
9010` (the original bug report's own config), on a real, temporarily-
registered Windows Service: `sc stop` now completes and the process
exits in ~1.1 seconds in both cases (timed with `date +%s.%N`
immediately before and after `sc stop`, not just "eventually gone") —
down from never exiting at all (12+ seconds, force-kill required) before
the fix. All test services/artifacts cleaned up afterward.

Moving to `review` for `CQR.08` sign-off.

CQR.08 [2026-09-07]: Reviewed `vw_net_ctx_interrupt_listener()` and the
`vw_server_main_request_stop()` change directly.

- Correctly guards against `ctx == NULL` and `fd == -1` (already-closed)
  before touching anything.
- Setting `ctx->listen_net.fd = -1` after closing is exactly what makes
  this safe to compose with the existing `vw_net_ctx_close()` →
  `mbedtls_net_free()` path — verified against `mbedtls_net_free()`'s own
  source (`if (ctx == NULL || ctx->fd == -1) return;`), not assumed.
- Platform split (`shutdown(fd, SD_BOTH); closesocket(fd);` on Windows vs.
  `shutdown(fd, SHUT_RDWR); close(fd);` on POSIX) matches this file's
  existing `#ifdef _WIN32` conventions elsewhere (e.g. the connect-path
  cleanup a few hundred lines up).
- `vw_server_main_request_stop()`'s new `g_net_ctx` read is a plain,
  non-atomic global read from a thread that isn't the main server
  thread — same category of sharing already used for `g_running` and
  `g_reload_cert` in this exact file (neither `volatile`-qualified for
  anything beyond basic single-word read/write atomicity, no locks).
  Not introducing a new class of hazard beyond what this file's existing
  signal/service-control-handler pattern already accepts; a narrow
  double-stop TOCTOU (a second concurrent stop request racing the first
  one's already-in-progress teardown) is the same pre-existing category
  of risk this file has always had for its other globals, not something
  this fix newly introduces, and out of scope for a `priority: normal`
  fix to a shutdown-hang bug.
- Comment on the new function clearly cross-references why the "obvious"
  alternative (adding a new shutdown-flag-check path in the accept loop)
  wasn't needed — reusing the existing `VW_ERR_NET_CONNECT` → `break`
  handling is simpler and already there.
