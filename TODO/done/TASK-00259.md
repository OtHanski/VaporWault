Implement `TASK-00257`'s `CLUSTER_CHUNK_REPAIR_FETCH`/`_DATA` messages:
the replica-side handler (serves a chunk by hash from its own local store)
and the primary-side caller (queries each active replica in turn via
`vw_cluster_node_list` until one returns a hash-verified match).

Tagged `security-sensitive`: a new message accepted on an existing
authenticated cluster channel still needs the same review every other
`CLUSTER_*` handler got (bounds checking, confirming it only ever answers
the already-authenticated peer of that specific `NODE_HELLO` session, not
an unauthenticated or wrong-peer request).

## Acceptance criteria

- Replica-side handler: reads its own chunk via `vw_storage_chunk_get`
  (already hash-verified as of `TASK-00254`'s chokepoint reasoning — reuse
  that same re-verify-before-send pattern here too, don't assume
  `vw_storage_chunk_get`'s raw output is safe to send untrusted) and
  replies with `CLUSTER_CHUNK_REPAIR_DATA`, or `VW_ERR_NOT_FOUND` if it
  doesn't have the chunk either.
- Primary-side caller: given a hash, iterates
  `vw_cluster_node_list`'s active replicas, sends
  `CLUSTER_CHUNK_REPAIR_FETCH` to each in turn (over that replica's
  already-established authenticated session, not a new connection) until
  one returns bytes that hash-verify, or all are exhausted.
- SEC.07 review confirming the replica-side handler cannot be reached by
  anything other than the primary node of an already-completed
  `NODE_HELLO` handshake on that same connection.

## Notes

SRV.01 (2026-09-09): implemented both handlers plus a public
`vw_cluster_repair_fetch(ctx, node_id, hash, timeout_ms, &data, &len)`
API for `TASK-260` to build on.

**Real protocol-design problem solved along the way, not anticipated by
the design task**: the connection between a replica and primary is a
strict alternating request-response stream (replica sends, primary
replies, always in that order) — the primary genuinely cannot just "send"
`CLUSTER_CHUNK_REPAIR_FETCH` at an arbitrary moment; the replica has to
actually be calling `vw_proto_recv` at that exact point or the bytes just
queue unread. Resolved by piggybacking on the replica's own OPLOG_PULL
cycle: right after receiving OPLOG_PULL (before building the OPLOG_DATA
reply it's for), the primary checks a small pending-request table for
this node_id and, if there's an entry, sends `CLUSTER_CHUNK_REPAIR_FETCH`
and waits for `CLUSTER_CHUNK_REPAIR_DATA`/ERROR *before* answering the
original OPLOG_PULL. The replica's own loop was extended symmetrically:
where it strictly expected only `OPLOG_DATA`, it now loops handling zero
or more interleaved `CLUSTER_CHUNK_REPAIR_FETCH` messages first. This
means repair-fetch latency is bounded by the replica's poll interval
(default 5s), which is fine for a background repair path.

**Synchronization**: a primary-side thread (not `primary_repl_loop`
itself) calls `vw_cluster_repair_fetch`, queues into a small fixed
`repair_slots[VW_CLUSTER_REPAIR_SLOTS]` table (one outstanding request
per node_id), and polls for completion in 100ms steps up to `timeout_ms`
— deliberately not a real condition-variable-with-timeout (researched
first: no existing cross-platform timed-wait primitive in this codebase,
and the actual latency floor here is the replica's poll interval, not
this loop's granularity, so the extra complexity wasn't worth it). A
4th slot state (`CANCELLED`, beyond `FREE`/`PENDING`/`DONE`) handles the
caller giving up before `primary_repl_loop` finishes servicing it —
without it, a timed-out caller would leak both the malloc'd result and
the slot itself forever for that `node_id`.

**Found in passing and fixed**: `handle_cluster_chunk_fetch` (the
existing, pre-`TASK-259` replica-pulls-from-primary handler) had the
identical gap `TASK-254` fixed for `handle_chunk_download` — it never
re-verified a chunk's hash before sending it. Fixed alongside the new
repair-fetch handler (same `chunk_bytes_verified` helper, shared by
both) rather than leaving a freshly-noticed instance of an
already-fixed-elsewhere bug class sitting right next to new code that
needed the identical check anyway.

Verified: `test_cluster_repair_fetch.c` (new, 25 assertions) — a real
two-`vw_cluster_t` primary+replica pair over real TLS, real NODE_HELLO

CQR.08 (2026-09-09): reviewed the repair_slots state machine
specifically for the CANCELLED-path cleanup (both `vw_cluster_repair_fetch`'s
timeout branch and `primary_repl_loop`'s servicing-completion branch
correctly free `result_data` exactly once, on whichever side finishes
second) and `vw_cluster_close`'s defensive free of any still-held
`result_data` at shutdown. No blocking findings.

SEC.07 (2026-09-09, security-sensitive): confirmed the replica-side
handler (`handle_cluster_chunk_repair_fetch`) is reachable only via the
existing `vw-cluster/1` ALPN dispatch path, gated by the same
already-completed `NODE_HELLO` authentication as every other `CLUSTER_*`
message on that connection — no new listener, no new credential, no new
unauthenticated code path. The primary re-verifies the replica's returned
bytes itself (`chunk_bytes_verified`) before ever accepting them into a
`DONE` slot, so a misbehaving or compromised replica can return garbage
but can never get the primary to treat it as a repaired chunk without
that hash actually checking out — same trust posture the rest of this
connection already has (a compromised replica can already do much worse,
per §7.9's existing "What the cluster channel does NOT protect against"
disclosure; this doesn't change that boundary). No blocking findings.
