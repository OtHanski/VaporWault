`TASK-00254` closed the read-path gap for chunks a client actively
requests, but nothing walks the chunk store proactively — a corrupted
chunk sits silently until (if ever) a client happens to download it. Add a
background scrub thread that periodically re-hashes every chunk on disk
against its own filename, so corruption is found and logged before a
client ever hits it.

Detection only — this task does not repair anything (Phase 22's repair
pipeline is `TASK-00260`, not implemented yet).

## Acceptance criteria

- New `vw_storage_scrub_run()` in `vw_storage.c`/`.h`: walks all 256 shard
  directories, re-hashes every `*.chunk` file, and distinguishes real
  corruption (`ref_count > 0`) from a legitimate tombstone
  (`ref_count == 0`) via the existing in-memory ref-count table — never
  reports a tombstone as corrupt.
- New `vw_scrub.c`/`.h` module: background thread modeled directly on
  `vw_gc.c`'s existing shape (`interval_secs` config, start/stop,
  synchronous `vw_scrub_run_once()` for on-demand runs), default interval
  6 hours (much slower than GC's 30 minutes, since a full scrub re-reads
  every byte of every chunk on disk).
- `vw_scrub_get_last_stats()` reports the most recent pass's counts
  (scanned/corrupt/tombstoned) and timestamp, for `TASK-00256`'s admin
  status query.
- Registered in `src/server/CMakeLists.txt` (`vw_server_lib`) and the two
  mirrored source lists that also compile `vw_admin.c` directly
  (`tests/unit/CMakeLists.txt`'s `test_vw_file_handlers`,
  `tests/integration/CMakeLists.txt`'s `test_file_list_vault_id`).
- New `tests/unit/test_vw_scrub.c` unit suite.
- Wired into `vw_server_main.c`'s startup/shutdown sequence (create+start
  after GC, before the admin server so its ctx can hand out a reference;
  stop+destroy at shutdown) and `server.conf`'s `scrub_interval_secs` key
  (defaults, INI parsing, `write_defaults`).

## Notes

SRV.01 (2026-09-09): implemented `vw_storage_scrub_run` (walks
`chunks_dir/{00..ff}/`, decodes each `.chunk` filename back to its hash via
`vw_crypto_hex_decode`, re-hashes the file contents, cross-checks the
existing in-memory `ht_find` ref-count lookup) and the `vw_scrub` module
(thread/mutex pattern copied from `vw_gc.c`/`vw_notify.c` rather than
inventing a third convention). Wired into `vw_server_main.c` right before
the admin server block, matching how `cluster` is opened before the admin
ctx assembly for the same reason (the admin ctx needs a live reference).
Added `scrub_interval_secs` to `server.conf` (default 21600s / 6h).

CQR.08 (2026-09-09): reviewed the shard walk against `vw_storage_gc_run`'s
existing Phase B directory-walk comments — consistent (missing shard dir
is normal, not an error, since shards are created lazily on first put).
`vw_storage_scrub_run` reads under a per-file basis with the read lock
held only for the ref-count lookup, not the file read/hash itself — same
contention profile as `vw_storage_gc_run`'s Phase B. No blocking findings.
Unit tests (`test_vw_scrub.c`) cover: clean store, corrupted
still-referenced chunk (detected + callback fires with the right hash),
corrupted `ref_count == 0` chunk (never flagged as corrupt), and the
`vw_scrub` module wrapper wiring `run_once` through to `get_last_stats`.
