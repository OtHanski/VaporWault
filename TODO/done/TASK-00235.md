Automate the manual verification path recorded in the Android design plan:
build via Gradle, run on an emulator/device, point at a local `vapourwaultd`
using the same throwaway-TLS-cert approach
`tests/integration/gen_test_cert.sh` already uses, with `adb reverse` tying
the emulator's loopback to the host-run server.

Scope:
- Instrumented/Espresso UI tests for login → 2FA → browse → upload →
  download → vault create/unlock → share/link, covering the same ground the
  manual pass in TASK-00229/00230/00231 exercised by hand.
- A regression test for every `blocking` finding TASK-00234 resolved.
- Wire into a CI-runnable convenience target analogous to the existing
  `vw_integration_test` CMake target, adapted to drive `adb` instead of a
  local process (coordinate with BLD.05/TASK-00233 on where this lives).

## Acceptance criteria

- Automated tests cover the full login→browse→transfer→vault→share path.
- Every SEC.07 finding from TASK-00234 has a corresponding regression test.

## Notes

QA.06, 2026-09-02: Implemented `android/app/src/androidTest/java/com/vaporwault/client/`
— `TestServerConfig.kt` (host/port/creds, overridable via `-e vw_test_*`
instrumentation args for a CI-provided server), `UiTestHelpers.kt` (UiAutomator
wrappers: `waitFor`/`click`/`clickText(Contains)`/`clickDesc`/`clearAndType`/
`shell`/`waitUntilTextAppears`), and `CoreFlowTest.kt`'s
`loginBrowseUploadDownloadDelete`: login → purge stale state → create folder →
open it → upload (via the real SAF Downloads picker) → download and verify the
file's actual on-device bytes exist → delete file → delete folder, all against
a real `vapourwaultd`. Chose UiAutomator over Espresso because the SAF picker
lives in a separate system process (`DocumentsUI`) that Espresso's in-process
view matchers cannot reach at all.

Verified: `adb shell am instrument -w -e class
com.vaporwault.client.CoreFlowTest
com.vaporwault.client.test/androidx.test.runner.AndroidJUnitRunner` →
`OK (1 test)`, 34.7s, on an x86_64 emulator against a real WSL-hosted
`vapourwaultd`. Cross-checked the server's own debug log for every step
(`FILE_MKDIR`/`CHUNK_UPLOAD`/`FILE_COMMIT`/`CHUNK_DOWNLOAD`/`FILE_DELETE`, all
`rc=0`), not just the test runner's own pass/fail — this caught several bugs
in the test itself that a green/red result alone wouldn't have (below).

Getting one clean pass took real iteration; every fix was confirmed against
server-log evidence before being treated as correct, not guessed at:
1. `am force-stop` in `@Before` killed the test's own process (instrumented
   tests run inside the target app's process) — removed.
2. Seeding a file into `/sdcard/Download` via a shell `echo >` failed under
   scoped storage even from the shell UID — switched to a real `MediaStore`
   insert through `ContentResolver`, matching what the SAF picker itself is
   backed by.
3. A `UiObject2.text = value` set that leaves the IME open made the *next*
   `wait*` call for an unrelated, genuinely-present view time out with no
   exception — `clearAndType` now dismisses the IME (`pressBack()`) after
   every field it sets, but only when the field was `.click()`ed first (a
   field set without prior click never got real focus/an IME, and
   `pressBack()` there dismisses the enclosing dialog instead — the
   new-folder dialog's `EditText` deliberately skips the extra back-press for
   this reason).
4. The new-folder dialog's positive button and the screen's own
   `newFolderButton` underneath it both auto-uppercase to identical text
   ("NEW FOLDER"), and a shown `AlertDialog` does not remove the covered
   Activity from the accessibility tree — a text match hit the wrong
   (covered, no-op) button. Confirmed via zero `FILE_MKDIR` in the server log
   despite an apparently-successful click; fixed via the framework's stable
   `android:id/button1` resource id instead of text matching.
5. Transient status text ("Download complete") is overwritten by the
   subsequent folder-reload before a text-wait can reliably catch it even
   though the transfer genuinely succeeded (confirmed via server log) —
   replaced with polling for the downloaded file's real on-device existence.
6. Accumulated leftover folders from earlier failed runs (a) made the
   real-user-facing `LoginActivity` bug filed as `TASK-00241` (6+ saved
   profiles hide `connectButton` entirely) start breaking this test's own
   reruns, and (b) pushed a newly-created folder off the `RecyclerView`'s
   rendered window, where — unlike a `ScrollView`, which keeps everything in
   the accessibility tree — a genuinely off-screen `RecyclerView` item is
   never inflated/bound and so can never be found by a text search. Fixed via
   `purgeStaleTestFolders()` (called right after login) and an `@After` that
   removes every saved profile matching the test account.
7. `FileBrowserActivity` has no custom back-press handling for its breadcrumb
   navigation, so `pressBack()` intended to go "up" one level instead exits
   the whole Activity (confirmed: `entryMenuButton` unfindable afterward
   because the app was simply gone). Fixed by tapping the "Home" breadcrumb
   instead — which itself needed `clickTextContains` rather than an
   exact-text `clickText`, since `BreadcrumbAdapter` renders every non-last
   breadcrumb level with a trailing "›" glyph ("Home ›"), not plain "Home".

Regression coverage for TASK-00234's findings: the one `blocking` finding
(TLS certificate verification was structurally absent — no way to trust a
self-signed/private-CA server cert, so every connection either failed closed
or, if the SDK-default trust store happened to accept it, provided no real
pinning) is exercised only indirectly here — this suite's `vapourwaultd`
already uses a CA the emulator has imported, so a real TLS handshake with
verification enabled completing successfully for the whole flow is a
positive-case regression check on the connect path TASK-00234 touched, but
**not** a negative case (deliberately connecting with an untrusted cert and
asserting the connection is refused). TASK-00234's own Notes already flagged
this gap explicitly rather than asserting full coverage; it remains open,
tracked here rather than silently dropped, as good follow-on scope for
whoever next touches this suite.

Not implemented — disclosed rather than silently dropped: the "CI-runnable
convenience target" part of this task's scope (wiring these instrumented
tests into an actual CI job, coordinating with `TASK-00233` on where an
emulator-in-CI setup would live) was not done this pass. `TASK-00233`'s CI job
builds `assembleDebug`/validates compilation only; it does not boot an

time, KVM/HAXM availability, a real `vapourwaultd` instance reachable from the
runner) than this task's remaining time budget covered — filed as
`TASK-00242` for BLD.05 rather than left undocumented.
