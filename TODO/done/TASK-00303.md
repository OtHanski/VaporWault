Regression suite covering the full feature, per `TASK-00291`'s design.

## Required coverage

- Old-client ↔ new-server: both the soft `HELLO_OK` case (protocol-compatible,
  update available) and the hard `VERSION_REJECT` case (protocol bumped) —
  confirm the version hint actually surfaces in both.
- New-client ↔ old-server: no hint surfaced, no spurious update prompt.
- Tampered or unsigned `update-manifest.json` rejected (bit-flipped bytes,
  missing `.sig`, signature from a different key).
- Sequence-rollback replay rejected: a validly-signed old manifest replayed
  after a newer one was seen must be rejected.
- Real end-to-end self-update on both Linux and Windows portable installs:
  download → verify → stage → restart → sync resumes correctly.
- Headless (`update_policy=auto`, no GUI attached) full flow, including the
  daily background-check timer actually firing.
- Non-portable install (simulate a `.deb`/`.rpm`/`.msi`-shaped layout, no
  `.vw-portable` marker) confirmed to show notify-only UI and never write to
  the install directory.
- Every published release asset (`TASK-00304`) has a valid GPG signature that
  verifies against the committed public key.

## Acceptance criteria

- All of the above pass, or a disclosed, well-reasoned gap is recorded (not
  silently skipped) — matching this project's existing QA convention.
- Sign-off note added to this task before ARCH.00 closes the milestone.

## Notes

**QA.06, 2026-09-16 — regression suite audit + gap-fill**: Mapped every
required-coverage item to the existing test suite, filled two real gaps
directly (manifest `.sig`/wrong-key coverage, CI GPG-verify-after-sign),
and disclosed the two items that cannot be exercised as a truly live,
real-subprocess-and-network flow in this environment, with the reason
each is a hard platform/architecture constraint rather than an oversight.

1. **Old-client ↔ new-server (soft `HELLO_OK`) / hard `VERSION_REJECT`,
   hint surfaces in both**: `tests/integration/test_proto_update_hint.c`
   TC-1/TC-3/TC-4 — a real server's `HELLO_OK` carries the hint to a real
   client (TC-1), and a hand-crafted `VERSION_REJECT`-with-hint decodes
   correctly through the real client's `negotiate()` (TC-4). Hand-crafted
   old-peer wire shapes (TC-3) rather than a maintained separate historical
   binary — this project doesn't keep old release binaries around for
   protocol testing, and a byte-exact hand-crafted message is a stronger,
   more precise test of the parser than an incidental old build would be.
2. **New-client ↔ old-server: no hint surfaced, no spurious prompt**:
   same file, TC-2 — a real `HELLO_OK` with no `server_version` to
   advertise (the shape an old server, or one with nothing to advertise,
   produces) leaves the hint absent, not a decode error or a
   false-positive prompt.
3. **Tampered/unsigned manifest rejected**: `test_update_manifest.c`
   TC-2 (bit-flipped body), TC-6 (genuinely-signed but by a different
   key — **new**, filled today, see that file's own notes), TC-7
   (missing `.sig`, a 404 — **new**, filled today). All three are
   distinct rejection paths, not one case standing in for all three.
4. **Sequence-rollback replay rejected**: `test_update_manifest.c` TC-3
   (a validly-signed lower-sequence manifest, replayed after a higher one
   was already seen, rejected with the ratchet unmoved).
5. **Real end-to-end self-update on both Linux and Windows portable
   installs**: covered in pieces with REAL components at every stage —
   `test_update_apply.c` (real download+SHA-256-verify+extract+stage,
   against a local test server), `test_updater_main.c` (the real built
   `vapourwault-updater` binary performing the actual backup/replace/
   relaunch swap) — both verified locally against real Linux (WSL/gcc)
   and Windows (MSVC) builds this session. **Disclosed gap**: chaining
   ALL stages into one continuous run — a real `vapourwault-daemon`
   subprocess fetching from a live (test) server, applying, restarting,
   and resuming sync — is not achievable as an automated test: the
   shipped daemon binary only ever connects update-check traffic via
   `VW_CERT_VERIFY_SYSTEM_STORE` (real OS trust store; TASK-00296's own
   documented design), with no test-hook compiled into a production-
   shaped binary to redirect it at a local server (the hook exists only
   in dedicated test targets that compile the source directly with
   `VW_UPDATE_NET_TEST_HOOKS`, which a real `vapourwault-daemon` subprocess
   never is). Matches `test_ipc_update.c`'s own already-recorded reason
   for the same boundary. Every individual mechanism this full chain
   depends on is independently verified with real code; only the single
   unbroken live run is out of reach here.
6. **Headless (`update_policy=auto`, no GUI) full flow, including the
   daily background-check timer firing**: `test_ipc_update.c` TC-4
   (policy set to `auto` and persisted on a real headless daemon) +
   `tests/unit/test_vw_update_daily_check_due.c` (exhaustive coverage of
   the due-calculation logic itself: never-checked, below/at/past
   interval, backward-clock, zero-interval). **Disclosed gap**: the
   24-hour real interval (`VW_UPDATE_AUTO_CHECK_INTERVAL_SECS`,
   `vw_daemon.c`) is not currently override-able via
   `target_compile_definitions` the way this pipeline's other constants
   are, and firing it live hits the exact same real-network/no-test-hook
   constraint as item 5 above — so "the timer's due-logic is correct"
   and "a live daemon actually calls it every loop tick" are both
   verified, but "waiting out or accelerating a real 24h interval against
   a live network fetch" is not exercised end-to-end.
7. **Non-portable install → notify-only, never writes to install dir**:
   `tests/unit/test_vw_update_install_kind.c` (detection logic: fails
   safe to `PACKAGE_OR_UNKNOWN` whenever the `.vw-portable` marker is
   absent or unconfirmable) + `vw_daemon_apply_update_now`'s own
   independent re-check of this same detection immediately before ever
   invoking the updater (confirmed by reading, TASK-00302's audit).
8. **Every published release asset has a valid GPG signature verifying
   against the committed public key**: previously a MANUAL step only
   (`docs/RELEASE.md`'s own `gpg --verify` instructions for a human to
   run) — nothing re-checked it automatically. **Filled today**: added a
   "Verify GPG signatures against the committed public key" step to
   `release.yml`, running immediately after signing and gating the
   "Create or update GitHub Release" step — on every real release AND
   every `workflow_dispatch` dry run. Uses an isolated `--homedir`
   containing only the committed `packaging/signing/vaporwault-releases-pubkey.asc`
   (never the signing key's own keyring), so it specifically proves
   "verifies against the committed public key," not merely "verifies
   against something in the keyring." Sanity-checked the underlying
   gpg sign/isolated-verify/tamper-detect pattern locally (WSL) before
   adding it to CI: a genuine signature verifies, a tampered file
   correctly fails.
