Phase 22's replica-based repair needs a primary to pull a specific chunk's
bytes from a replica — the reverse of today's `CLUSTER_CHUNK_FETCH`
(`docs/PROTOCOL.md` §7.8), which only lets a replica pull from the primary
(`vw_cluster.c`'s `handle_cluster_chunk_fetch` runs only on the primary
side, dispatched from `primary_repl_loop`). Publish the spec for the new
reverse-direction messages before `TASK-00259` implements the handlers.

## Design (from TASK-00253)

| Opcode | Name | Direction | Purpose |
|--------|------|-----------|---------|
| 0x0710 | `CLUSTER_CHUNK_REPAIR_FETCH` | Primary → Replica | Request one chunk's bytes for repair |
| 0x0711 | `CLUSTER_CHUNK_REPAIR_DATA`  | Replica → Primary | Chunk bytes (same shape as `CLUSTER_CHUNK_DATA`) |

Rides the *existing* authenticated `NODE_HELLO` cluster session — no new
credential. The replica must only serve this to the primary node it
already authenticated via that session (same trust boundary as every
other `CLUSTER_*` message), not to an arbitrary caller.

## Acceptance criteria

- New `docs/PROTOCOL.md` §7.8-adjacent subsection documenting both
  messages' payload shapes, direction, and the trust model (rides the
  existing authenticated session; replica-side handler in `TASK-00259`
  must reject a repair-fetch from anything but the already-authenticated
  primary connection).
- New revision row in §11's Version History table.
- Error behavior when the replica doesn't have the requested chunk either
  (mirrors `CLUSTER_CHUNK_FETCH`'s existing `VW_ERR_NOT_FOUND` behavior).

can't be reached this way until its next reconnect, which `TASK-260`'s
pipeline needs to treat as just another failure-to-obtain-a-clean-copy,
