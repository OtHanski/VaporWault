`docs/DEPLOYMENT.md`'s existing §6 "Cluster setup" only covers pairing a
replica for oplog backup purposes — it needs updating now that a replica
is a genuine hot standby (`TASK-00172`), plus new material for actually
configuring automatic fallback (`TASK-00173`/`00176`).

## Work

- Update §6 to describe what a replica now actually holds (live,
  independently-queryable data — not just an oplog backup) and the new
  `CLUSTER_RECORD_*`/`CLUSTER_CHUNK_*` traffic in general terms (no need
  to duplicate `docs/PROTOCOL.md`'s wire-level detail).
- New subsection: configuring automatic fallback for the client daemon
  (`--fallback-*`/`account add`'s new flags, `TASK-00174`) and the gateway
  (`--fallback-server-*`, `TASK-00176`) — a concrete end-to-end walkthrough:
  set up primary + replica (§6), then point a daemon account or gateway
  deployment's fallback fields at the replica, then a "how to verify it
  actually works" section (kill the primary, confirm read continues,
  confirm writes queue, restart the primary, confirm the queue flushes).
- Explicitly document the read-only-while-degraded limitation and WHY
  (cross-reference `ARCHITECTURE.md`'s decision rather than re-deriving
  the split-brain rationale) — a user should understand uploads/edits
  don't work during a failover before they hit that themselves.
- Security hardening checklist (§10) gains a line about the fallback
  `--fallback-ca-cert`/`--ca-cert` requirement, mirroring the existing
  gateway `--state-dir` permissions line added in `TASK-00167`.

## Acceptance criteria

- A reader who has never touched the cluster feature before can follow
  this doc, start to finish, and end up with a working automatic-fallback
  setup — verified by actually following it during this task, not just
  writing prose that sounds plausible (same "verified, not just
  documented" bar `TASK-00167` held itself to).

- **Real, non-obvious finding from actually running the walkthrough
  (not just writing plausible prose — this task's own required bar):**
  a graceful `kill`/`SIGTERM` (and by extension `systemctl stop`) on the
  primary did **not** cause it to release its port or stop serving for
  well over 20 seconds while a fallback-configured daemon held an open
  connection to it — a worker thread blocked in a blocking `recv()` on a
  live connection never notices `g_running` flipping to 0 until that
  connection sees activity or closes. Confirmed with an isolated
  no-client repro (SIGTERM alone: dies in ~3-5s) vs. the full
  daemon-connected scenario (SIGTERM alone: still alive and serving
  `FILE_LIST` 30+ seconds later; the automated Python test suite's own
  `terminate()`-then-`kill()`-on-timeout pattern is why the existing
  `test_cli_fallback.py`/`test_gateway_fallback.py` never surfaced this).
  `kill -9` reproduces a real crash/outage instantly and is what the
  walkthrough now tells the reader to use for an unambiguous test — this
  is documented as its own numbered step (§6.1 step 2) rather than left
  as a trap for the first reader to hit.
- **Second real finding, also only surfaced by actually running it:**
  the task's own draft wording assumed `--fallback-ca-cert` is a soft
  recommendation for the daemon (matching `TASK-00174`'s "optional" CLI
  flag framing). Traced the actual code path
  (`vw_daemon.c`'s `try_connect_fallback` → always
  `VW_CERT_VERIFY_REQUIRED`, no `ca_cert_pem_path` → `vw_net.c` returns
  `VW_ERR_INVALID_ARG` before any network I/O, `vw_net.h` confirms there
  is no "trust OS store" mode at all) and then verified live: omitting
  the flag leaves the account permanently `offline` during a real primary
  outage (never `fallback (read-only)`), with the daemon log filling with
  `fallback connect failed ...: 3` for the whole outage. Corrected §6.1
  and the §10 checklist item to state this precisely — CLI-optional but
  functionally required, a silently-broken feature rather than a security
  gap if omitted — rather than shipping the original, less accurate
  assumption.
- Verification method: built `build-gw-e2e` (WSL/GCC) fresh, then drove
  the exact commands this section now documents against real binaries —
  a real primary + replica pair (server.conf, `cluster node-add`/
  `register-self`, `cluster status`), a real daemon with
