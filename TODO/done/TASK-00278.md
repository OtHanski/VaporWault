`TASK-00275` implemented the server side of `VAULT_DELETE`
(`docs/PROTOCOL.md` §7.11.4, revision 33). Nothing on the client side can
send it yet — no `vw_client_core.c` wrapper, no daemon IPC message, no
`vapourwault-cli` subcommand.

## Acceptance criteria

- `vw_client_core.c` gains a `vw_client_vault_delete(vault_id)`-shaped
  wrapper sending `VAULT_DELETE` and parsing `VAULT_DELETE_ACK`, matching
  the existing `vw_client_vault_create`/`vw_client_vault_list` pattern in
  the same file.
- Daemon IPC gains whatever request/response pair `vw_gui_ipc`/
  `vapourwault-cli` need to reach it (check `vw_ipc.h`'s existing vault-
  related IPC messages first for the pattern to follow).
- `vapourwault-cli` gains a `vault delete <vault_id>` (or matching
  existing `vault` subcommand naming) command.
- Surfaces `VW_ERR_VAULT_NOT_EMPTY` and `VW_ERR_PERMISSION` as clear CLI
  error text, not a bare numeric code.
- Unit/integration test coverage for the new IPC message and CLI command,
  following this codebase's existing test conventions for similar
  client-side additions.

CLI.02 [2026-09-11]: Implemented.

- `vw_client_core.h`/`.c`: `vw_client_vault_delete(sess, vault_id)`, built
  on the existing `revoke_common()` helper (already shared by
  `vw_client_share_revoke`/`vw_client_link_revoke` — identical
  `token[32]+id(u64)` request, `error_code(u32)` response shape).
- `vw_ipc.h`: new `VW_IPC_VAULT_DELETE_REQ`/`_RESP` (0x802D/0x802E, the
  next free pair after the existing vault IPC block) plus doc-comment
  entry.
- `vw_daemon.c`: new `VW_IPC_VAULT_DELETE_REQ` dispatch case (account
  lookup, read-only-fallback rejection — matching `VAULT_CREATE_REQ`'s
  existing treatment as a write-shaped op). On success, also removes the
  vault from that account's in-memory unlocked-vault registry via a new
  `vault_registry_remove()` helper (mirrors `vault_registry_put`'s style;
  a no-op, not an error, if the vault was never unlocked this session).
- `vw_client_cli.c`: new `delete-vault <vault_id>` command (flat verb
  naming, matching this CLI's existing `revoke-link`/`create-link`
  convention — **not** a `vault delete` subcommand, since no `vault`
  subcommand namespace exists in this CLI at all today; adding one just
  for this would be out of scope). New `cmd_delete_vault()` (same wire
  shape as `cmd_revoke()`, kept separate so the success message reads
  "deleted" rather than "revoked").

**Correction to this task's own acceptance criteria**, found by reading
the actual code before implementing (matching the review's own emphasis
on verifying before acting): `check_u32_resp()` — the shared response
handler used by every single command in this CLI, including `unshare`/
`revoke-link`/every other error path — always prints `"daemon returned
error %u"` with the bare numeric code; no command anywhere in this file
has a human-readable per-error-code string table. Adding one solely for
`VW_ERR_VAULT_NOT_EMPTY`/`VW_ERR_PERMISSION` would be inconsistent,
one-off special-casing rather than following existing convention, so
`delete-vault` intentionally reports errors the same way every other
command does. A project-wide "give the CLI human-readable error strings"
pass, if wanted, is a separate, larger task, not folded in here.

**Test coverage** (also correcting this task's own "unit test" framing —
the client-core wrapper is thin wire encoding, already exercised via the
Python wire-level tests below rather than a separate C unit test, the
same coverage split `test_vw_vault.c`'s own docstring already documents
for `vw_vault_create`/etc.): added `vault_delete()` to
`tests/integration/vw_client.py` and four new tests to
`tests/integration/test_vault.py` — basic delete removes it from
`VAULT_LIST`/`VAULT_KEY_FETCH`, non-owner gets `VW_ERR_PERMISSION`,
unknown/already-deleted gets `VW_ERR_NOT_FOUND`, and a vault with a live
referencing version gets `VW_ERR_VAULT_NOT_EMPTY`. All 17 tests in
`test_vault.py` pass against a real server (WSL, `build-wsl-werror`).

No daemon-IPC-level automated test added: confirmed no such test exists
for *any* existing vault IPC message (`VAULT_CREATE_REQ`/`_LIST_REQ`/
etc. either) — this whole layer's only real consumer today is the
desktop GUI, tested manually. Not introducing a new coverage pattern
just for this one message; verified instead by exact structural mirroring
of `VAULT_CREATE_REQ`'s already-working dispatch case, plus a manual
`--help`/usage-error smoke test of the new `delete-vault` CLI command.
