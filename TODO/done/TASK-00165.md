Depends on `TASK-00164`'s per-slot cookie/session model. Today the gateway
has zero on-disk state (`src/gateway/main.c` opens no files besides
stdout/stderr logging) and its session pool is purely in-memory
(`vw_gateway_session_pool_create`, `vw_gateway_session.c:22`) — a gateway
process restart wipes every logged-in browser's session, and login cookies
carry no `Max-Age` (session-only, cleared on browser close).

## Work

- `/api/login` gains a `remember: boolean` field. When true, the
  `Set-Cookie` response for that slot gets `Max-Age=2592000` (30 days,
  matching the server's own `DEFAULT_SESSION_TTL_SECS`,
  `src/server/vw_auth.c:54`) instead of being session-only.
- New `--state-dir` CLI flag for `src/gateway/main.c` (the gateway has
  never had one before). Add a small on-disk store there — a flat
  fixed-size-record file, following this codebase's established
  `vw_cache.c`-style convention — mapping remembered cookie value (the
  gateway-issued `cookie_hex`, `VW_GATEWAY_COOKIE_HEX_LEN` bytes) →
  `vw_client_get_token()`'s resumable session token (`VW_TOKEN_BYTES`) +
  a display username, one entry per remembered slot-cookie.
- On a `require_session()` cookie-miss (gateway restarted, or the pool
  entry was idle-evicted/capacity-evicted but the browser still presents a
  `remember`-flagged cookie): look up the persisted store by that exact
  cookie value; if found, call `vw_client_resume()` with the stored token.
  On success: re-register the live session in the pool under the *same*
  cookie value (transparent to the browser — no new `Set-Cookie` needed),
  and immediately persist the rotated token (`vw_client_resume`'s
  single-use-per-resume rule, `docs/PROTOCOL.md` §7.1 — mirror exactly what
  `vw_daemon.c`'s `try_connect()` already does: "Persist fresh token" right
  after `vw_client_get_token`). On failure (expired/revoked): fall through
  to today's 401, and delete the stale on-disk entry (simple lazy GC, no
  separate sweep needed).
- `/api/logout` with a `remember`-flagged slot must also delete that
  slot's on-disk entry, not just the in-memory pool one — otherwise a
  "logged out" browser would silently resume itself on its next request.

## Security note (`security-sensitive`)

This on-disk store is a bearer-credential store exactly as sensitive as a
password — anyone who can read it can impersonate every remembered
account. `ARCHITECTURE.md`'s Risks table already flags the daemon's
`session.tok` precedent as having no real Windows ACL/OS-keychain
protection and explicitly warns against carrying that into "a richer
multi-session gateway target" — this is that target. Apply real file
permission hardening: POSIX `0600` owned by the gateway service user;
on Windows, an explicit ACL restricting access to the service account (not
just relying on default NTFS inheritance). SEC.07 sign-off required before
`done`, and must include a check for the resume-rotation race: two
near-simultaneous requests both hitting a cookie-miss and both attempting
`vw_client_resume()` on the same stale token — only one can succeed
(single-use); the loser must get a clean 401, not a crash or a corrupted
on-disk entry.

## Acceptance criteria

- A `remember`-flagged login survives a full gateway process kill +
  relaunch: the same browser cookie, presented again after restart,
  transparently resumes without re-sending credentials.
- A non-`remember` login does not survive a gateway restart (no on-disk
  entry created for it) — this feature is opt-in.
- Logging out a remembered slot removes both the in-memory pool entry and
  the on-disk one.
- File permissions verified on both POSIX and Windows (SEC.07-reviewed
  test, not just code inspection).
- Resume-rotation race handled cleanly (test in `TASK-00168`).

**WEB.09 [2026-08-13]:** Implemented as designed, plus one deliberate
simplification vs. the literal "Work" section: `vw_cache.c`-style fixed-
records file, but WITHOUT that module's in-memory hashtable + rwlock —
neither is needed here (the gateway's own request loop is single-
threaded, `main.c`/`vw_gateway_session.h`'s existing convention; the
store's realistic scale is a handful of remembered browsers, not
thousands of cache entries), so the "established convention" being
reused is specifically "fixed-size on-disk records with a free-slot
marker," not the concurrency machinery around it.

- New `src/gateway/vw_gateway_remember.[ch]`: `remember.db` under a new
  `--state-dir` (`main.c`), one 192-byte fixed record per remembered
  login (`cookie_hex` → `token[32]` + `username`), fully mirrored in
  memory, `VW_GATEWAY_REMEMBER_MAX_ENTRIES = 256` hard cap (matches
  `vw_gateway_session.h`'s own philosophy). Entirely opt-in: omitting
  `--state-dir` leaves the whole feature disabled (a `remember: true`
  login is silently treated as session-only — never an error).
- Permission hardening (the task's own security note, and the reason
  this is `security-sensitive`): POSIX `chmod 0600`; Windows a REAL
  `SetNamedSecurityInfoA` DACL restricted to the current user, with
  `PROTECTED_DACL_SECURITY_INFORMATION` explicitly blocking inherited
  ACEs — NOT `vw_daemon.c`'s `tok_save()` Windows path, which is the
  exact "simplified: use normal file" gap `ARCHITECTURE.md`'s Risks
  table already flagged and this task exists to not repeat. A matching
  `vw_gateway_remember_verify_perms()` (POSIX stat-mode check; Windows
  queries the real DACL and requires exactly one ACE, for the current
  user) backs a real test, not just code inspection — see the new
  `tests/unit/test_vw_gateway_remember.c`, which ran on **both** trees
  (`build-gw-e2e` for the POSIX path, `build-msvc-105` for the real
  Windows ACL path — 286/286 assertions pass on each).
- `vw_gateway_api.c`: `cfg`/the remember store are cached in file-static
  globals (`g_server_cfg` set every `vw_gateway_dispatch()` call — same
  pointer/values every time, `main.c` never rebuilds it;
  `g_remember_store` set once at startup via a new
  `vw_gateway_api_set_remember_store()`) rather than threading a new
  parameter through the ~20 handlers that never otherwise needed `cfg` —
  safe specifically because this module is already documented single-
  threaded-only.
  - `require_session()`: on a pool cookie-miss, tries
    `try_resume_and_reinsert()` before giving up — looks up the store,
    `vw_client_resume()`s, and on success re-inserts into the pool under
    the SAME cookie value (new `vw_gateway_session_reinsert()` in
    `vw_gateway_session.[ch]` — transparent to the browser, no new
    `Set-Cookie`) and immediately persists the rotated token (single-use
    resumption, `docs/PROTOCOL.md` §7.1 — same "persist fresh token
    right after `vw_client_get_token`" convention `vw_daemon.c`'s
    `try_connect()` already follows). A resume failure (expired/revoked)
    or a reinsert failure (pool at capacity) both delete the on-disk
    entry — correct even for the capacity case, since `vw_client_resume`
    succeeding has *already* rotated past the old token server-side
    (comment in the code walks through why explicitly, since this isn't
    obvious on a first read).
  - `handle_login()` gained the `remember` body field; on success (and
    only if the store is enabled) persists the token and adds
    `Max-Age=2592000` (30 days, matching the server's own
    `DEFAULT_SESSION_TTL_SECS`) to the `Set-Cookie`.
  - `handle_logout()` and `evict_slot_if_present()` (the re-authenticate-
    an-occupied-slot path from `TASK-00164`) both now also delete the
    matching on-disk entry — otherwise a logged-out or replaced slot
    would either silently resume itself on the next request (logout) or
    permanently leak a store slot (re-auth).
- **SEC.07's required "resume-rotation race" check**: satisfied by
  *architecture*, not added locking. `main.c`'s accept loop is
  single-threaded and strictly sequential (accept → recv → dispatch →
  close → accept next), so two requests presenting the same stale
  cookie can never both reach `vw_client_resume()` concurrently — the
  first either succeeds (re-inserting a live pool entry, so a second
  request takes the ordinary live-session path, never re-resuming) or
  fails (evicting the on-disk entry, so a second request gets a clean
  401). New integration test
  `test_remember_resume_then_immediate_second_request_both_succeed`
  exercises exactly this sequence end-to-end (two requests on the same
  cookie right after a real gateway restart, both must succeed) —
  documented as the actual proof, not just an inline code comment.
- New integration tests (`tests/integration/test_gateway.py`, all four

  `test_non_remember_login_does_not_survive_restart`,

**Self-review (CQR.08 + SEC.07 combined, since both are required
reviewers here) [2026-08-13]:** One real bug caught before ever reaching
a build: the unit test's own `make_cookie()` helper generated only 16
truly distinct cookie strings (a rotating single hex digit, aliasing for
`n` and `n+16`), which silently turned the hard-cap test's "put 256
distinct entries" into "update the same 16 entries repeatedly" — the
store never actually filled, so the expected `VW_ERR_QUOTA_EXCEEDED`
never fired. Caught by the test itself failing on first run (not by
inspection) and fixed by encoding `n` directly into the first 8 hex
digits. Re-verified afterward that no *production* code has the same
class of bug: `vw_gateway_remember_put`'s free-slot search and
`find_by_cookie`'s linear scan both operate on the real, full-length
64-hex-char `cookie_hex` value (the caller's actual random cookie, never
a test-only shortened key), so this was a test-helper bug only, not a
store bug — confirmed by re-reading `vw_gateway_remember.c`'s `put`/
`find_by_cookie` line by line against this exact failure mode.
Everything else reviewed clean: `evict_slot_if_present`/`handle_logout`/
`try_resume_and_reinsert`'s remember-store cleanup calls are all
correctly guarded by `g_remember_store != NULL`; the Windows ACL code
was actually exercised (not just compiled) via `build-msvc-105`, not
left as an untested code path; `vw_gateway_session_reinsert`'s defensive
`VW_ERR_ALREADY_EXISTS` check confirmed unreachable in practice (only
called after `require_session`'s own `vw_gateway_session_get` already
missed the same cookie) but kept rather than removed, since the cost of
keeping a defensive check that never fires is near zero and the cost of
being wrong about "never" is a use-after-free-adjacent double-insert.
