Full audit of the new attack surface this milestone introduces — the
client's first-ever outbound connection to a non-VaporWault host, plus a
self-replacing install mechanism. Cover at minimum:

- Outbound TLS to a non-pinned host (`vw_update_net.c`): cert validation
  actually enforced (no silent fallback to unverified), redirect-loop
  bounding, response-size bounding, the Windows `CertOpenStore` shim.
- Hand-rolled HTTP/1.1 response parsing: malformed input handling, no buffer
  overflows on attacker-controlled `Content-Length`/headers.
- Hand-rolled manifest parser: fuzz-test results, verify-before-parse
  ordering actually enforced in code.
- ECDSA verify wrapper and the manifest signing scheme: rollback/sequence
  ratchet correctness, no TOCTOU between manifest verify and asset fetch.
- Self-replacing install logic on both platforms: `vapourwault-updater`'s
  target-directory/PID handling, no arbitrary-path or privilege-escalation
  angle, package-manager-owned files never touched (portable-vs-package
  detection's fail-safe default actually holds under adversarial conditions).
- `daemon.conf` policy toggle: can a local unprivileged process or a
  malicious IPC client flip `update_policy` or corrupt the ratchet value in
  a way that defeats rollback protection?
- The new `UPDATE_SIGNING_KEY`/GPG key custody in CI — confirm no key
  material is logged or left on disk after the job.

## Notes

**SEC.07, 2026-09-16 — full audit**: Read every listed area end-to-end
(not just diffs). Cross-referenced against the per-task SEC.07/CQR.08
review passes already done during implementation (commit `9a9075c` for
TASK-00292-00298, plus this session's TASK-00305 review) rather than
re-litigating findings already fixed there. No new blocking findings.
One pre-existing advisory (recorded on TASK-00305, related
infrastructure, not this milestone's own code) noted below for
completeness.

1. **Outbound TLS to a non-pinned host** (`vw_update_net.c`): uses
   `VW_CERT_VERIFY_SYSTEM_STORE` (the OS trust store), never
   `VERIFY_NONE`, for the one real production host. Redirects are
   restricted to an exact-or-subdomain allowlist of `github.com`/
   `githubusercontent.com` (`host_is_allowed_redirect_target`) — verified
   the suffix check is a true trailing-bytes comparison requiring a `.`
   boundary, not a substring/`strstr` check, so `evilgithub.com` and
   `github.com.evil.com`-style bypasses both correctly fail. Redirect
   count is hard-bounded to 1. Response size is bounded
   (`VW_UPDATE_MAX_HEADER_BYTES`, `max_body_bytes` checked *before* any
   body allocation) and the whole read phase has a wall-clock deadline
   (`VW_UPDATE_TOTAL_READ_DEADLINE_SECS`) independent of the per-recv
   timeout, closing the "peer trickles bytes to stall forever without
   any single recv() timing out" gap. Windows `CertOpenStore` shim
   (`vw_net.c`) reviewed separately under TASK-00296's own review; no
   changes since.
2. **Hand-rolled HTTP/1.1 response parsing**: `parse_response_head`
   rejects malformed status lines, uses `strtol` (not `atol`, already a
   documented prior finding) with explicit `ERANGE`/overflow checks for
   `Content-Length`, rejects chunked encoding outright (no chunked
   parser exists to have bugs in), and never allocates the body buffer
   before the size bound is checked. No buffer overflow found in the
   header-scan loop (bounded by `hdrbuf`'s fixed size, checked every
   iteration before the next `recv`).
3. **Hand-rolled manifest parser**: verify-before-parse ordering
   confirmed enforced in code, not just by convention —
   `vw_update_manifest_fetch_and_verify` computes the SHA-256 and calls
   `vw_crypto_ecdsa_p256_verify` over the raw fetched bytes, and only
   calls `vw_update_manifest_parse` after that returns `VW_OK`; a
   verify failure returns before the parser is ever reached. Parser
   rejects unknown top-level/asset fields (fail-closed, not
   permissively-ignored), caps string field lengths, rejects raw
   control bytes and unsupported escapes, and `is_path_safe_component`
   rejects any `filename`/`release_version` containing a path separator
   or `..` before either value can reach a filesystem path anywhere
   downstream. Existing fuzz target `tests/fuzz/fuzz_update_manifest.c`
   present and wired into `tests/fuzz/CMakeLists.txt`.
4. **ECDSA verify wrapper + manifest signing scheme**: verification goes
   through mbedTLS's own public `mbedtls_pk_parse_public_key`/
   `mbedtls_pk_verify` (not a hand-rolled ECDSA implementation) — the
   only hand-written part is wrapping the compiled-in raw point into a
   fixed, well-known DER SubjectPublicKeyInfo prefix, which
   `mbedtls_pk_parse_public_key` then validates. Rollback ratchet
   (`sequence < last_seen` → `VW_ERR_UPDATE_MANIFEST_ROLLBACK`, ratchet
   NOT advanced on rejection) correctly rejects a replayed older
   manifest once a newer one has been seen, while still accepting a
   repeat of the same (unchanged) latest manifest — required for normal
   daily-check operation, not a gap. TOCTOU between manifest verify and
   asset fetch: closed by construction — `vw_update_download_and_verify_asset`
   fetches the asset from the manifest's own version-pinned URL
   (`/releases/download/v{version}/{filename}`, never `latest` a second
   time) and independently re-hashes the downloaded bytes against the
   manifest's pinned `sha256` before anything is written to disk, so
   even a compromised/changed asset at that exact URL between the two
   fetches would be caught, not silently trusted.
5. **Self-replacing install logic**: `vapourwault-updater` is invoked
   with `--target` = `vw_client_self_exe_dir()` — the *running* binary's
   own resolved path (`/proc/self/exe` on Linux, `GetModuleFileNameA` on
   Windows), never anything IPC/manifest/attacker-influenced. Portable-
   vs-package detection (`vw_update_detect_install_kind`) fails safe
   toward `PACKAGE_OR_UNKNOWN` (notify-only, never self-update) on any
   ambiguity — self-path resolution failure, missing marker, or
   filesystem error — confirmed this is the only path that leads to
   `VW_UPDATE_KIND_PORTABLE`, and `vw_daemon_apply_update_now` re-checks
   this same detection function immediately before applying (not a
   cached/stale value from earlier). `is_safe_entry_name` in the updater
   itself independently rejects any staged entry name with a path
   separator or `..`, not solely relying on `tar`/bsdtar's own
   anti-traversal defaults (already a documented prior finding).
   `--wait-pid` is bounded (`VW_UPDATER_MAX_WAIT_SECS`), and a failed
   swap best-effort restores the `.old` backup rather than leaving the
   install half-swapped.
6. **daemon.conf policy toggle / malicious IPC client**: the IPC
   listener (`vw_ipc_server_open`) binds loopback-only
   (`INADDR_LOOPBACK`), and every accepted connection is already
   verified against the daemon process's own owning user before this
   milestone existed — Linux via `/proc/net/tcp`'s per-socket uid
   (`vw_ipc_linux_proc_net_tcp_uid`, TASK-093) and Windows via
   `GetExtendedTcpTable` + `OpenProcessToken`/SID comparison (TASK-103).
   This pre-existing, already-audited mechanism governs every IPC
   message type, the new `UPDATE_*` ones included — confirmed no
   separate/weaker path exists for them. `VW_IPC_UPDATE_POLICY_SET_REQ`
   strictly validates the requested policy byte against the two known
   enum values (`VW_ERR_INVALID_ARG` otherwise, never silently
   coerced). No IPC message writes the rollback-ratchet sequence value
   directly — it's only ever advanced by
   `vw_update_manifest_fetch_and_verify` after a full signature check,
   so a same-user local process can toggle operational policy or
   trigger applying an already-verified pending update sooner, but
   cannot fabricate or forge what "pending update" means. A same-user
   process directly editing `daemon.conf` on disk is an existing,
   accepted trust boundary of this daemon generally (session tokens,
   vault key material, etc. share that same file/directory), not a gap
   specific to this feature.
7. **`UPDATE_SIGNING_KEY`/GPG key custody in CI**: both the ECDSA
   manifest-signing key (`UPDATE_SIGNING_KEY`) and the Android release
   keystore secret follow the same pattern — materialized to
   `$RUNNER_TEMP` (never a build artifact directory, never `dist/**`)
   for the signing step only, removed by an immediately-following
   `if: always()` cleanup step so removal still runs on failure, and
   never echoed (GitHub Actions masks secret values referenced only via
   `secrets.*`). Confirmed no `actions/upload-artifact` step in
   `release.yml` globs `$RUNNER_TEMP` or a path that could include it.

No blocking findings. Milestone tasks may proceed to `done` on this
