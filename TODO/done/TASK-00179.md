**Out-of-domain discovery, found while implementing `TASK-00173`** (daemon
per-account read-only fallback): the read-only property this whole
milestone is named after is currently enforced ONLY by the daemon's own
good behavior (`TASK-00173`: the daemon simply chooses not to send
write-shaped requests to a fallback session, queuing them locally
instead). Nothing on the server side actually stops a normal client from
sending `FILE_COMMIT`/`CHUNK_UPLOAD`/`FILE_DELETE`/`FILE_MOVE`/`FILE_MKDIR`/
`SHARE_GRANT`/`VAULT_CREATE`/etc. straight to a replica's own client-facing
`vw/1` listener — `TASK-00172` confirmed the replica runs the FULL normal
server stack unconditionally, and none of its handlers check
`cfg.cluster.is_replica` before executing a write.

**Why this wasn't a blocking finding for `TASK-00172`/`00173`:** a write that
lands directly on a replica is not *permanently* divergent. `TASK-00172`'s
sync pass does a wholesale hash-compare-then-overwrite of the replica's
own copy of all 8 syncable files on every batch with oplog activity
(`CLUSTER_FILE_SYNC_LIST` reports every tag's current hash every time, not
just changed ones) — so the next time the primary produces ANY oplog
entry after reconnecting, the replica's diverged copy gets silently
overwritten back to the primary's content. The rogue write is lost, not
propagated, and does not corrupt the primary. Still, "silently discarded
eventually" is a sharp edge worth closing rather than relying on: (a) the
daemon behaving itself, and (b) every other possible client (`vapourwault-
cli` pointed manually at the replica's host:port, a hand-rolled script,
the web gateway before `TASK-00176` lands, etc.) also behaving itself.

## Work

- In `vw_file_handlers.c`'s (or wherever is cleanest — `vw_server_core.c`'s
  dispatch, if that's a single choke point) top-level message dispatch:
  when the running server's own `cfg.cluster.is_replica` is true, reject
  every write-shaped message type (`FILE_COMMIT`, `CHUNK_UPLOAD`,
  `FILE_DELETE`, `FILE_MOVE`, `FILE_MKDIR`, `SHARE_GRANT`/`REVOKE`,
  `LINK_CREATE`/`REVOKE`, `VAULT_CREATE`, and any others CQR.08/SEC.07
  identify as mutating) with a distinct, documented error code (not
  `VW_ERR_PERMISSION`, which already means something else — e.g. a new
  `VW_ERR_READ_ONLY_REPLICA`) rather than executing them. Reads (`FILE_
  LIST/STAT`, `CHUNK_DOWNLOAD_REQ`, `SHARE_LIST`, `VERSION_LIST/CHUNKS`,
  vault list/key-fetch, `LINK_ACCESS` for a view-permission link) are
  unaffected.
- Update `docs/PROTOCOL.md` with the new error code and this rejection
  behavior (new row in whatever table documents `VW_ERR_*` codes, plus a
  note in §7.7 or a new subsection cross-referencing this).
- `TASK-00173`'s daemon should be updated to treat this new error code the
  same as a net error when talking to a fallback session (queue instead
  of counting as an action error) — a small follow-up note on `TASK-00173`
  if that task closes first, or folded in here if not.

## Acceptance criteria

- A direct `FILE_COMMIT`/`CHUNK_UPLOAD`/etc. attempt against a server
  configured with `cluster_is_replica = 1` is rejected with the new error
  code and does not mutate any on-disk state.
- The identical request against a non-replica server is unaffected
  (regression: full existing test suite green).
- Reads against a replica are unaffected.

**SRV.01, 2026-08-17 — implementation complete, moving to review.**

- `vw_proto.h`: new `VW_ERR_READ_ONLY_REPLICA = 606` in the existing
  "File transfer" (600s) block, next to `VW_ERR_RATE_LIMITED` — placed
  there rather than alongside `VW_ERR_READ_ONLY_FALLBACK` (801) since this
  one genuinely crosses the wire; the 800 block's own comment says
  "never sent over the wire," which would be actively misleading here.
- `vw_cluster.h`/`.c`: new `int vw_cluster_is_replica(const vw_cluster_t
  *ctx)` accessor (`vw_server_ctx_t` has no direct access to `cfg.cluster`
  today — only a borrowed `vw_cluster_t *` via `vw_server_ctx_cluster()`
  — so this is the minimal new surface needed). NULL-safe (a
  non-clustered server has `cluster == NULL`, correctly reads as "not a
  replica").
- `vw_file_handlers.c`: new file-local `is_write_shaped_msg()` and one
  check at the very top of `vw_server_dispatch_file_op` (before either of
  its two switches, so it covers both the admin-ops branch and the
  file-ops branch with a single choke point) — rejects with
  `VW_ERR_READ_ONLY_REPLICA` before any handler runs, so no on-disk state
  is ever touched for a rejected request.
- **Scope note, decided here rather than silently expanded:** the task
  text's own list (`FILE_COMMIT`, `CHUNK_UPLOAD`, `FILE_DELETE`,
  `FILE_MOVE`, `FILE_MKDIR`, `SHARE_GRANT`/`REVOKE`, `LINK_CREATE`/
  `REVOKE`, `VAULT_CREATE`) explicitly invites CQR.08/SEC.07 to add
  anything else that mutates. Went through both of the dispatcher's
  switches by hand and added three more real mutations: `VERSION_RESTORE`
  (creates a new version record + adjusts refcounts — a write in every
  sense the listed ones are), and the admin-only `USER_SUSPEND`/
  `QUOTA_ADJUST`/`INVITE_CREATE` (dispatched from the same function's
  first switch, before the file-store null-check — a replica has no
  business accepting an admin write either, for the identical
  eventually-silently-overwritten reasoning the task gives for the file
  ops). `AUDIT_QUERY`/`USER_LIST`/`CLUSTER_STATUS` (same first switch)
  and `LINK_ACCESS` (not in this dispatcher at all — scoped-session
  entry, separate code path) are reads/handshakes and correctly left
  alone.
- `docs/PROTOCOL.md`: added the new code to §10.1's table plus a
  paragraph explaining the rejection behavior and cross-referencing
  `ARCHITECTURE.md`'s amended "Client-side automatic fallback" decision
  row (found and closed the exact gap that row calls out by name).
  Backfilled two pre-existing but-never-documented codes found missing
  from that same table while touching it (`VW_ERR_IPC_NOT_RUNNING` = 700,
  `VW_ERR_READ_ONLY_FALLBACK` = 801) and one missing Version History row
  for `TASK-00169`/`00170`'s hot-standby protocol section (added as revision
  20; this task's own change is revision 21) — both were prose-only gaps
  already present in the working tree before this task touched the file,
  not something this task's own change introduced.
- `vw_sync.c`'s `is_net_err()` (this task's own listed follow-up for
  `TASK-00173`, which closed first): added `VW_ERR_READ_ONLY_REPLICA`
  alongside the existing `NET_*` codes, so a client that legitimately hit
  this — despite `ctx->read_only` already stopping the sync engine from
  attempting the send in the first place — queues the write instead of
  counting it as an action error. True backstop-of-a-backstop; documented
  inline why the normal path shouldn't reach it at all.
- No IPC-side change needed: `vw_daemon.c`'s six synchronous
  `account_is_read_only()` checks (`SHARE_GRANT_REQ` etc., `TASK-00173`)
  reject before ever touching the network, so they never see this new
  wire-level code either way.

**CQR.08/SEC.07 self-review, 2026-08-17.**
