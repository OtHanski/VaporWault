Otto asked for "an actual proper installer" for the server and client
software, built and distributed by the CI release workflow — a step up
from today's release artifacts, which are plain tarball/zip archives
(`.github/workflows/release.yml`) containing raw binaries plus manually-run
install scripts (`packaging/linux/install.sh`, `client_install.sh`,
`packaging/windows/Install-VaporWault.ps1`,
`Install-VaporWaultClient.ps1`). Those scripts already encode real,
correct install logic (system user creation, directories, systemd
unit/Windows Service or Scheduled Task registration, config templating,
idempotent re-install) — this design reuses that logic rather than
replacing it, wrapping it in real OS-native packages.

Two decisions were confirmed directly with Otto:

1. **Windows**: MSI via CMake's built-in CPack WIX generator (WiX Toolset
   v3 `candle`/`light`), not a separate Inno Setup script — this reuses the
   CMake `install()` rules already in `CMakeLists.txt` instead of a second,
   parallel packaging mechanism.
2. **Linux**: both `.deb` (CPack DEB) and `.rpm` (CPack RPM), not `.deb`
   only — covers Debian/Ubuntu and Fedora/RHEL/openSUSE.

## Design

- **Packaging mechanism**: CPack, driven entirely by `install()` rules
  already declared in `CMakeLists.txt`. No new external dependency — CPack
  and its DEB/RPM/WIX generators ship with the CMake already in use; WiX
  Toolset v3 itself is the one new *build-time* tool required (not a
  runtime dependency of the shipped software).
- **Component split**: two CPack components, `server` and `client`,
  mirroring the existing install-script split exactly. Each pulls in its
  GUI binary when `VW_BUILD_GUI=ON` (`vapourwault-server-gui` /
  `vapourwault-gui`). `vwdump` ships with `server` (admin diagnostic tool).
  Four Linux artifacts (`server`/`client` × `deb`/`rpm`) and two Windows
  MSIs (`server`/`client`) — one installable unit per component per
  format, not a single combined package with optional features.
- **Linux maintainer scripts**: written once as portable POSIX `sh` under
  `packaging/linux/scripts/`, reused as both DEB's `postinst`/`prerm`/
  `postrm` and RPM's `%post`/`%preun`/`%postun` scriptlets. The scripts'
  *content* (create service user, directories, config template, systemd
  unit reload) can be identical across both ecosystems; only the
  *invocation argument convention* differs (DEB's `postrm remove` vs
  `postrm purge`; RPM's `$1` install-count semantics for upgrade vs final
  removal) — each ecosystem gets a thin wrapper that interprets its own
  convention and calls into the shared logic.
- **Windows server**: WiX native `<ServiceInstall>`/`<ServiceControl>`
  elements register `vapourwaultd` as a real Windows Service participating
  in the MSI's own install/rollback/uninstall transaction — replacing
  `Install-VaporWault.ps1`'s manual `New-Service`/`sc.exe` calls for this
  path. `WixFirewallExtension` declares the inbound TLS port rule
  declaratively (replacing the manual `New-NetFirewallRule` call). This
  package **requires elevation** (per-machine install), matching the
  existing script's own Administrator requirement.
- **Windows client**: the client daemon is a **per-user Scheduled Task**
  (logon trigger), not a Windows Service (`Install-VaporWaultClient.ps1`'s
  existing design — no root/admin required, installs under
  `%LOCALAPPDATA%`/`%APPDATA%`). WiX has no clean native Scheduled-Task
  authoring in v3 without extra fragility, so the client MSI runs a
  deferred custom action invoking the same scheduled-task-registration
  logic already proven in `Install-VaporWaultClient.ps1`, rather than
  reimplementing Scheduled Task XML from scratch.
- **Existing PowerShell/shell install scripts are kept**, not removed —
  documented as the manual/advanced-use path (e.g. custom install
  locations, air-gapped installs from a tarball) alongside the new
  packages as the standard path.
- **No package signing** in this initial design (no code-signing
  certificate/infrastructure exists for this project) — unsigned `.deb`/
  `.rpm`/`.msi` will trigger the usual OS trust warnings on install. Noted
  as an accepted gap, not silently glossed over.

SEC.07 [2026-08-11]: Adversarial design review complete. One `blocking`
finding, now resolved:

**Blocking (resolved):** The original sketch for the Windows client MSI
didn't specify its elevation context. This matters concretely: if the
client MSI required machine-wide elevation (as the server MSI correctly
does, for its per-machine Windows Service), its deferred custom action
would run as `SYSTEM` (or under whatever elevated token triggered the
UAC prompt) — registering the per-user Scheduled Task in the *wrong*
security context (owned by SYSTEM/the elevating admin account, not the
actual interactive user who wants their files synced), or requiring
custom-action impersonation tricks to work around it. **Resolved**: the
client MSI must be a **per-user install requiring no elevation** —
`%LOCALAPPDATA%`/`%APPDATA%` install locations (already what
`Install-VaporWaultClient.ps1` uses) need no admin token, so the MSI, its
file deployment, and its custom action all naturally run in the same
(correct, current-user) security context with no impersonation needed.
Added to `ARCHITECTURE.md`'s Windows client registration decision row.
