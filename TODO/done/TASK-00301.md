`.github/workflows/release.yml` changes:

- New step (after the existing `.sha256` generation, before the GPG-import
  step) fetches the *current*
  `https://github.com/OtHanski/VaporWault/releases/latest/download/update-manifest.json`
  (best-effort; a **404 on the very first release must not fail the job** —
  treat as `sequence` starting at 1), extracts its `sequence` via `jq`
  (present on `ubuntu-latest`), sets this run's `sequence = previous + 1`.
- Builds `update-manifest.json` from `$PKG_VERSION`, the computed `sequence`,
  `$(date +%s)`, and the tarball/zip filenames + their already-computed
  SHA-256 sums (reuse existing `.sha256` output — no second hashing pass).
  `min_client_protocol_version`: grep it directly from
  `src/core/vw_proto.h`'s `VW_PROTO_VERSION_CURRENT` define, not
  hand-duplicated in the workflow.
- Signs with `openssl dgst -sha256 -sign` against the private key
  materialized from the `UPDATE_SIGNING_KEY` secret (`TASK-00293`) into a
  runner-local temp file, deleted immediately after signing.
- Adds `update-manifest.json` + `update-manifest.json.sig` to the
  `gh release create`/`gh release upload` file list.
- Adds a `.vw-portable` marker file to the Linux/Windows tarball/zip staging
  directories **only** (never to what CPack packages — no `install()` rule
  changes, confirmed by `TASK-00295`'s research into `release.yml`'s
  `cp build/bin/* "$STAGE"/` vs. CPack's declared-target packaging).
- Ships the new `vapourwault-updater` helper binary (`TASK-00298`) inside the
  portable `tar.gz`/`zip` archives.

- `.vw-portable` confirmed present in tarball/zip, confirmed **absent** from

## Notes

**BLD.05, 2026-09-16**: Implemented with one real design deviation from
the original sketch, found necessary while actually writing the workflow
rather than assumed.

**Design deviation, and why**: the original sketch placed the new
manifest-generation step "after the existing `.sha256` generation, before
the GPG-import step" — both of which exist only in `build-linux`. But a
manifest with `assets[]` entries for *both* Linux and Windows can't
actually be built there: `build-linux` and `build-windows` run in
parallel, and `build-linux` has no access to the Windows zip's checksum
at that point. The only job that already has both platforms' artifacts
downloaded (`dist/linux-release/*`, `dist/windows-release/*`) is
`publish` — so manifest generation, the previous-sequence fetch, and
signing all moved there instead. This also required removing `publish`'s
job-level `if: github.event_name == 'push'` gate (replaced with a
step-level gate on just the final `gh release create`/`upload` step) —
otherwise a `workflow_dispatch` dry run would never reach the manifest
steps at all, contradicting this task's own first acceptance criterion.
`publish` also gained its own `actions/checkout` (previously it only
downloaded build artifacts) — needed to grep `min_client_protocol_version`
from `src/core/vw_proto.h`.

**Implementation**:
- `.vw-portable` marker added to both `build-linux`'s and `build-windows`'s
  "Stage release archive" steps, directly in `$STAGE`/`$stage` — never
  touches what CPack packages for `.deb`/`.rpm`/`.msi` (those are built
  from `build/`'s own `install()` rules, which never read from the
  staging directory at all).
- `vapourwault-updater` needs no separate copy step — `cp build/bin/*`
  (Linux) and `Copy-Item build/bin/*.exe` (Windows) already include it,
  since it's an ordinary, unconditional target in
  `src/client/CMakeLists.txt` alongside every other client binary.
- `publish` job: `Fetch previous update-manifest sequence` (404-tolerant,
  `curl` against the same stable `releases/latest/download/...` alias the
  client itself uses) → `Generate update-manifest.json` (`jq`, reusing the
  already-computed `.sha256` sidecars, `min_client_protocol_version`
  grepped from `vw_proto.h`) → `Sign update-manifest.json` (`openssl dgst
  -sha256 -sign` against `UPDATE_SIGNING_KEY`, materialized to
  `$RUNNER_TEMP` and removed by the very next step regardless of outcome)
  → both files added to the `gh release create`/`upload` file lists.

**Verification performed (no real GitHub Actions run available)**:

- Every step's shell logic hand-traced against this project's own
  established conventions (TAG/REPO always via workflow-level `env:`

  behavior confirmed compatible with the 404-tolerant `curl` check, since

**SEC.07 (2026-09-16)**: Confirmed `UPDATE_SIGNING_KEY` custody:
materialized to `$RUNNER_TEMP/update-signing-key.pem` only for the
signing step's duration, removed by the very next step with `if:
always()` (so it's deleted even if signing itself fails) — same pattern
already established for the Android keystore. The secret is referenced
only via `secrets.*` inside an `env:` block, never interpolated into a
shell string directly, so GitHub Actions' log-masking applies; `set -e`
means a failed `openssl` call fails the job rather than silently
proceeding with an unsigned manifest. `$RUNNER_TEMP` is per-job and
wiped with the ephemeral runner regardless. The independently-run
production-code verification (real `vw_crypto_ecdsa_p256_verify()`
against the exact `openssl dgst -sha256 -sign` output, throwaway keypair)
is real evidence, not just YAML inspection. No blocking findings.
