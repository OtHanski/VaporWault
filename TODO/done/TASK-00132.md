Wire the gateway's first real HTTP/JSON endpoints onto `vw_client_core`'s
existing connect/auth API (`src/client/vw_client_core.h`), using the
session manager from `TASK-00131`.

Endpoints:

- `POST /api/login` — username + password → calls `vw_client_core`'s
  connect/`AUTH_REQUEST` equivalent; on `AUTH_CHALLENGE` (2FA enabled)
  return a challenge state to the browser rather than failing.
- `POST /api/login/otp` — OTP code → completes the 2FA round trip
  (`AUTH_OTP`/`AUTH_OK` per `docs/PROTOCOL.md` §8.3), on success creates a
  gateway session (`TASK-00131`) and sets the session cookie.
- `POST /api/logout` — invalidates the gateway session and the underlying
  server session.
- Session-resume-on-reconnect handled transparently inside the session
  manager (`TASK-00131`), not a separate browser-facing endpoint.

Password handling: the browser sends the raw password over HTTPS (nginx
terminates TLS) to `/api/login`; the gateway performs whatever client-side
stretching `vw_client_core`'s connect path already does before putting it
on the wire (matching what `vapourwault-cli`/`vapourwault-gui` do today) —
this task does not change the wire auth scheme itself (that's `TASK-00009`'s
pre-existing, separately-tracked concern), only wires the existing client
path through HTTP.

## Acceptance criteria

- Full login flow (including 2FA challenge/response) works end-to-end
  against a real VaporWault server from an HTTP client (`curl`/integration
  test), producing a valid gateway session cookie.
- Failed login / wrong OTP returns a clean 401-class response, not a crash,
  and does not leak whether a username exists (matching the server's own
  enumeration-resistant design intent for `AUTH_FAIL`/recovery flows).
- Logout actually invalidates both the gateway session and the server-side
  session token (`AUTH_LOGOUT`) — a stolen gateway cookie after logout must
  not still work.

Mapping the actual implementation to this task's scope:
- `POST /api/login` — implemented, calls `vw_client_connect` with the
  raw username/password (client-side stretching happens inside
  `vw_client_core`, unchanged from what `vapourwault-cli`/`-gui` already
  do, per this task's own scope note). On success, creates a gateway
  session (`TASK-00131`) and sets the cookie.
- **Real design deviation, deliberate and documented, from a separate
  `POST /api/login/otp` endpoint**: 2FA is folded into the *same*
  `/api/login` call rather than a second endpoint — the browser
  resubmits username+password+otp together once it sees an
  `otp_required` response (confirmed both sides agree: `vw_gateway_dispatch`
  only ever routes `/api/login`, and `web/src/api.ts`'s `loginWithOtp`
  posts to `/api/login` too, never a separate path). This works because
  `vw_client_connect`'s own OTP callback can distinguish "no code
  supplied yet" (`VW_ERR_AUTH_2FA_REQUIRED`) from "wrong code"
  (`VW_ERR_AUTH_2FA_INVALID`) without any gateway-side "pending login"
  state needing to survive between two HTTP requests. Simpler than the
  originally-sketched two-endpoint design and already reviewed
  (`TASK-00137`'s frontend note, `TASK-00144`'s security pass) without
  objection — recording the deviation here explicitly rather than
  leaving this task's text silently wrong about the actual route shape.
- `POST /api/logout` — implemented (`handle_logout`), calls
  `vw_gateway_session_remove`, which calls `vw_client_logout` on the
  underlying session before clearing the gateway-side slot — confirmed
  by direct code read that this invalidates the real server-side
  session too, not just the gateway's local cookie mapping (also
  independently confirmed during `TASK-00144`'s review).
- Enumeration resistance: `bad_credentials` is returned uniformly for
  both wrong-password and wrong-OTP-after-otp_required (matching this
  task's own acceptance criterion) — confirmed via `handle_login`'s
  error-mapping switch.
- Session-resume-on-reconnect: handled transparently inside
  `vw_client_core` itself, no separate gateway-facing endpoint — matches
  this task's own scope note that this shouldn't be a separate
  browser-facing endpoint.
