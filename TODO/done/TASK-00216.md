Discovered while implementing `TASK-00190` (which was scoped to "add a
password prompt to the frontend's link redemption page" — the design
task, `TASK-00185`, assumed one existed). It doesn't. Checked thoroughly
before filing: no route/view in `web/index.html`/`main.ts` ever calls
`POST /api/links/access` at all, no URL-parameter/path handling for a
shared-link URL exists, and there is no "you followed a shared link,
here's the content" view anywhere in this frontend. The gateway API
side (`handle_link_access` in `vw_gateway_api.c`) has always supported
this — `TASK-00134`/`00140` built the server-side redemption endpoint and
`TASK-00190` just added its password support — but nothing in the browser
frontend has ever called it. `main.ts` line ~160's comment already
anticipates "a redeemed public-link session" (empty-username display
handling exists), suggesting this was scoped once and then the actual
redemption UI never got built, or got dropped silently.

Right now, a link created through this frontend can only be *consumed*
by copying the raw token into some other tool (`vapourwault-cli`, or a
hand-rolled request) — there is no way for an ordinary recipient to
click a link and see anything in a browser.

## Work

- Decide the URL shape: most likely a query parameter or path segment
  nginx routes to the same static frontend (e.g. `/link/<hex-token>` or
  `/?link=<hex-token>`), read client-side via
  `window.location`/`URLSearchParams` — no server-side routing change
  needed since nginx already serves this as a static SPA-less page; the
  frontend's own `main.ts` bootstrap just needs to detect this case
  before showing the normal logged-in UI.
- A minimal redemption view: calls `POST /api/links/access` with the
  token (and, per `TASK-00190`'s work, a password field show/hidden based
  on the `link_password_required`/`_wrong` response — this task can
  reuse that error-handling shape directly).
- On success, reuse as much of the existing logged-in file-browser UI as
  the anonymous scoped session's permissions allow (list/download for
  VIEW, list/download/upload/delete for EDIT) — the empty-username
  display path already partially anticipated this (`main.ts` ~line 160).
- Decide and document what an EDIT-permission anonymous session can and
  can't do in this UI (e.g., should it expose "create a new file" the
  same as a logged-in user, or only edit-in-place existing content?) —
  a real product decision, not just a wiring question; flag to ARCH.00
  if it needs a design call rather than assuming.

## Security note (`security-sensitive`)

Same externally-reachable-surface posture as every other gateway-facing
frontend change (`ARCHITECTURE.md`'s Risk table). A password typed into
this new view must never appear in a URL, browser history, or referrer
header — confirm the request is a `POST` with the password in the body
(matching `TASK-00190`'s existing pattern), never a query string.

## Acceptance criteria

- A real, unauthenticated browser session can open a shared link's URL,
  supply a password if the link requires one, and browse/download (or
  edit, if the link is EDIT-permission) the shared content — verified
  end-to-end through the actual browser frontend, not just the API.
- The link's own token never appears anywhere logged server-side beyond
  what `TASK-00134` already established for the API layer itself.

  instead, which is correct regardless of numbering gaps or sort order.
