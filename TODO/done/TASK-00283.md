Full-project review (`TASK-00269`) confirmed a disclosed limitation from
`TASK-00139`: browser uploads/downloads don't survive a page refresh. Both
native clients (desktop daemon, Android) already resume interrupted
transfers via the existing chunked-upload/resumable-download protocol
primitives — the gap is purely in the browser frontend's own state
handling, not a missing wire capability.

## Acceptance criteria

- On reload, an in-progress upload/download resumes from its last
  completed chunk rather than restarting from zero, using the existing
  `CHUNK_QUERY`-style "which chunks does the server already have"
  mechanism the native clients rely on (`vw_client_core.c`'s upload path
  is the reference implementation to follow, not a new browser-side
  scheme).
- State needed to resume (in-flight transfer id, target vault_id if
  encrypted, chunk progress) persisted client-side in a way that survives
  a reload (e.g. `IndexedDB`/`localStorage`) — no server-side change
  should be needed since the protocol already supports resumability.
- Explicitly handle the E2EE vault case: an in-progress encrypted upload's
  DEK/vault key material must never be persisted unencrypted across a
  reload — flag this to SEC.07 if the natural implementation would
  otherwise do so.

ARCH.00 [2026-09-10]: Filed from the full-project review (`TASK-00269`).

WEB.09 [2026-09-14]: Investigated the native reference implementation
before designing, per this project's own established precedent
(`TASK-00281`). Two corrections to this task's own framing:

1. **Native downloads are not actually resumable.** Read
   `vw_client_core.c`'s `download_by_entry` end to end: it writes to a
   `.tmp` file and on *any* error calls `vw_fs_chunk_writer_abort` and
   deletes the tmp file — there is no code path that resumes from a
   partial `.tmp` on retry. `vw_sync.c` confirms this: it calls
   `vw_client_file_download`/`_by_id` directly with no additional resume
   logic. So "native clients already resume via existing resumable-
   download protocol primitives" is not accurate for downloads — there is
   no such primitive to mirror.
2. **Native "resume" is dedup, not a resume cursor.** What actually makes
   a native *upload* retry cheap is `upload_chunks`'s Pass 2: batched
   `CHUNK_QUERY` (docs/PROTOCOL.md §7.2) asks the server which of the
   locally re-hashed chunks it already has, then Pass 3 uploads only the
   missing ones. There is no persisted "resume cursor" anywhere — a retry
   just re-hashes everything (cheap) and re-queries. This is good news for
   the browser: it means resumability doesn't need a complex persisted
   byte-offset scheme, just the same query-before-upload flow, which also
   means it's automatically robust to a file changing between attempts
   (a stale cursor could never detect that; a fresh hash always would).

Given that, the real, concrete gap this task closes is narrower and more
useful than its own framing suggested: **the gateway had no query-only
endpoint**, so even though the server already deduped chunk storage
per-chunk (`handle_chunk_upload` → `vw_client_chunk_upload_if_missing`),
the browser had no way to avoid re-transmitting a chunk's full body over
the network for content the server already had.

Implementation:

- `src/client/vw_client_core.c`/`.h`: extracted the batched CHUNK_QUERY
  wire logic already inside `upload_chunks`'s Pass 2 into a new public
  `vw_client_chunk_query_batch()` (send in rounds of up to
  `CHUNK_QUERY_MAX` hashes, decode `CHUNK_QUERY_RESP` into a caller-
  supplied missing-bitmask). `upload_chunks` itself now just calls this —
  behavior-preserving refactor, verified by the full native/gateway/CLI
  build all still passing. This file compiles directly into the daemon,
  CLI, and gateway (and, per `MOB.10`'s docs, the Android JNI bridge) —
  build-verified clean in all three C consumers, both gcc `-Werror`
  (`build-wsl-werror`) and MSVC (`build-msvc-105`).
- `src/gateway/vw_gateway_api.c`: new `POST /api/chunks/query` — decodes
  a JSON `chunk_hashes` array (reusing `handle_file_commit`'s existing
  `count_array_elem_cb`/`decode_chunk_hash_cb`/`chunk_hash_decode_ctx_t`
  helpers verbatim, not a re-implementation), calls
  `vw_client_chunk_query_batch()`, responds `{"missing": [bool, ...]}` in
  request order. Route registered alongside `/api/chunks/upload`/
  `/api/chunks/download`.
- `web/src/api.ts`: new `queryChunks()` wrapper; `uploadFile` restructured
  to the native reference's own three-pass flow (hash everything → query
  → upload only what's missing) — this is what gives real cross-reload
  resumability for **plaintext** uploads: a re-selected File is re-hashed,
  queried, and only the chunks that never landed are re-sent. A query
  failure degrades safely to "upload everything" (never a correctness
  risk). `uploadFile`/`uploadFileEncrypted`/`downloadFile`/
  `downloadFileEncrypted` all gained an optional chunk-count progress
  callback for the registry below.
- **Vault uploads are explicitly *not* given this same three-pass
  treatment**, and this is a real, disclosed limitation rather than an
  oversight: `uploadFileEncrypted`'s DEK is generated fresh
  (`randomDek()`) on every call and is a hard requirement to never
  persist (this task's own acceptance criteria, and `vault-crypto.ts`'s
  standing invariant). A fresh DEK means every chunk's ciphertext — and
  therefore its hash — differs on every attempt, so a query against a
  prior attempt's hashes can never find a match; there is nothing to
  dedup against, whether the retry follows a page reload or just a
  same-session failure. No SEC.07 flag needed beyond what already exists
  in `vault-crypto.ts` — the natural implementation here simply doesn't
  persist any key material at all, so the acceptance criteria's third
  bullet is satisfied by construction, not by an added safeguard.
- `web/src/transfer-registry.ts` (new, 4th `web/src/*.ts` module —
  `docs/STYLE.md` §18 updated accordingly): `localStorage`-backed record
  of in-progress transfers (id, slot, direction, file fingerprint,
  path/versionId/vaultId, chunk progress, a `resumable` flag). Explicitly
  persists **no** chunk hashes (re-hashing a re-selected File is cheap and
  always correctness-safe; trusting a stale hash cache instead of
  re-reading the actual bytes would not be) and **no** key material.
- `web/src/main.ts`: `uploadOne`/`handleDownload` register/update/clear a
  transfer record around the existing per-chunk progress callbacks; a new
  interrupted-transfers banner renders on entering the browser view
  (scoped to the active multi-account slot, since the registry is one
  browser-wide `localStorage` store shared across all logged-in slots).
  Upload records offer Resume (re-select the file via a hidden input,
  matched back to the record by name/size/`lastModified` before anything
  is sent) or Discard; non-resumable (vault) upload records and download
  records are worded accordingly — a download's "Resume" is a plain
  restart (no byte-level savings are possible for downloads either way,
  per point 1 above), offered because retrying still saves the user from
  re-finding the file in the browser UI, not because it resumes bytes.

Scope decision on downloads, made explicit rather than left implicit:
given point 1 above, downloads get the same UX-recovery treatment
(tracked in the registry, offered a one-click restart) but not genuine
byte-level resume. Implementing that for real would mean persisting
partially-downloaded ciphertext chunks in IndexedDB across a reload and
re-deriving the DEK on resume — a much larger feature than this task's
own acceptance criteria actually require once corrected against what
native clients really do (nothing, for downloads), and not something this
pass builds speculatively. Filing as a fresh feature idea if wanted is a
call for ARCH.00, not assumed here.
