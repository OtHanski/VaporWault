Discovered while building `TASK-00299`'s IPC integration test
(`test_ipc_update.c`) — extensively misdiagnosed at first as flaky,
ctest-launch-specific sandbox behavior (multiple failed investigation
attempts are visible in that file's and `tests/integration/CMakeLists.txt`'s
git history) before being root-caused directly by reading
`vw_watcher_wait()`.

Root cause: `vw_watcher_wait(watcher, timeout_ms)` — called once per
`vw_daemon_run()` main-loop iteration, with `timeout_ms = cfg->sync_interval_ms`
(default 30000, i.e. 30 seconds) — blocks for the **entire** `timeout_ms`
whenever there are zero watched roots:

- Windows (`vw_watch_windows.c:304-307`): `if (n == 0) { Sleep(timeout_ms); return VW_ERR_TIMEOUT; }`
- Linux (`vw_watch_linux.c:367`): `poll(&pfd, 1, timeout_ms)` on the inotify
  fd, which never fires early since there's nothing registered to watch.

"Zero watched roots" is not a rare edge case — it's the state of **every
freshly-installed daemon with no configured accounts yet**, and of any
account with no sync folders added. `vw_daemon_run()`'s main loop only
reaches its "accept and dispatch pending IPC connections" step once per
this same wait (see the loop's own step ordering, `src/client/vw_daemon.c`),
so in this state, an IPC request can sit unanswered for up to the full
`sync_interval_ms` depending purely on when it happens to arrive relative
to the loop's current sleep/poll call. A real user running
`vapourwault-cli status` (or the GUI polling, or trying to add their
first account) moments after starting a fresh daemon could see a
response delayed by up to 30 real seconds for no reason apparent to
them — this looks exactly like "the daemon hung" from the outside.

## Acceptance criteria

- A daemon with zero watched roots (no accounts, or an account with no
  sync folders) responds to an IPC request promptly (sub-second),
  regardless of how much of the configured `sync_interval_ms` has
  elapsed — verified with a real test issuing two IPC requests moments
  apart against such a daemon (not just by inspection).
- No change to the actual sync-pass cadence once folders ARE configured
  — this is specifically about IPC responsiveness while idle/unconfigured,
  not a general "poll more often" change to the sync loop's own timing.
- Consider decoupling "how often do we check for pending IPC connections"
  from "how long do we wait for a filesystem event" — e.g., capping the
  per-iteration wait passed to `vw_watcher_wait`/the no-watcher `Sleep`
  branch to something short (a second or less) and looping additional
  iterations to accumulate the configured `sync_interval_ms` before
  actually running a sync pass, rather than changing what
  `sync_interval_ms` itself means.

## Notes

**CLI.02, 2026-09-16**: Found and root-caused while implementing
`TASK-00299`. Not fixed there — this is `vw_daemon_run()`'s own main-loop
architecture, unrelated to the update feature itself, and warrants its
own careful fix + test rather than a rushed change alongside an unrelated
task. Worked around in `TASK-00299`'s own test by pinning that test's
`sync_interval_ms` to 200ms — a test-only mitigation, not a fix for real
deployments still using the real (30s) default.

**CLI.02, 2026-09-16 — implementation**: Went with the acceptance
criteria's suggested approach — decoupled "how often do we check for
pending IPC connections" from "how long do we wait for a filesystem
event" — rather than changing what `sync_interval_ms` itself means.

Added `VW_DAEMON_MAX_WAIT_CHUNK_MS` (1000ms) in `vw_daemon.c`. Each main-
loop iteration now waits (or sleeps, in the no-watcher poll-only branch)
for at most that many ms, tracking how much of the configured
`sync_interval_ms` a run of these short chunks has covered in a new
`accumulated_wait_ms` local. Step (c) — accept/dispatch pending IPC
connections — runs after every chunk exactly as before, so it's now
reached at least once per second regardless of `sync_interval_ms`. Step
(d) — the actual per-account sync pass (`vw_sync_run`, real network
I/O) — only runs once `accumulated_wait_ms` reaches the full configured
interval, or immediately on a real watch event (`vw_watcher_wait`
returning `VW_OK` rather than `VW_ERR_TIMEOUT` — previously discarded,
now checked), a ring-buffer overflow, or an explicit `VW_IPC_SYNC_NOW_REQ`
(`sync_now`) — the same triggers that already caused an immediate sync
before this fix, just no longer tied to the wait's own timeout length.
When none of those fire, the iteration takes an early `continue` after
still calling `maybe_run_daily_auto_check()` (TASK-00298's daily
update-check gate — cheap, self-throttled to once/day internally, so
calling it every ~1s chunk instead of every full interval is a strict
correctness improvement, not a behavior change worth gating).

`sync_interval_ms == 0` (`vw_watcher_wait`'s own documented "block
indefinitely" sentinel) is preserved as "never trigger a sync pass from
elapsed time alone, only from a real event/overflow/sync-now" — the wait
itself is still chunked for IPC responsiveness, but the time-based
trigger is skipped entirely for that value, matching its documented
"indefinite" semantics rather than reinterpreting it as "poll every
second."

No change to the actual sync-pass cadence for any nonzero
`sync_interval_ms`: verified `test_ipc_update.c`'s own `sync_interval_ms
= 200` daemon (which pinned that value specifically to route around this
bug) still passes unmodified — its per-tick sync/IPC behavior is
identical because 200 < `VW_DAEMON_MAX_WAIT_CHUNK_MS`, so chunking is a
no-op at that interval.

New regression test `tests/integration/test_daemon_ipc_responsiveness.c`
(target `test_daemon_ipc_responsiveness`) spawns a real daemon with the
REAL production default `sync_interval_ms` (30000ms, deliberately left
unset in its `daemon.conf` rather than overridden down) and zero
configured accounts (zero watched roots — this task's exact incident
condition), then issues two plain `status` IPC round trips moments
apart and asserts each completes in under 5000ms (generous CI slack,
still decisively below the 30s worst case this fix bounds). Observed
locally: both round trips complete in ~1000-1002ms, bounded by
`VW_DAEMON_MAX_WAIT_CHUNK_MS` as designed.

Verified locally (WSL, gcc, `-DVW_WERROR=ON`): full test suite (36/36,
unit + integration, including the Python-driven multi-daemon
`tests/integration` suite) passes.

**CLI.02, 2026-09-16 — build validation**: Also verified against real
MSVC (`build-msvc-105`, native Windows) alongside TASK-00305 in the same
pass — `vw_daemon.c`'s changes compiled clean, and
`test_daemon_ipc_responsiveness`/`test_ipc_update` both pass natively
(status round trips completed in ~1000-1016ms against the real 30000ms
default, matching the WSL result).

**CQR.08, 2026-09-16 — code quality review**: No blocking findings.

- Reviewed the `run_sync_pass` gating: `got_watch_event || sync_now ||
  (interval > 0 && accumulated >= interval)` correctly preserves every
  pre-existing eager-sync trigger (real event, ring-buffer overflow,
  explicit `VW_IPC_SYNC_NOW_REQ`) while adding the new time-accumulation
  trigger, and the early-`continue` branch still calls
  `maybe_run_daily_auto_check()` so that self-throttled check's own
  cadence is unaffected either way.
- Confirmed `sync_now` was already effectively dead as a gate before
  this change (step (d) ran unconditionally every tick regardless of its
  value) — this fix is the first thing that makes it actually
  meaningful. Noting this as an observation, not a finding: making a
  previously-vestigial flag load-bearing is in scope for a task whose
  whole point is "decouple what triggers a sync pass," not scope creep.
- `sync_interval_ms == 0` handling: preserved as "wait is still chunked
  for IPC responsiveness, but never time-triggers a sync pass" — matches
  `vw_watcher_wait()`'s own documented "block indefinitely" sentinel
  without silently reinterpreting it as "poll every second," which would
  have been a real, if narrow, behavior change for anyone relying on
  that value. Confirmed no config path sets this in practice (default is
  `DEFAULT_SYNC_MS = 30000`; not treated as a real deployment case
  anywhere else in this codebase), so this is a defensive choice, not a
  gap.
- `chunk_ms` is provably never 0 in either branch (the `if` branch only
  taken when `accumulated_wait_ms < cfg->sync_interval_ms`, so
  `remaining >= 1`; the `else` branch always uses the 1000ms constant) —
  avoids any ambiguity with `vw_watcher_wait`'s own "0 = block
  indefinitely" sentinel leaking into the per-chunk call unintentionally.
- No new resource lifetime or thread-safety concerns — this is all
  single-threaded main-loop-local state (`accumulated_wait_ms`,
  `sync_now`, `got_watch_event`), same as the pre-existing `sync_now`.
