Add Android build validation to CI so the app doesn't silently bit-rot the
way the web gateway's build did before it was wired in (`VW_BUILD_WEB_GATEWAY`
still defaults `OFF` and isn't in `release.yml` — don't repeat that gap here
if avoidable).

Scope:
- New job/matrix leg in `.github/workflows/ci.yml`: set up JDK + Android
  SDK/NDK, run `./gradlew assembleDebug` (and unit tests if any exist by this
  point) for the `android/` project.
- Document required SDK/NDK/Gradle versions — either a new
  `docs/ANDROID_BUILD.md` or an addendum to `VENDOR_SETUP.md` (which today
  has no Node.js/npm prerequisite documented for the existing web frontend
  either — don't leave the same gap for Android).
- Pin exact NDK version consistent with the 16 KB page-size compliance
  requirement for new Play Store submissions (AGP ≥ 8.5.1, NDK ≥ r28 handle
  this automatically; verify whatever gets pinned actually clears that bar).

## Acceptance criteria

- CI fails if the Android app fails to build, the same way it already does
  for the Linux/Windows targets.
- Toolchain version requirements are documented somewhere a new contributor
  would actually find them.

## Notes

BLD.05, 2026-09-02: Added `build-android` to `.github/workflows/ci.yml`
(JDK 17 via `actions/setup-java`, then the specific SDK/build-tools/CMake/NDK
components via `sdkmanager` — GitHub's `ubuntu-latest` runner already ships
the cmdline-tools, no third-party marketplace action needed to bootstrap
it), running `./gradlew assembleDebug`. Documented the toolchain in a new
`docs/ANDROID_BUILD.md` (linked from `README.md`'s documentation map) rather
than folding it into `VENDOR_SETUP.md`, which is scoped to desktop/server
third-party *library* vendoring — a different kind of concern from Android's
JDK/SDK/NDK *toolchain* requirements.

**Real finding, acted on**: the project's Android app was scaffolded
(`TASK-225`) against NDK r27.2.12479018 — below the `NDK ≥ r28` bar this
task's own scope calls out for automatic 16 KB memory-page-size compliance
on new Play Store submissions. Bumped to `28.2.13676358` (r28b, the latest
stable release as of this writing; r29/r30 are still release-candidates).
Verified this wasn't just a version-string change: installed the new NDK,
did a clean rebuild (`rm -rf android/app/.cxx` first) of all three ABIs,
installed the resulting APK on the emulator, and confirmed a real
session-resume login still works — the native library the new NDK produced
is genuinely functional, not just "it compiled."

Confirmed via `actions/runner-images`' published `ubuntu-latest` (24.04)
manifest that `28.2.13676358` is one of the runner's pre-installed NDK
side-by-side versions (alongside r27.3 and r29.0), so this CI job's NDK
install step should resolve near-instantly rather than re-downloading it —
checked rather than assumed, same for confirming `Android Command Line
Tools | 12.0` (i.e. `sdkmanager`) is actually present on that image before
writing a job that depends on it.

`.github/workflows/ci.yml`'s YAML validated with `python -c "import yaml;
yaml.safe_load(...)"` — syntactically correct, though the job itself could
only be exercised for real once pushed (no way to run GitHub Actions
locally); the toolchain versions it installs were all independently
verified locally first, which is the part most likely to silently drift.

No blocking findings on self-review.
