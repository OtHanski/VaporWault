The client has never made an outbound connection to a non-VaporWault host.
`vw_net.c` forces ALPN `vw/1` and requires an explicit pinned CA cert — wrong
shape for talking to `github.com`. This is genuinely new attack surface;
SEC.07 review is mandatory.

New files `src/client/vw_update_net.c`/`.h`, cross-platform (Linux + Windows,
no POSIX-only shortcuts — unlike `vw_acme.c`, which is server-only/POSIX-only
and not reusable here).

## API

```c
typedef struct {
    uint8_t *body;
    size_t   body_len;
    size_t   body_cap;
} vw_update_response_t;

vw_err_t vw_update_https_get(const char *host, const char *path,
                              size_t max_body_bytes,
                              vw_update_response_t *out);
void vw_update_response_free(vw_update_response_t *r);
```

- Fresh mbedTLS TLS 1.3 connection to `host:443`.
- Certificate verification against the **real OS trust store**, not a pinned
  PEM (GitHub's chain isn't ours to pin):
  - Linux: probe, in order, `/etc/ssl/certs/ca-certificates.crt`,
    `/etc/pki/tls/certs/ca-bundle.crt`, `/etc/ssl/cert.pem`; load the first
    that exists via `mbedtls_x509_crt_parse_file`.
  - Windows: `CertOpenStore(CERT_STORE_PROV_SYSTEM, ..., L"ROOT")` +
    `CertEnumCertificatesInStore`, feeding each enumerated DER cert into an
    `mbedtls_x509_crt` chain built at runtime, used as this connection's
    `ca_chain`. Do **not** bundle a fixed pinned root list — GitHub's
    Fastly-fronted CDN can rotate roots/intermediates over the keypair's
    lifetime, and a hardcoded set would silently bit-rot.
- Minimal HTTP/1.1: bare `GET <path> HTTP/1.1\r\nHost: <host>\r\nConnection:
  close\r\n\r\n`; parse status line + headers; require `Content-Length`
  present; **reject chunked encoding outright** (not needed — GitHub's
  asset/manifest responses are always `Content-Length`-framed); enforce
  `body_len <= max_body_bytes` (caller passes a small cap for the manifest,
  larger-but-bounded for asset downloads — streamed to a temp file for the
  asset case rather than buffered in memory, see `TASK-00298`).
- Follow **at most one** `301`/`302`/`307`/`308` redirect (GitHub's `latest`
  alias 302s to a versioned URL); a second redirect is a hard failure — bounds
  redirect-loop/SSRF-shaped risk.
- Timeouts on connect/read (do not hang the daemon indefinitely on a stalled
  or malicious peer).

This module must be the **only** place in the client that connects to a
non-pinned, non-VaporWault-server TLS endpoint — add a code comment saying so
for future auditors.

## Acceptance criteria

- Unit/integration tests against a local test HTTPS server: happy path,
  oversized `Content-Length` rejected, chunked encoding rejected, two
  redirects rejected, malformed status line/headers rejected without crash,

- Real fetch against `https://github.com/OtHanski/VaporWault/releases/latest/download/`

- SEC.07 review of the new attack surface (parsing untrusted HTTP responses

### Design change: reused `vw_net.c` instead of a standalone TLS stack

Rather than building a second, wholly separate TLS/socket implementation
in `vw_update_net.c` as originally sketched, extended `src/core/vw_net.c`
(the project's one existing TLS abstraction) with:
- A new `VW_CERT_VERIFY_SYSTEM_STORE` cert-verify mode.
- A new `vw_net_connect_generic()` entry point — like `vw_net_connect()`
  but with no forced ALPN and support for the new verify mode.

`vw_update_net.c` is a thin HTTP/1.1-GET-only layer on top of this,
reusing `vw_net.c`'s already-audited connect/timeout/BIO/send/recv
machinery instead of duplicating it. Every VaporWault-protocol connection
(`vw_net_connect`/`_cluster`) is completely unchanged — this only adds a
new, additive code path.

### Real bug #1: Windows never called `WSAStartup` on the non-blocking connect path

`connect_with_timeout()`'s custom non-blocking branch (taken whenever
`opts->connect_timeout_ms != 0`, which `vw_update_net.c` is the *first*
caller in this codebase to ever do) talks to raw Winsock directly and
never called `WSAStartup`, unlike `mbedtls_net_connect()` (the
`timeout_ms==0` path every existing caller takes, which calls it
internally via `net_prepare()`). Every existing production call site
passes `conn_opts=NULL` (timeout 0), so this was a real, latent gap that
never manifested until now — reproduced live as a DNS-resolution failure
in a from-scratch process (a fresh daemon with `update_policy=auto` and
zero configured accounts, per `TASK-00298`'s design, can legitimately make
this the very first network call the process ever makes). Fixed with a
one-time `InitOnceExecuteOnce`-guarded `WSAStartup()` call inside
`connect_with_timeout` itself (same pattern already used for
`now_ns()`'s `QueryPerformanceFrequency` init in this file) — fixes the
gap for any future caller of this path, not just this one.

### Real bug #2: `opts->recv_timeout_ms` is silently discarded post-handshake

`net_connect_impl()` deliberately resets a connection's recv timeout to 0
(unlimited) once the TLS handshake completes (`ARCHITECTURE.md`'s
"vw_net recv timeout" row) — every other caller in this codebase already
knows to re-arm it via `vw_net_conn_set_recv_timeout()` post-connect
(`vw_server_core.c`, `vw_cluster.c`, `vw_server_main.c`). `vw_update_net.c`
didn't do this at first, causing a real (not simulated) indefinite hang
against a server that accepts a connection and never responds — caught
by `TASK-00296`'s own test suite, not assumed away. Fixed by calling
`vw_net_conn_set_recv_timeout()` right after connecting, matching every
other real caller's pattern; documented why `opts.recv_timeout_ms` itself
is deliberately left unset in `vw_update_net.c` (it would be dead code —
`net_connect_impl` ignores it for the handshake and discards it after).

### Windows system-trust-store verification: two implementation attempts

The design brief's original sketch (`CertOpenStore` + `CertEnumCertificatesInStore`,
parsing every enumerated cert into one `mbedtls_x509_crt` chain via
`mbedtls_x509_crt_parse_der`, then `mbedtls_ssl_conf_ca_chain`) was
implemented first and empirically **failed** against a real connection:
the Windows `ROOT` store holds a large, heterogeneous set of CAs
accumulated over the OS's lifetime, and mbedTLS's own certificate-chain
verification walk hard-aborted the *entire* handshake — not just skipped
one bad anchor — reproduced live as
`MBEDTLS_ERR_X509_INVALID_ALG`/`MBEDTLS_ERR_OID_NOT_FOUND` against a real
`github.com` connection.

Replaced with Windows' own native chain-verification engine
(`CertGetCertificateChain` + `CertVerifyCertificateChainPolicy`,
`CERT_CHAIN_POLICY_SSL`) via a custom `mbedtls_ssl_conf_verify()` callback
(`win32_verify_cert_cb`, `vw_net.c`) — the same class of approach other
cross-platform tools use to validate TLS peers against the OS store on
Windows rather than fighting a foreign X.509 stack. Two further findings
while getting this working, both confirmed via a real live connection, not
assumed:
- mbedTLS's TLS 1.3 client code hard-requires *some* `ca_chain` object to
  exist when `authmode == REQUIRED`, even with a verify callback
  registered (fails outright with "No CA Chain is set, but required to
  operate" otherwise). Fixed by loading a fixed, VaporWault-internal,
  non-CA placeholder self-signed cert (`VW_NET_PLACEHOLDER_CA_PEM`) purely
  to satisfy that structural requirement — it can never match a real
  peer's chain, so it grants no trust by itself; `win32_verify_cert_cb`
  unconditionally **overwrites** (not ORs into) `*flags` based on
  Windows' own verdict, so the placeholder's own non-match is irrelevant
  to the actual trust decision.
- Deliberately configured `CertGetCertificateChain` with **no online
  revocation checking** (`dwFlags = 0`, not
  `CERT_CHAIN_REVOCATION_CHECK_*`) — a flaky/unreachable OCSP responder
  must never fail a background update check outright; the manifest's own
  ECDSA signature (`TASK-00293`/`00297`) is the real trust boundary for
  what gets installed, TLS here is defense-in-depth, so this residual risk
  is accepted deliberately, not overlooked.

### Real bug #3 (found during the above, root-caused, not worked around): `MBEDTLS_SHA384_C` was never enabled

After fixing both of the above, `github.com` *specifically* still failed
with the same `X509_INVALID_ALG`/`OID_NOT_FOUND` error while
`objects.githubusercontent.com` (the actual redirect target for a real
release download) worked cleanly. Root-caused via a one-time
`MBEDTLS_DEBUG_C` diagnostic rebuild (reverted after use — not left
enabled): `github.com`'s server sends its real 3-certificate chain (leaf
signed ECDSA/SHA-256, intermediate + root signed ECDSA/SHA-384, confirmed
independently via `openssl s_client -showcerts`), and mbedTLS's parser
correctly parses the leaf but then fails to even parse the SHA-384-signed
intermediate — this project's `third_party/mbedtls_config.h` enables
`MBEDTLS_SHA512_C` but not the **separate** `MBEDTLS_SHA384_C` flag this
mbedTLS version (3.6.x) requires for SHA-384 support (they share the same
underlying compression function but are distinct opt-ins; the existing
comment on `MBEDTLS_SHA512_C` already claimed "used in certificate chains
with SHA-384 signatures" — true intent, but the config predates this
version's flag split and was never updated). Confirmed via a targeted
preprocessor check
(`#ifdef PSA_WANT_ECC_SECP_R1_384` → yes, `#ifdef MBEDTLS_MD_CAN_SHA384` →
no) before touching anything, not guessed. Fixed by adding
`#define MBEDTLS_SHA384_C` — a narrow, well-understood, low-risk addition
(SHA-384 is a completely standard, uncontroversial algorithm; enabling it
only adds capability). **This is a real capability gap that would have
affected any future use of this codebase against SHA-384-signed
certificates, not just this feature** — flagging for SEC.07/CQR.08 as
independently worth noting in review, beyond this task's own scope.

**SEC.07 + CQR.08, 2026-09-16**: Full adversarial read, part of a
full-milestone pass across `TASK-00292`–`TASK-00298`. `fetch_once`'s many
early-return paths were traced individually — every one closes `conn`
and frees `body` where allocated, no leaks found. The Windows cert-chain
verification callback (`win32_verify_cert_cb`) correctly performs real
hostname verification via `CertVerifyCertificateChainPolicy`'s
`pwszServerName`, and unconditionally overwrites (not ORs) `*flags` with
its own verdict — the placeholder CA cannot itself grant trust. No bypass
found on either platform's verify path.

Two advisory findings, both fixed:
- **`parse_response_head`'s Content-Length parsing used `atol`** on a
  caller-controlled numeric string — `atol`'s behavior on an out-of-range
  value is undefined per the C standard (bounded in practice by the
  subsequent `max_body_bytes` check, but still UB). Fixed: replaced with
  `strtol` + explicit `errno == ERANGE` / trailing-garbage / negative
  checks (`vw_update_net.c`).
- **Redirect-following had no host allowlist** — validated `https://` and
  TLS-verified the target's own identity, but a compromised/malicious
  response could redirect the fetch to an arbitrary HTTPS host. Fixed:
  added `host_is_allowed_redirect_target()`, restricting a followed
  redirect to `github.com`/`githubusercontent.com` (exact match or `.`
  + suffix subdomain, never a bare suffix match) — overridable via
  `VW_UPDATE_REDIRECT_ALLOWED_SUFFIX_1`/`_2` (same convention as
  `VW_UPDATE_GITHUB_HOST`) so `test_update_net.c` can prove the mechanism
  itself works against its own local test server rather than disabling
  it. New `test_update_net.c` TC-8 proves a redirect to a disallowed host
  is rejected before any connection attempt to it.

Both fixes verified: full test suite (30/30 on `build-msvc-105`, 33/33 on
WSL `build-wsl-werror`) passes clean, including the new TC-8 case.
`status: done`.
