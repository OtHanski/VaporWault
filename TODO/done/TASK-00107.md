Discovered while starting `TASK-00096` (Sharing UI): the GUI client's login
view (`src/gui/client/views/vw_view_login.cpp`) is a stub that tells the
user to run `vapourwault-cli login` instead — "Credential management is not
yet available in the GUI." `VwGuiIpc` has no `login()` method at all,
despite the daemon-side `VW_IPC_LOGIN_REQ`/`VW_IPC_LOGIN_RESP` handler
already existing and working (`vapourwault-cli login` uses it today).

`TASK-00096`'s acceptance criteria require "all flows work against a real
client + server (manual test, not just compiles)" — meaningless if the user
can never actually reach a logged-in state through the GUI itself.

## Acceptance criteria

- `VwGuiIpc` gains a `login(password, otp)` method mirroring
  `vw_client_cli.c`'s `cmd_login` (same `VW_IPC_LOGIN_REQ`/`_RESP`
  exchange); zeroes the payload buffer after sending, matching this
  codebase's existing raw-password-handling convention.
- `vw_view_login_render` gains real password/OTP input fields (password
  masked) and a Login button; displays the specific error (bad password,
  locked out, 2FA required — prompting for the OTP field) rather than a
  generic failure message.
- On success, no explicit view-transition code is needed —
  `ClientApp::render_frame` already switches to `Browser` once the next
  daemon status poll reports `connected == true`.
- Manually verified against a real running daemon + server (not just a
  compile check).

**Significant bug found and fixed while implementing this (affects every
pre-existing `VwGuiIpc` method, not just the new one):** `VwGuiIpc` held
one persistent `vw_ipc_conn_t*` reused across calls, but the daemon closes
every IPC connection after handling exactly one request
(`handle_ipc_client`'s caller in `vw_daemon.c` calls `vw_ipc_conn_close()`
immediately after each dispatch — matching how `vapourwault-cli` opens a
fresh connection per subcommand). This "worked" for the existing
2-second status-poll loop only by accident: every *other* poll would fail
(send on an already-half-closed socket), trigger `disconnect()`, and the
*following* poll would transparently reconnect and succeed — invisible
when the only thing ever called repeatedly was the same single method, but
it broke outright for any back-to-back sequence of *different* calls
(discovered via a standalone diagnostic harness: `login()` succeeded, but
the very next `file_list()` call on the same connection failed
immediately). Since `TASK-00096`'s sharing dialogs need exactly that
pattern (e.g. `share_grant()` then re-fetch `share_list()`), this had to
be fixed at the root rather than patched around. Redesigned `VwGuiIpc` so
every method opens its own short-lived connection via a new internal
`one_shot()` helper instead of sharing one persistent socket;
`connect()`/`is_connected()`'s public meaning is preserved (a reachability
probe / flag) but no longer holds an open socket between calls.

**Validation:** wrote a standalone diagnostic (`gui_ipc_check.cpp`, linked
directly against `vw_gui_ipc.cpp` + `vw_ipc.c` + the prebuilt
`libvw_core.a`, not committed — scratch verification only) against a real
running daemon + server: `login()` succeeds and zeroes the password buffer,
followed immediately by `file_list()`, `fetch_status()`, and a second
`file_list()` — all succeed on the same `VwGuiIpc` object, proving the
one-shot fix. Also launched the real `vapourwault-gui` binary under WSLg
and confirmed it starts and stays alive (no crash, empty stderr) for 5s
against a live daemon.
