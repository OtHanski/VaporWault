`TASK-00258`'s own closing notes disclosed a real race, discussed with
the user afterward: a chunk was assigned its parity-group slot at
**upload** time (`vw_storage_chunk_put`'s "truly new chunk" path), while
real client uploads legitimately sit at `ref_count == 0` until
`FILE_COMMIT`'s `vw_storage_chunk_addref` (`TASK-180`'s design). If a
client abandoned an upload before committing, `vw_storage_gc_run`'s
Phase A (which deletes any `ref_count == 0` chunk, by design) could
delete that chunk while its parity group was still open. When the group
later tried to seal, `seal_group`'s read of that member's now-gone file
would fail — permanently, since the same failure repeats on every future
`vw_storage_open` recovery attempt too.

User chose the fix that avoids new coupling between `vw_gc.c` and
`vw_storage.c`'s parity internals (the alternative — gating GC's Phase A
on parity-group state, mirroring `TASK-171`'s replica-safety gate — was
offered and declined as more machinery for a narrower problem).

## Fix

- `register_parity_member` is now self-guarding: a no-op if the hash
  already has a membership (checked via `pg_ht_find`), so every call site
  can call it unconditionally.
- `vw_storage_chunk_addref`: registers the caller's hash the first time it
  gets a genuine, permanent reference (i.e. essentially every call, since
  the self-guard makes a dedup hit's re-addref a no-op) — this is now the
  only registration point for real client uploads. The chunk's length is
  looked up via `vw_fs_file_size` (a cheap stat, not a full read),
  best-effort — a stat failure just means no parity coverage for that
  hash, it does not fail the addref.
- `chunk_put_impl`'s "truly new chunk" path still registers, but now only
  for the **replicated** write path (`establish_own_ref`, i.e.
  `vw_storage_chunk_put_replicated`) — a replica has no `FILE_COMMIT`/
  addref call of its own, and a replicated write always establishes
  `ref_count >= 1` immediately at write time, so there's no
  abandoned-pre-commit window for it and registering at write time is
  correct (and the only place it can happen) for that path.

## Residual risk (accepted, disclosed — not eliminated by this fix)

A real client upload can still be committed, then have its version
deleted again (`decref` back to `ref_count == 0`), all while its parity
group is still open. If `vw_storage_gc_run` sweeps it before the group's
remaining slots fill, the same permanent-seal-failure recurs. This window
is far narrower than the original one (requires an explicit delete of
just-created content, not merely an abandoned upload) and is accepted
rather than fixed — the full fix (gating GC on parity-group state) was
the alternative the user declined above.

## Acceptance criteria

- `vw_storage_chunk_put` (real-upload path) no longer assigns a
  parity-group slot by itself.
- `vw_storage_chunk_addref` assigns the slot on first real reference,
  self-guarded against double-registration on subsequent dedup addrefs.
- `vw_storage_chunk_put_replicated` still registers at write time
  (unchanged behavior for the replication path).
- Existing `test_vw_storage_parity.c` updated to call
  `vw_storage_chunk_addref` after each `vw_storage_chunk_put` (matching
  the real `FILE_COMMIT` flow) and still passes, including the
  dedup-hit-doesn't-double-register case now exercised via a second
  `addref` against an already-registered hash rather than a second `put`.
- Full existing test suite (unit + integration) still passes with no
  regressions — `vw_storage_chunk_addref` is on the real `FILE_COMMIT`
  path, exercised by the entire existing upload/commit integration
  coverage, not just this feature's own tests.
