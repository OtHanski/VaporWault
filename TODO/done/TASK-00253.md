User asked whether VaporWault can detect and correct file/chunk corruption,
ideally checking replicas for a clean copy when local corruption is too
severe to fix in place. Investigation found: no detection exists at all
(`vw_storage_chunk_get`/`handle_chunk_download` never re-hash on read; no
scrub job), cluster replication (`vw_cluster.c`) is a fixed-direction pull
with no reverse path for a primary to fetch a clean chunk from a replica,
and the existing filesystem-level backup (`docs/DEPLOYMENT.md` §7) has no
per-chunk granularity.

User decision (via clarifying questions): pursue local erasure coding
(Reed-Solomon) and replica-based repair, on top of a detection baseline
both depend on.

## Design

Recorded in `ARCHITECTURE.md`'s Architectural Decisions table and a new
Phase 22 row: data layout (`parity_groups.db`, tombstone-vs-corruption
handling via `refcounts.db`), the new `CLUSTER_CHUNK_REPAIR_FETCH`/`_DATA`
protocol messages (0x0710/0x0711), and repair ordering (local RS
reconstruct first, replica-fetch fallback, unrepairable alert last).
