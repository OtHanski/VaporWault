`TASK-00255`'s scrub currently only detects and logs corrupt chunks.
`TASK-00258` (local Reed-Solomon) and `TASK-00259` (cluster repair-fetch)
give two independent repair mechanisms. Wire them together into the
actual repair ordering from the Phase 22 design: local reconstruction
first (cheap, no network), replica-fetch fallback second, give up and
alert third (`TASK-00261`).

## Design (from TASK-00253)

When `vw_storage_scrub_run`'s callback fires for a chunk with
`ref_count > 0`:

1. Try local Reed-Solomon reconstruction from its parity group
   (`vw_ecc`) — verify the reconstructed bytes hash-match before writing
   back to disk.
2. If the group has too many simultaneous faults for RS to resolve, ask
   each active replica in turn (`TASK-00259`'s primary-side caller) until
   one returns hash-verified bytes; write those back to disk.
3. If neither succeeds, do not serve or silently drop the chunk — hand off
   to `TASK-00261`'s alert category instead of failing silently.

Also apply the same ordering to the `handle_chunk_download` chokepoint
(`TASK-00254`): a client hitting a corrupted chunk synchronously should
trigger the same repair attempt before falling back to
`VW_ERR_CHUNK_CORRUPT`, not just log-and-reject.

## Acceptance criteria

- Scrub's corrupt-chunk callback drives the repair pipeline instead of
  only logging.
- `handle_chunk_download`'s corruption path attempts repair before giving
  up.
- Successful repair writes the corrected bytes back to the chunk store
  (through the same atomic-write path `vw_storage_chunk_put` already uses,
  not a new write primitive).
- Integration test: corrupt a chunk with an intact parity group → confirm
  local reconstruction repairs it with no network involved; corrupt two
  chunks in the same parity group (exceeding single-fault redundancy) with
  a live replica available → confirm replica-fetch repairs it instead.

## Notes

SRV.01 (2026-09-09): implemented as designed, plus one new piece the
design didn't call out explicitly: a new `src/server/vw_repair.c`/`.h`
module (`vw_repair_chunk(chunks, cluster, hash)`) is the actual
orchestration layer — neither `vw_storage.c` nor `vw_cluster.c` reference
each other directly (vw_storage stays cluster-agnostic, matching its
existing design), so something above both was needed. Two new
`vw_storage` primitives back it: `vw_storage_repair_local` (read-only —
gathers a parity group's other members via the existing
`vw_storage_parity_*` API, calls `vw_ecc_decode_single`, verifies the
result against the requested hash before returning it) and
`vw_storage_chunk_repair_write` (verifies + atomically overwrites an
already-referenced chunk's bytes, touching no ref-count/quota/parity
accounting — repair only ever corrects bytes, never creates or
re-accounts a chunk).

Wired into both required chokepoints: `vw_scrub`'s corrupt-chunk callback
(`vw_scrub_create` gained an optional `cluster` parameter) now calls
`vw_repair_chunk` and logs the outcome instead of only logging detection;
`handle_chunk_download` (`vw_file_handlers.c`) does the same inline
before falling back to `VW_ERR_CHUNK_CORRUPT`, re-fetching and
re-verifying the repaired bytes before ever serving them (never trusts
a repair result blindly).

**Real bug found and fixed while writing this task's own integration
test, not by inspection**: `vw_cluster_repair_fetch` (`TASK-259`) never
cleared `repair_slots[i].result_data` after transferring ownership out to
a successful caller (or freeing it on failure) — the stale pointer stayed
in the slot struct even after the slot was reset to `FREE` and reused.
`vw_cluster_close`'s defensive shutdown cleanup then unconditionally
freed every slot's `result_data` again, a real double-free that crashed
the process on shutdown any time a repair-fetch had actually completed
during the run. Never caught by `TASK-259`'s own test (which never
exercises a *successful* fetch followed by teardown from the same run in
quite the right sequence) — only surfaced once `test_repair_pipeline.c`
ran a real successful replica-fetch (TC-2) and then hit process exit.
Fixed by nulling `slot->result_data` immediately after either disposal
path. `TASK-259`'s own notes/task file are not amended (per the
protocol's "never delete/rewrite" rule) — recorded here instead, at the
task that actually found it.

New `tests/integration/test_repair_pipeline.c` (41 assertions, real
primary+replica pair, `VW_ECC_MAX_DATA_SHARDS=4` for speed): single
corruption in an intact group repairs locally with no cluster call at
all; a second simultaneous corruption (exceeding local redundancy) with
the replica holding a clean copy of one falls through to replica-fetch
and repairs from there; a corruption with neither local redundancy nor
any replica coverage returns `VW_ERR_NOT_FOUND` cleanly (chunk still
corrupt on disk, not served, no crash). Full suite: 25/25 `ctest`
(including the whole pre-existing Python integration collection and both
prior cluster C-tests) on Linux/WSL `-Wall -Wextra -Wpedantic -Werror`,
plus a clean MSVC compile+link of both the new test and `vapourwaultd`
(the sandboxed-Windows firewall limitation already disclosed for
`test_cluster_repair_fetch.c` applies identically here — not re-verified
at runtime on MSVC for the same documented reason).

CQR.08 (2026-09-09): reviewed `vw_storage_repair_local`'s buffer
lifecycle (per-sibling `calloc`'d buffers, `parity`, `reconstructed`, the
trimmed output) for the same class of leak/double-free risk the
`vw_cluster_repair_fetch` bug above turned out to have — all paths
(early `break` on OOM, decode failure, hash-mismatch-after-decode)
free correctly exactly once via the unconditional cleanup loop at the
end. `vw_repair_chunk`'s replica-iteration loop frees `nodes` on every
exit path. No further blocking findings.
