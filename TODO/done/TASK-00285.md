Implements `TASK-00284`'s design (`docs/PROTOCOL.md` §7.7 revision 34,
new `client_conn_count` on `OPLOG_ACK`/`CLUSTER_STATUS_RESP`). Surface
real per-replica fallback-client counts in the admin CLI/GUI
(`vw_admin.c`, `src/gui/server/views/vw_view_dashboard.cpp` and/or
`vw_view_cluster.cpp` — implementer's call on which is the better fit),
replacing today's approximate `replica_lag`-only signal.

## Acceptance criteria

- `vw_cluster_open()` gains the new borrowed `vw_conn_registry_t
  *conn_registry` parameter `TASK-00284`'s design specifies; thread it
  through from `vw_server_main.c` (registry already opens before
  `vw_cluster_open` is called — no init-ordering change needed).
- Replica side: `OPLOG_ACK`'s send site reads `vw_conn_registry_list`'s
  live count and includes it. Primary side: stores each node's most
  recently received `client_conn_count` for `CLUSTER_STATUS_RESP` to
  report.
- Admin-visible per-replica client count (a count, not an account list —
  the design doesn't identify *which* accounts, only how many
  connections a given replica currently has), sourced from this real
  data, not inferred heuristically.
- No unilateral reinterpretation of `TASK-00284`'s published spec — flag
  ARCH.00/PRT.04 if implementation surfaces a gap in the design rather
  than deciding it locally.

**Server-side plumbing**: `vw_cluster_open()` gained the designed
`vw_conn_registry_t *conn_registry` (borrowed, may be NULL) parameter,
threaded through from `vw_server_main.c` (registry already opens first —
no init-ordering change, as the design predicted). `struct vw_cluster_ctx`
gained an in-memory-only `client_conn_counts` array, dense-indexed by
`node_id` in lockstep with the existing `nid_to_slot` (same pattern
`vw_vault.c`'s `pin_counts` uses alongside `vid_to_slot`, `TASK-00290`) —
grown/freed together everywhere, never independently. New public getter
`vw_cluster_node_client_conn_count`. Replica-side `OPLOG_ACK` send site
now appends its live `vw_conn_registry_list` count; primary-side receive
accepts the now-optional 12-byte length (`plen >= 8`, defaulting the
trailing field to 0 for a pre-upgrade replica sending the old 8 bytes)
and stores it per-node under the existing `nodes_lock`.

**Two admin-visible surfaces**, not just one — the acceptance criteria
left the choice open, and both turned out to matter for different
reasons:
- The client-facing `CLUSTER_STATUS_RESP` (`vw_file_handlers.c`,
  `docs/PROTOCOL.md`'s actual documented wire message) — consumed by the
  desktop server GUI's cluster view, which now has a "Fallback Clients"
  column. Entry size 154→158 bytes.
- The separate admin-socket `VW_ADMIN_CLUSTER_STATUS_RESP`
  (`vw_admin.c`) — a *different*, previously-undocumented-in-`docs/
  PROTOCOL.md` wire shape that `vapourwault-server-cli cluster status`
  and this project's own existing cluster integration tests
  (`tests/integration/test_cluster.py`'s `_cluster_status` helper)
  actually go through, discovered only by checking how pairing is
  already tested before assuming the client-facing path alone was
  enough. Extended the same way (entry size 148→152 bytes, new
  `FALLBACK_CLIENTS` CLI column) so the real, already-used admin
  tooling gets this too, not just the GUI.

**Found and fixed, not just documented, a real gap in `TASK-00284`'s own
published design** (flagging per this task's own instruction, then
fixing rather than leaving it broken, since the fix needed no wire
format change): the pre-existing `OPLOG_ACK` exchange skipped itself
entirely whenever a poll found nothing new to sync (`entries_count == 0`
on the primary, mirrored by the replica) — sensible before this field
existed (nothing new to acknowledge either way), but it silently
defeats `client_conn_count`'s own documented "bounded by the poll
interval" staleness claim for exactly the steady-state case the whole
feature exists to catch: a client quietly parked on a fallback replica
while the primary sees no other write activity. Fixed by having both
sides always exchange `OPLOG_ACK` every poll cycle (re-acknowledging an
unchanged watermark on an empty batch) — `OPLOG_ACK`'s byte layout is
untouched, only the decision of *when* to send/await it changed.
Factored the replica's ack-building code into a shared
`replica_send_oplog_ack` helper used at both the empty- and
real-batch call sites rather than duplicating it.

**How the gap was actually found**: not by inspection — a real
end-to-end test (`test_cluster_status_reports_live_fallback_client_
count`, `tests/integration/test_cluster.py`) that connects a real,
persistent client straight to a paired replica and asserts the
primary's `cluster status` shows the count go 0 → 1 → 0 across
connect/disconnect failed on its first run (`fallback_clients never
reached 1`) against the *design-faithful* implementation, before the
ack-cadence fix above existed. That failure is what surfaced the gap;
fixing it, then rerunning, is what confirmed the fix actually closes it
rather than papering over the specific test scenario.

**Also fixed while in the same code** (small, adjacent, not part of
this task's scope but directly in the block being changed): the
client-facing `CLUSTER_STATUS_RESP` doc comment above `handle_cluster_
status` and `docs/PROTOCOL.md`'s own per-node entry table both predate
this task and were already wrong before it — neither mentioned the
`role` byte the implementation has always sent, and the protocol doc
described `hostname` as a length-prefixed string when it has always
been fixed-size and NUL-padded. Corrected both to match the real,
already-shipped wire format while extending the same table for
`client_conn_count`, rather than leaving one new field correctly
documented next to two pre-existing wrong ones.
