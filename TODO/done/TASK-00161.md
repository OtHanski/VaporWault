Foundation task for `TASK-00160`'s multi-account design. Today
`vapourwault-daemon` (`src/client/vw_daemon.c`) holds exactly one
`vw_client_sess_t` (`dc->sess`), one `vw_cache_t` (`dc->cache`, opened once
against the daemon's single `state_dir`), and one global
`daemon_vault_registry_t`. This task makes it multi-account.

## State layout

Repurpose `state_dir` as a daemon-global root. New layout:

```
{state_dir}/daemon.conf          (global: ipc_port, sync_interval_ms — unchanged fields, minus username/server_host/server_port/ca_cert_pem_path which move per-account)
{state_dir}/daemon.log
{state_dir}/daemon.pid
{state_dir}/accounts/<account_id>/
    account.conf                 (label, server_host, server_port, ca_cert_pem_path, username)
    cache.db
    sync_folders.db
    session.tok
```

`account_id` is a daemon-assigned monotonic `u32` (not user-chosen), stored
in `account.conf` and stable for the account's lifetime (used thereafter on
every account-scoped IPC call instead of repeating the label).

Reuse `vw_cache_open()`, `tok_load`/`tok_save`, and `try_connect()`
unchanged — call each once per `accounts/<account_id>/` subtree instead of
once globally.

## In-memory model

Replace `dc->sess`/`dc->cache`/the global `vault_registry` with:

```c
typedef struct {
    uint32_t account_id;
    char     label[64];
    vw_client_sess_t *sess;      /* NULL if currently offline/unauthenticated */
    vw_cache_t       *cache;
    vw_sync_ctx_t    *sync_ctx;
    daemon_vault_registry_t vaults;
} vw_account_ctx_t;
```

held in a small dynamic array on the daemon context, populated at startup by
scanning `accounts/`, and mutable at runtime via the new `ACCOUNT_ADD`/
`ACCOUNT_REMOVE` IPC calls below.

## Sync loop

Keep the daemon single-threaded (no new locking/threading in `vw_sync.c`/
`vw_cache.c` — each `vw_cache_t`/`vw_sync_ctx_t` instance is already
independent per account, so round-robin needs no shared-state protection).
Each tick iterates every account context and runs one sync cycle for it,
instead of one global cycle. This is what makes "every logged-in account
keeps syncing regardless of which is displayed" true — the actual
requirement — without OS-thread-level parallelism.

## IPC (`src/client/vw_ipc.h`)

New messages:

- `VW_IPC_ACCOUNT_LIST_REQ` / `_RESP`: list configured accounts
  (`account_id`, `label`, `username`, `server_host`, connected bool, pending
  upload/download counts).
- `VW_IPC_ACCOUNT_ADD_REQ` / `_RESP`: `label`, `server_host`, `server_port`,
  `ca_cert_pem_path`, `username`, `password`, `otp` → creates a new
  `accounts/<account_id>/` subtree, authenticates via `vw_client_connect`,
  persists the resumable token, adds a live `vw_account_ctx_t`. `_RESP`
  returns the assigned `account_id`.
- `VW_IPC_ACCOUNT_REMOVE_REQ` / `_RESP`: `account_id` → `vw_client_logout`s
  that account's session, deletes its `accounts/<account_id>/` subtree
  (session token + cache — matches today's single-account logout deleting
  nothing else, but the account is fully gone afterward, not just logged
  out). Already-synced local files are untouched (this only removes daemon
  bookkeeping, never touches the synced folders on disk).

Every existing per-file/vault/share/folder request (`FILE_LIST_REQ`,
`FOLDER_ADD_REQ`, `VAULT_UPLOAD_REQ`, etc.) gains a leading `u32 account_id`
field, validated against the live account-context array before dispatch
(`VW_ERR_INVALID_ARG` if unknown, `VW_ERR_AUTH_REQUIRED` if that account's
`sess == NULL`). This is internal IPC (both ends ship from the same build),
so no version-negotiation concern — same reasoning already used for every
prior `vw_ipc.h` addition.

## Security note (`security-sensitive`)

`ARCHITECTURE.md`'s Risks table already flags the daemon's single
`session.tok` file as having no real Windows ACL/OS-keychain protection.
This task turns 1 such file into N (one per account) — the existing
`tok_save`/`tok_load` (POSIX `0600` via `open()` flags; no explicit ACL on
Windows) are reused unchanged, so this multiplies the pre-existing gap
without fixing it. **Deliberately not fixed here**: `TASK-00165` (gateway
remember-me) hits the identical gap for its own new on-disk store, and
`ARCHITECTURE.md`'s risk-table entry already calls for closing it once,
for both the daemon's per-account tokens and the gateway's store together,
rather than twice. SEC.07 sign-off for *this* task covers the multi-account
IPC surface itself (account isolation, `ACCOUNT_REMOVE_REQ` cleanup,
resume-rotation correctness per account) — real ACL hardening is
`TASK-00165`'s acceptance criterion, not re-stated as a blocking requirement
here to avoid two tasks both claiming (and neither actually owning) it.

## Acceptance criteria

- Two accounts configured against two different real test-server users on
  one daemon instance both keep syncing (file changes on either account's
  server side get pulled locally) while only one is being queried via
  `ACCOUNT_LIST_REQ`/file-list IPC calls — i.e. syncing is not gated on
  which account a GUI/CLI happens to be looking at right now.
- `ACCOUNT_ADD_REQ`/`_REMOVE_REQ` round-trip correctly; removing an account
  stops its sync cycle and its `accounts/<id>/` subtree is gone, but files
  already synced to the local filesystem remain untouched.
- Real per-account isolation: neither account's `vw_client_sess_t`/cache
  can observe or affect the other's data, even though both run in the same
  process — verified with a real two-user integration test, not just code
  inspection (file permission *hardening* itself is `TASK-00165`'s
  criterion, per the security note above).
- Full `ctest` green on both `build-msvc-105` and `build-gw-e2e`; a new
  integration test covers the round-robin scheduling (each account context
  gets a sync-cycle call independent of the others' state, including while
  only one account is being queried).
