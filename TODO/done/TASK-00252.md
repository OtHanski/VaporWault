Found while re-verifying `TASK-00152`'s item 5 ("uninstall actually removes
it") after `TASK-00247`–`251` closed — this specific half of item 5 had never
actually been tested end-to-end (`TASK-250`'s own verification only exercised
registration, via a bare copy of the daemon with no MSI involved at all).

`UNREGISTERCLIENTTASK`'s deferred custom action calls
`register-client-task.ps1 -Uninstall`, which calls `Unregister-ScheduledTask`.
This hits the *exact same* Windows session-boundary limitation `TASK-250`
diagnosed for `Register-ScheduledTask` — the underlying Task Scheduler COM API
needs a real interactive logon session, which an MSI deferred custom action
never has, regardless of impersonation. Confirmed for real: manually
registered `VaporWaultDaemon` (simulating what the daemon's self-registration
from `TASK-250` would have produced), ran `msiexec /x` on a real per-user
install, and the task **survived** — the MSI log shows `UNREGISTERCLIENTTASK`
"succeeding," because the script's own `-Uninstall` branch wraps the call in
`-ErrorAction SilentlyContinue` plus an empty `catch {}`, silently swallowing
the same failure `TASK-250` found for registration.

Net effect: uninstalling the client MSI can leave an orphaned scheduled task
behind, pointing at a binary that no longer exists (deleted by the same
uninstall). Windows will simply fail to launch it at the next logon trigger
and move on — not catastrophic, but not "uninstall actually removes it"
either, which is exactly what `TASK-152`'s item 5 requires and what SEC.07's
original `TASK-145` design review cared about (the client MSI's whole
per-user/no-elevation posture was justified partly by "this stays cleanly
removable").

## Fix

Unlike registration (which gets a natural interactive-session hook for free
at the daemon's own next startup), there's no equivalent "something runs
interactively for this user again" moment guaranteed at uninstall time. Fix:
when the direct `Unregister-ScheduledTask` attempt doesn't leave the task
gone, fall back to scheduling a one-time cleanup at this **specific user's**
next interactive logon via `HKCU\Software\Microsoft\Windows\CurrentVersion\
RunOnce` — a self-deleting-after-one-run, per-user mechanism (deliberately
*not* the machine-wide `HKLM` Active Setup mechanism `TASK-250` considered
and rejected for the opposite direction, for the same "why should every
account on this machine be affected" reason). Registry writes aren't subject
to the interactive-session restriction the Task Scheduler API has, so this
works fine from within the deferred custom action.

## Acceptance criteria

- Real test: register `VaporWaultDaemon` (simulating self-registration),
  uninstall the client MSI, confirm the task is either gone immediately or a
  `RunOnce` entry now exists that — when actually invoked — successfully
  removes it.
- The `RunOnce` command is self-contained (does not depend on any file the
  uninstall just deleted).
- No machine-wide (`HKLM`) registry entry is left behind — scoped to the
  current user's own `HKCU` only.
- Reviewed by `SEC.07` (a `RunOnce` command that runs automatically at next
  logon is real attack surface if the invoked command isn't tightly scoped)
  given the `security-sensitive` tag.

SEC.07 [2026-09-07]: Reviewed the new `RunOnce` fallback in
`register-client-task.ps1` directly.

- The queued command is a fixed, compile-time literal string with no
  interpolated data of any kind (not even the daemon path) — no injection
  surface regardless of what state the machine is in when it's written.
- `HKEY_USERS\<SID>\...\RunOnce` is per-user by construction (the SID is
  read from the actual impersonated token at write time) — matches
  `TASK-250`'s own reasoning for rejecting the machine-wide `HKLM` Active
  Setup mechanism: only the user who actually ran the uninstall gets a
  queued command for their own next logon, not every account on the
  machine. This is also not a new capability being granted — any process
  already running as that user could always write to their own `RunOnce`
  key directly; this doesn't cross a privilege boundary that didn't
  already exist.
- **Advisory, not blocking**: a narrow timing window exists where
  uninstalling, then reinstalling before the next logon, then logging
  off/on, would have the stale queued command remove the *new* install's
  freshly self-registered task (the command only knows the fixed task
  name, not which install "owns" it). Self-correcting in practice — the
  user relaunching the app once re-registers it (`TASK-250`'s own
  self-heal logic) — and the window requires a specific sequence most
  users won't hit. Not fixed here: the queued command is authored at
  uninstall time with no way to know about a not-yet-existing future
  reinstall to disambiguate against. Worth a one-line mention in
  `docs/RELEASE.md`'s known-limitations if this project wants to track
  it, not a blocker.
- No blocking findings. Sign-off: `SEC.07` requirement satisfied.

CQR.08 [2026-09-07]: Reviewed the same change for code quality. The
debugging trail preserved in the header comment (`HKCU:` looked fine by
every check except the one that mattered — actual visibility from the
real user's own session) is exactly the kind of non-obvious gotcha worth
keeping in a comment rather than just fixing silently; a future reader
tempted to "simplify" back to `HKCU:` now has the reason not to, in the
same file. The fallback is correctly scoped to only fire when the direct
attempt demonstrably didn't work (`if (Get-ScheduledTask ...)` re-checks
reality rather than assuming the first attempt's exit code), avoiding an
unconditional/redundant `RunOnce` queue on the common case where direct
removal happens to succeed. `-ErrorAction Stop` on the `New-ItemProperty`
call (with an enclosing `try/catch`) is the correct pattern for "attempt
this, and don't let a failure here break the overall exit code" — matches
this script's existing `try { ... } catch {}` idiom used throughout.
No blocking findings. Sign-off: `CQR.08` requirement satisfied. Ready
for `done`.
