Full-project review (`TASK-00269`) confirmed the single most concrete
feature gap found: a vault registration has been write-only since
`TASK-00098` — no `VAULT_DELETE` wire message exists at all (absent from
both `docs/PROTOCOL.md` and `src/core/vw_proto.h`), so vault records
accumulate forever. This was already disclosed as a known gap at Phase 21
closure (`ARCHITECTURE.md`'s Phase 21 row, surfaced while writing
`TASK-00243`'s Android `VaultFlowTest`) but never actually designed or
built.

## Design

New messages `VAULT_DELETE` (0x0807, C→S) / `VAULT_DELETE_ACK` (0x0808,
S→C), immediately after the existing `VAULT_LIST_RESP` (0x0806).

- **Payload**: `VAULT_DELETE` = `session_token[32]` + `vault_id` (uint64).
  `VAULT_DELETE_ACK` = `error_code` (uint32).
- **Semantics**: a plain **soft-delete** — matches `SHARE_REVOKE`/
  `LINK_REVOKE`'s `revoked`-flag convention (§7.5), not
  `vw_store_files.c`'s hard-delete-and-reclaim-slot GC path. Only the
  vault's `owner_id` may delete it (`VW_ERR_PERMISSION` otherwise, same as
  `VAULT_KEY_FETCH`).
- **New error code**: `VW_ERR_VAULT_NOT_EMPTY` (610, §10.1) — the server
  refuses deletion while any file version, current or superseded, still
  carries this `vault_id`, since that version's `wrapped_dek` lives nowhere
  else and would become permanently unrecoverable otherwise. Same
  "children still exist" shape as the existing `VW_ERR_DIR_NOT_EMPTY`
  (604).
- Once deleted: `VAULT_KEY_FETCH` against the same `vault_id` returns
  `VW_ERR_NOT_FOUND`; it no longer appears in `VAULT_LIST_RESP`.
- Purely additive — no protocol version bump (wire version stays 6).
  `VAULT_DELETE` is added to the existing write-shaped-message set, so
  `VW_ERR_READ_ONLY_REPLICA` correctly rejects it on a cluster replica.

Tagged `security-sensitive` since it touches vault ownership/authorization
and the wrapped-DEK availability invariant the E2EE design depends on.
