`vw_storage.h`'s own comment has claimed since `TASK-024` that
`handle_chunk_download` "must re-verify the hash before sending to
clients" — this was never actually implemented. `vw_storage_chunk_get`
does not re-hash on read, and `handle_chunk_download`
(`vw_file_handlers.c`) streamed whatever bytes came back straight to the
client. A corrupted on-disk chunk (bit rot, filesystem bug) would be
served to a client with no detection anywhere.

## Acceptance criteria

- `handle_chunk_download` re-verifies `SHA-256(data) == chunk_hash` after
  `vw_storage_chunk_get` returns bytes, before building the `CHUNK_DATA`
  response.
- On mismatch: does not send the corrupted bytes; returns a new
  `VW_ERR_CHUNK_CORRUPT` (609) instead, logged via `LOG_WARN`.
- New error code documented in `docs/PROTOCOL.md` §7.2 and §10.1's
  normative error table, with a new revision row.
- `vw_storage.h`'s stale security comment updated to describe what
  actually re-verifies chunk integrity today (this handler + TASK-255's
  scrub) instead of the old unimplemented claim.

## Notes

SRV.01 (2026-09-09): implemented in `handle_chunk_download`
(`vw_file_handlers.c`) — re-hashes via `vw_crypto_sha256` (already
included) and `memcmp`s against the requested hash; on mismatch frees the
buffer and returns `VW_ERR_CHUNK_CORRUPT` via the existing `send_error`
path, logging via `LOG_WARN`. Added `VW_ERR_CHUNK_CORRUPT = 609` to
`vw_proto.h`. Updated `docs/PROTOCOL.md` (§7.2 CHUNK_DATA note, §10.1 error
table, revision 31) and `vw_storage.h`'s security comment.

CQR.08 (2026-09-09): change is a minimal, correctly-scoped addition at the
one chokepoint every client-facing chunk read goes through; frees `data`
on the error path (no leak). No blocking findings.

SEC.07 (2026-09-09): this closes a real integrity gap — previously a
corrupted chunk (whether from bit rot or a compromised/faulty disk) would
be served to any client with a valid grant, with no signal anywhere that
the bytes didn't match their own declared hash. The fix re-establishes the
invariant `vw_storage.h` always claimed to hold. No new attack surface:
uses the existing hash comparison already used at write time
(`vw_storage_chunk_put`), same constant-effort `memcmp` semantics as
elsewhere in this codebase (this is a content-integrity check, not a
secret comparison, so non-constant-time `memcmp` is fine here, same as the
existing SHA-256 verify path at write time). No blocking findings.
Regression coverage: `tests/integration/test_file_ops.py::
test_chunk_download_detects_corruption` (added in this same pass) flips a
byte directly in the on-disk chunk file and asserts `CHUNK_DOWNLOAD_REQ`
now fails with `VW_ERR_CHUNK_CORRUPT` instead of returning the corrupted
bytes. `TASK-00262` (filed) covers the broader scrub/RS/replica-repair
pipeline once `TASK-00260` lands, not this handler-level check.
