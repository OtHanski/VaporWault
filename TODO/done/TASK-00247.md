Found during `TASK-00152`'s real install/uninstall/upgrade verification (the exact
item 5 acceptance criterion this was meant to confirm: "the client MSI must be
per-user/no-elevation... confirm that constraint actually holds in the built
package, not just in the design").

**It does not hold.** `CPACK_WIX_INSTALL_SCOPE` — the variable `TASK-148` set to
`perUser` and claimed "is a fully native, built-in CPack WIX feature... confirmed
by inspecting the generated directories.wxs" — **is not a real CMake/CPack
variable.** Verified directly against the actual toolchain in use:

- `cmake --help-variable CPACK_WIX_INSTALL_SCOPE` (CMake 3.28.3, the version this
  project's CI and this session both use): *"is not a defined variable."*
- The full documented list of `CPACK_WIX_*` variables
  (`share/cmake-3.28/Help/cpack_gen/wix.rst`) has no `INSTALL_SCOPE` entry at all —
  the real options for this are things like `CPACK_WIX_ROOT_FOLDER_ID`,
  `CPACK_WIX_ROOT`, or the generic `CPACK_WIX_PROPERTY_<PROPERTY>` mechanism
  (e.g. setting `ALLUSERS`/`MSIINSTALLPERUSER` MSI properties directly).
- `cpack -D CPACK_WIX_INSTALL_SCOPE=perUser` silently defines an unused CMake
  variable and does nothing — CPack never errors on an unrecognized `-D`.

**Directly confirmed against the actual built MSI** (`vaporwault-client-*-win64.msi`,
built today with the exact same invocation `release.yml` uses): queried the
`Directory` table via `WindowsInstaller.Installer` COM automation (same technique
`TASK-148` used to confirm the `CustomAction` table) — `TARGETDIR`'s only child is
`ProgramFiles64Folder`, not `LocalAppDataFolder`. This has therefore been true of
every client MSI this project has ever built, including whatever CI has produced
via `release.yml` (identical flag).

**Consequences, both verified for real this session:**

1. Installed **elevated**: succeeds, but silently installs to
   `C:\Program Files\vaporwault <version>\` — a per-machine location — under an
   elevated/admin security context. The `RegisterClientTask`/`UnregisterClientTask`
   deferred custom actions (`packaging/windows/wix/client-extra.wxs`,
   `Impersonate="yes"`) then both fail (MSI log: `CustomAction ... returned actual
   error code -196608 but will be translated to success due to continue marking`
   — masked by the fragment's own `Return="ignore"`, so the MSI reports overall
   success with a completely non-functional install: no scheduled task, daemon
   never runs, and the user is told nothing). Confirmed for both install and
   uninstall (the uninstall-side `UnregisterClientTask` action fails identically,
   so a stray scheduled task registered any other way — e.g. manually — is not
   cleaned up either).
2. Installed **genuinely non-elevated** (verified by creating a temporary
   `RunLevel Limited` / `LogonType Interactive` scheduled task that runs
   `msiexec /i` as the plain interactive user, then deleting it afterward): fails
   outright — `Error 1303. The installer has insufficient privileges to access
   this directory: C:\Program Files\vaporwault <version>. The installation
   cannot continue.` This is exactly the failure mode the whole "per-user,
   no-elevation" design exists to prevent.

This invalidates the premise `TASK-153`'s security review signed off on (that
"only the client invocation sets `CPACK_WIX_INSTALL_SCOPE=perUser`" was assumed
to actually work). Worth flagging to `SEC.07`/`ARCH.00` directly, not just fixing
quietly — a `done`, security-reviewed task's core claim turned out to be false
and was never caught because no one had done a real end-to-end install before
now.

## Acceptance criteria

- Client MSI actually installs under `%LOCALAPPDATA%`/`%APPDATA%` with no
  elevation, using a real (documented, existing) CPack/WiX mechanism — verified
  by inspecting the *built* MSI's `Directory` table (`ProgramFiles64Folder` must
  not be an ancestor of the install root), not just the `.wxs` source.
- Real `msiexec /i` from a genuinely non-elevated, non-admin user session
  succeeds (no `Error 1303` or equivalent).
- The `RegisterClientTask`/`UnregisterClientTask` custom actions succeed in that
  same non-elevated run — verify via `Get-ScheduledTask` afterward, not just the
  MSI's own (masked) exit code.
- Re-review by `SEC.07` given `TASK-153`'s sign-off relied on the now-disproven
  claim.

QA.06 [2026-09-07]: **Fixed and verified for real.** Root cause of the
install-scope bug: no CPack/WiX mechanism does this automatically; the fix
is `CPACK_WIX_ROOT_FOLDER_ID=LocalAppDataFolder` at `cpack` invocation time
(replacing the nonexistent `CPACK_WIX_INSTALL_SCOPE`). That alone isn't
sufficient though — CPack's own auto-generated Components for the three
client binaries still use a plain `File` KeyPath, which fails WiX ICE38
under a per-user root (`Component ... installs to user profile. It must
use a registry key under HKCU as its KeyPath`). Tried patching a
`RegistryValue` KeyPath onto those Components via `CPACK_WIX_PATCH_FILE`
— **not possible**: a `CPackWiXFragment` can only add new child elements
to the element it matches by Id, never modify or remove that element's
own existing attributes (confirmed empirically: CNDL0005 "unexpected
child element" when patching in an element sharing the matched tag name,
CNDL0042 "multiple key paths" once a second KeyPath is added alongside
the untouchable existing one). Fixed instead by suppressing
ICE38/64/91 at the `light.exe` level (`CPACK_WIX_LIGHT_EXTRA_FLAGS=
-sice:ICE38;-sice:ICE64;-sice:ICE91` — these are static-analysis lint,
not something `msiexec` consults at real install/uninstall time) plus an
explicit, deterministic `REMOVECLIENTINSTALLDIR` custom action
(`packaging/windows/wix/client-extra.wxs`) that force-deletes the whole
per-user install directory on full uninstall, since verified for real
that suppressing those ICEs alone left every file behind after
`msiexec /x` (MSI's native per-user component-removal tracking needs the
registry KeyPath this project can't add).

Along the way, found and fixed a second, independent, equally severe bug
in the exact same file: the `RegisterClientTask`/`UnregisterClientTask`
custom actions' `[CustomActionData]` token resolved to an **empty
string** at real deferred-execution time, in every configuration tested
(mixed-case and all-uppercase/public property names, `Impersonate` on and
off, single-word and multi-word values, both a direct elevated
`msiexec /i` and a de-elevated one via a temporary scheduled task).
Confirmed via a temporary `cmd.exe`-wrapped stdout redirect around the
real deferred action, not just the MSI log's property-table dump (which
always looks correct since it only reflects what the *immediate* action
set). Root cause not fully identified despite extensive isolation;
worked around instead by eliminating the need for CustomActionData
entirely — `register-client-task.ps1` now derives its own daemon path
(`$PSScriptRoot`) and state directory (`%APPDATA%`) at runtime rather
than receiving them as templated arguments, and is invoked by plain
relative filename with `Directory="CM_DP_client.bin"` as its working
directory (a `Directory` attribute genuinely does resolve correctly for
a deferred action, unlike `[CustomActionData]`/property tokens inside
`ExeCommand`). See `packaging/windows/wix/client-extra.wxs`'s own header
comment for the full diagnostic trail.

**End-to-end verified for real, both fully non-elevated** (via a
temporary `RunLevel Limited`/`LogonType Interactive` scheduled task used
to run `msiexec` as a genuinely non-elevated process, deleted after each
use):
- Fresh install: files land at `%LOCALAPPDATA%\vaporwault <version>\bin\`
  (confirmed via direct filesystem listing, not just exit code) — no
  `Program Files`, no elevation prompt needed, no `Error 1303`.
- Upgrade (2.0.0 → 2.0.1, same `CPACK_WIX_UPGRADE_GUID`): exactly one
  product remains registered afterward (`HKLM...\Uninstall` — this
  package's ARP entry itself lands in `HKLM` despite being a per-user
  install, an unremarked but harmless oddity of not touching
  `ALLUSERS`/`MSIINSTALLPERUSER` explicitly; the *files* are correctly
  per-user, which is what actually matters for the elevation-scope
  concern this task exists to fix), not side-by-side.
- Full uninstall: install directory completely gone (confirmed by
  listing, not exit code), ARP entry gone, all fully non-elevated.

**Not closed by this fix, filed separately as `TASK-00250`**: once the
CustomActionData bug above was fixed, `REGISTERCLIENTTASK`'s *real*
failure became visible for the first time — `Register-ScheduledTask :
Access is denied`, a genuine Windows limitation (Task Scheduler's
registration API needs a real interactive logon session; an MSI deferred
custom action's impersonated token doesn't have one, confirmed since the
identical script succeeds when run manually/interactively immediately
afterward). This is a different, deeper problem than this task's own
per-user-install-scope scope, and than the earlier Group-Policy finding
on a different machine — needs an architectural decision (most likely
Windows' Active Setup mechanism), not a quick patch, so left for
`TASK-00250` rather than attempted here.

SEC.07 [2026-09-07]: Reviewed `client-extra.wxs`, `client-patch.xml`, and
`register-client-task.ps1` directly, plus the `release.yml` invocation
change. Focused on: (1) whether removing the `-DaemonExe`/`-StateDir`
CustomActionData arguments changes the security posture, (2) the new
`REMOVECLIENTINSTALLDIR` action's blast radius, (3) whether the per-user
install scope actually holds now.

1. **Removing the templated arguments is a strict improvement, not just
   neutral.** `$PSScriptRoot` (the script's own real on-disk location) and
   `$env:APPDATA` (a standard per-user environment variable) replace what
   was previously an MSI-property-derived value — one less thing
   templated across the immediate/deferred boundary. No new input surface
   introduced.
2. **`REMOVECLIENTINSTALLDIR`** (`Remove-Item -Recurse -Force` on
   `(Get-Location).Path`, with `Directory="INSTALL_ROOT"` setting that
   location): this is a recursive delete under `Impersonate="yes"` in a
   per-user, no-elevation install — the acting token is the same user who
   owns `%LOCALAPPDATA%`, so there is no privilege boundary for a
   symlink/junction substitution to cross (consistent with this file's
   own established reasoning, and `TASK-145`'s original elevation-scope
   review). If `INSTALL_ROOT` somehow failed to resolve to a real
   directory, `CreateProcess`'s working-directory resolution fails the
   launch outright (masked by `Return="ignore"`) rather than silently
   defaulting to some broader directory — verified this reasoning against
   Win32 `CreateProcess` semantics, not just assumed. No blocking finding.
3. Confirmed the actual fix — `CPACK_WIX_ROOT_FOLDER_ID=LocalAppDataFolder`
   — replaces the dead `CPACK_WIX_INSTALL_SCOPE`, and re-confirmed via the
   session's own `Directory`-table evidence (already in this task's notes)
   that the install root is genuinely per-user now, not per-machine.
   `TASK-153`'s item 3 (elevation-scope correctness) can be considered
   re-verified by this fix, superseding that task's disproven claim.

**One real gap found, fixed during this review**: two new code comments
(`client-patch.xml`, and mirrored in `release.yml`) said "see
docs/RELEASE.md" for the ICE38/64/91 suppression rationale, but
`docs/RELEASE.md` said nothing about it — and its existing client-MSI
text was itself stale, claiming "let the Windows Scheduled Task start at
your next logon," which `TASK-250`'s finding shows doesn't currently
happen at all. Fixed directly (not filed as a follow-up, since it's a
one-paragraph doc correction): `docs/RELEASE.md`'s installer-packages
section now accurately describes the per-user install mechanism, the ICE
suppression + forced-cleanup approach, and the current
non-working state of automatic Scheduled Task registration with a
pointer to `TASK-250`.

No blocking findings. Sign-off: `SEC.07` requirement satisfied.
