Dedicated feature-level review for the installer packaging effort
(`TASK-00145`), beyond each implementation task's own `review_by` sign-off —
same pattern as `TASK-00144` for the web gateway feature.

Specific items, carried forward from `TASK-00145`'s design review and each
implementation task's own flagged risks:

1. **Root-privileged Linux maintainer scripts** (`TASK-00149`/`TASK-00150`):
   argument quoting, no unvalidated interpolation into `sh -c`/`eval`-style
   constructs, correct permission bits on every created file/directory
   (matching `install.sh`'s existing, already-reasonable defaults — this
   is about not *regressing* that when the logic moves into `postinst`).
2. **Windows client custom action** (`TASK-00148`): the PowerShell
   invocation's command-line construction — this is the same class of risk
   `TASK-00081` already fixed once in `release.yml`'s ref-name handling;
   confirm it wasn't reintroduced here via a different mechanism (MSI
   properties instead of GitHub Actions expressions, same underlying
   injection shape).
3. **Elevation-scope correctness** (`TASK-00147` vs `TASK-00148`): confirm the
   server MSI actually requires elevation and the client MSI actually
   doesn't — a build-time regression here (e.g. a copy-pasted WiX fragment
   that accidentally elevates the client) would silently reintroduce the
   exact SEC.07 finding `TASK-00145`'s design review already resolved.
4. **DEB/RPM purge-vs-remove semantics** (`TASK-00150`): confirm the
   documented asymmetry (RPM's `dnf remove` behaving like DEB's
   `apt purge`) is real and not a scripting bug that happens to look like
   an intentional design difference.
5. **Unsigned packages**: confirm this is clearly disclosed
   (`TASK-00154`), not just an implementation-time gap nobody wrote down.
6. **WiX Toolset supply chain** (`TASK-00151`): if the WiX binaries are
   fetched from a third-party NuGet mirror in CI (rather than a package
   manager with its own integrity checks), confirm the download is pinned
   to a specific version and checksum-verified, matching the existing
   `SDL2_ZIP_SHA256` precedent in `release.yml` for exactly this class of
   "vendor a third-party binary into CI" risk.

Findings tagged `blocking` prevent any of `TASK-00145`, `TASK-00147`–`TASK-00151`
from moving to `done`, per `CLAUDE.md`'s routing rules.

**Blocking (resolved):** Item 6 — the WiX Toolset NuGet-package fallback
in `release.yml` (`TASK-00151`) fetched a third-party binary
(`nuget.org/api/v2/package/wix/3.11.2`) with **no integrity verification**
at all, unlike this exact same workflow's own `SDL2_ZIP_SHA256` precedent
for the identical class of risk (a tampered or unexpectedly-changed
vendored binary silently entering the build). **Resolved**: added
`WIX_ZIP_SHA256` (pinned to `ac2fff0541f87756b530c93ca3a45ff2dfb1ebe392c269901de0c19074bec5d0`,
this exact package's real hash) and a checksum-mismatch abort, mirroring
the SDL2 step's structure exactly. Verified for real, not just written: ran
the fallback fetch against the actual URL, confirmed the checksum matches
and extraction succeeds, then re-ran with a deliberately wrong expected
hash and confirmed the mismatch is correctly detected.

**Reviewed via static analysis, not just reading**:
- Item 1 (root-privileged Linux maintainer scripts, `TASK-00149`/`TASK-00150`):
  ran `shellcheck -S style` (strictest severity) against all seven scripts
  (`packaging/linux/scripts/{server,client}/{postinst,prerm,postrm}` +
  `rpm/server-postun.sh`) — zero findings at any severity level.
- Item 2 (client MSI custom action, `TASK-00148`): ran PSScriptAnalyzer
  against `register-client-task.ps1`. Findings: three
  `PSAvoidUsingEmptyCatchBlock` warnings (the idempotent
  unregister-before-register / stop-if-running calls) and one
  `PSUseBOMForUnicodeEncodedFile` warning. The empty-catch pattern is
  **accepted, not a new problem** — it's identical to the existing,
  already-shipped `Install-VaporWaultClient.ps1`'s own
  `try { ... } catch {}` blocks (confirmed by direct comparison, 3
  matching instances), so this is established project convention, not a
  regression. The BOM warning **was real and fixed**: the file had two
  em-dash characters (non-ASCII) with no BOM; replaced with plain ASCII
  hyphens (simpler and more foolproof than adding a BOM, given the script
  is invoked via `powershell.exe -File` from an MSI custom action where
  the exact runtime code page/locale isn't something this project
  controls). Command-line argument construction itself (the
  `CustomActionData` two-step pattern) was reviewed in `TASK-00148`'s own
  implementation note — the severity assessment there (low, since this is
  a per-user no-elevation install with no privilege boundary for a
  crafted property to cross) still holds on re-review.
- Item 3 (elevation-scope correctness, `TASK-00147` vs `TASK-00148`): confirmed
  by direct inspection of `release.yml`'s two `cpack -G WIX` invocations —
  only the client invocation sets `CPACK_WIX_INSTALL_SCOPE=perUser`; the
  server invocation has no such override (defaults to per-machine/
  elevated). No copy-paste cross-contamination between the two.
- Item 4 (DEB/RPM purge-vs-remove asymmetry, `TASK-00150`): confirmed real,
  not a scripting bug, via the actual container-based upgrade/removal
  testing already performed during `TASK-00150`'s implementation (`rpm -U`
  preserved data, `dnf remove` afterward deleted it) — re-verified the
  reasoning holds, not re-run here.
- Item 5 (unsigned packages disclosed): confirmed present in
  `docs/RELEASE.md`'s new "Installer packages" section (`TASK-00154`).
