Discovered while implementing `TASK-00182` (daemon IPC + CLI for version
history) and verifying it against a real grantee account.
`vw_client_version_list`/`vw_client_version_restore` are 100% path-based:
`vw_client_version_list` resolves the file via `vw_client_file_stat`
first, and the server's `VERSION_RESTORE` handler resolves
`virtual_path` the same owner-namespaced way. Per `ARCHITECTURE.md`'s
`TASK-00106` note, path resolution never crosses into another user's tree —
so a grantee gets `VW_ERR_NOT_FOUND` on a shared item's version history
today, regardless of whether their grant is VIEW or EDIT. This is
inconsistent with `FILE_LIST`/`FILE_STAT`/`FILE_UPLOAD`/`FILE_DOWNLOAD`/
`FILE_DELETE`, all of which got a `file_id`-addressed variant precisely
so a grantee (or a file_id-addressed shared-folder sync target) could
reach content they don't own by path (`TASK-00095`/`TASK-00106`).

Confirmed with a real integration test, not just code reading —
`tests/integration/test_cli_version_history.py::
test_cli_version_restore_not_available_for_a_shared_file`.

## Work

- Design (small — this is following an established pattern, not
  inventing one): either (a) add an optional `file_id` field to
  `VERSION_LIST`/`VERSION_RESTORE` that, when present and the session
  isn't path-resolving, is checked via `effective_permission()` exactly
  like `FILE_LIST`'s `dir_file_id` extension (`TASK-00106`) does, or
  (b) new `VERSION_LIST_BY_ID`/`VERSION_RESTORE_BY_ID` message pairs if
  the payload shapes diverge enough to make (a) awkward. Recommend (a)
  for consistency with the precedent unless a real wire-layout conflict
  turns up.
- Permission requirement: `VERSION_LIST` via `file_id` needs
  `VW_PERM_VIEW`; `VERSION_RESTORE` via `file_id` needs `VW_PERM_EDIT` —
  same split `docs/PROTOCOL.md`'s existing permission table already
  documents for the path-based versions.
- Publish the section in `docs/PROTOCOL.md`, then file the SRV.01
  (server-side permission-checked resolution) and CLI.02 (client-core
  wrapper + daemon IPC + CLI/GUI surfacing for shared items) follow-up
  tasks once this lands, per CLAUDE.md routing rule 3.

## Acceptance criteria

- SRV.01 can implement server-side resolution against this section
  without further clarification.
- Existing path-based `VERSION_LIST`/`VERSION_RESTORE` behavior is
  byte-for-byte unchanged for a caller that doesn't supply `file_id`.

PRT.04 [2026-08-27]: Read both handlers in full before designing the
options this task itself proposed, and found the premise wrong: no wire
change is needed at all.

- `handle_version_list` (`VERSION_LIST`, `src/server/vw_file_handlers.c`)
  already takes `file_id` directly on the wire and already calls
  `effective_permission()`/`VW_PERM_VIEW` — it has always worked
  correctly for a grantee. This task's own claim that it "resolves via
  `vw_client_file_stat`" was true only of the *client* wrapper, not the
  server handler, and got conflated into "the protocol needs a
  `file_id` option" incorrectly.
- `handle_version_restore` (`VERSION_RESTORE`) resolves entirely via
  `version_id -> src_ver.file_id -> effective_permission()/VW_PERM_EDIT`.
  Its `virtual_path` field is read and shape-validated
  (`vw_path_validate`, which rejected zero-length strings) but **never
  used** for resolution or authorization anywhere in the handler. This
  directly contradicts this task's own filed claim that "the server's
  VERSION_RESTORE handler resolves virtual_path the same owner-namespaced
  way" as FILE_STAT — that claim was factually wrong, confirmed by
  reading the full handler body line by line, not by re-guessing.
- The real, sole blocker is client-side: `vw_client_version_list`/
  `vw_client_version_restore` (`src/client/vw_client_core.c`) only ever
  obtain `file_id`/`version_id` via a `vw_client_file_stat` path
  resolution first (owner-namespaced), and `virtual_path`'s mandatory
  non-empty shape requirement on the wire blocked a client from omitting
  it even though the server never used its contents.
- Minimal fix, published as `docs/PROTOCOL.md` §7.3 revision 25: server
  now accepts an empty `virtual_path` on `VERSION_RESTORE`, skipping
  `vw_path_validate` in that case only (`src/server/vw_file_handlers.c`,
  `handle_version_restore`) — meaning "resolve by `version_id`/`file_id`
  alone." Any caller supplying a real path is byte-for-byte unaffected.
  No protocol version bump: this is a pure permissive relaxation (a
  previously-always-rejected zero-length string is now accepted), not a
  new field or message.
- Landed the one-line server change directly in this task rather than
  filing a separate SRV.01 follow-up, since it turned out too small to
  warrant one. Filed `TASK-00223` (CLI.02) for the actual remaining work:
  client-core by-file_id wrappers, daemon IPC, and CLI/GUI surfacing —
  that is where reaching this fix now depends entirely on client work,
  not protocol or server work.
- Verified: WSL/GCC (`build-gw-e2e`) and MSVC (`build-msvc-105`) both
  build clean; `ctest` (20/20 suites, including `unit_vw_file_handlers`
  on both toolchains) and the full `tests/integration/
