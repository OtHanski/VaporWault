`CMakeLists.txt`'s top-level `project(VaporWault C CXX)` has no `VERSION`
field — no built binary can report its own version at runtime, only
whatever the packaging step happened to bake into a filename from the
git tag used to build it (and only for tagged release builds, not local/
CI dev builds at all).

## Work

- Add a `VERSION` field to the top-level `project()` call. Decide the
  source of truth: a checked-in `VERSION` file read by CMake at
  configure time is simplest and works identically for local builds, CI,
  and `release.yml`'s tag-triggered builds — prefer that over deriving
  from `git describe` alone, since a shallow CI checkout may not have
  tag history available.
- Generate a small header (`configure_file`, e.g. `vw_version.h`) exposing
  a `VW_VERSION_STRING` macro, optionally including the git short hash
  when available (best-effort — must not fail the build if `git` isn't
  on `PATH` or this isn't a git checkout, e.g. a source tarball).
- Wire a `--version` flag into every binary's argument parsing
  (`vapourwaultd`, `vapourwault-daemon`, `vapourwault-cli`,
  `vapourwault-server-cli`, `vapourwault-gui`, `vapourwault-server-gui`,
  `vapourwault-web-gateway`) that prints `VW_VERSION_STRING` and exits.
  This is mechanical/uniform across binaries — if any of them turns out
  to need real design input (not just "print a string and exit"), file
  that specific one as its own out-of-domain task against its owning
  agent rather than guessing.
- `release.yml`/packaging: confirm the `VERSION` file (or its equivalent)
  is kept in sync with the git tag used for a release build — decide
  whether that's a manual bump-before-tagging step or a CI check that
  fails the release build on mismatch, and document the choice in
  `docs/RELEASE.md`.

## Acceptance criteria

- `<any-binary> --version` prints a real, non-empty version string on
  every platform this project builds for (Linux, Windows).
- A local dev build (no tag, possibly no git at all — e.g. from a source
  tarball) still produces a working binary with a sensible fallback
  version string, not a build failure.
- `docs/RELEASE.md` documents how the embedded version relates to the
  git tag.

BLD.05 [2026-08-26]: Implemented.

- Added a checked-in `VERSION` file (repo root, plain `0.3.0` — the next
  planned release after the last tag `v0.2.0`; no leading `v`, no suffix,
  since `project(VERSION ...)` requires a numeric-dotted value). Read via
  `file(STRINGS ... LIMIT_COUNT 1)` + `string(STRIP ...)` before the
  `project()` call so it can feed `project(VaporWault VERSION ...)`
  directly, rather than deriving from `git describe` (a shallow CI
  checkout may have no tag history, and a source tarball has no `.git` at
  all — this must not fail configure either way).
- The existing `VW_VERSION` cache variable (already used by
  `cmake/Packaging.cmake`/`release.yml` since `TASK-00145`/`00151`) now
  defaults to the `VERSION` file's contents instead of the hardcoded
  `"0.0.0-dev"` placeholder, so a local/dev build reports something real.
  CI's existing `-DVW_VERSION="$PKG_VERSION"` override (tag-derived) is
  unaffected and still wins — verified both paths explicitly (see Testing
  below), not just read from the CMake logic.
- New `VW_VERSION_STRING` = `${VW_VERSION}` plus a best-effort
  `+<short-git-hash>` suffix: `find_package(Git QUIET)` +
  `execute_process(git rev-parse --short HEAD)`, guarded on `GIT_FOUND`
  and the presence of a `.git` path, with the hash reset to empty on any
  non-zero exit — never fails configure if `git` is missing or this isn't
  a git checkout.
- `cmake/vw_version.h.in` → `configure_file` → `${CMAKE_BINARY_DIR}/generated/vw_version.h`
  exposing `VW_VERSION_STRING`. Exposed via a new `vw_version` INTERFACE
  library (include-path-only, no object code) so every binary target adds
  it to `target_link_libraries` without needing to know the generated
  header's absolute path.
- `--version` wired into all 7 binaries the task named
  (`vapourwaultd`, `vapourwault-daemon`, `vapourwault-cli`,
  `vapourwault-server-cli`, `vapourwault-gui`, `vapourwault-server-gui`,
  `vapourwault-web-gateway`) plus `vwdump` (not in the task's explicit
  list, but trivial to include and the acceptance criteria says
  "any binary" — filing it separately would have been pure overhead for
  one line). Each prints `<prog-name> <VW_VERSION_STRING>` and exits 0,
  checked first thing in argument parsing (before the two GUI binaries'
  `SDL_Init`, matching every other binary's convention of checking
  `--help`/`--version` before doing any real work). The two GUI `main.cpp`
  files previously had their own `#ifndef VW_VERSION #define VW_VERSION
  "dev" #endif` placeholder (used only in the window title) that nothing
  ever actually defined via a compile definition — that placeholder is
  gone now; `VW_VERSION` is `#define`d locally from the real
  `VW_VERSION_STRING` macro so the window title changes from always
  "VaporWault dev" to the real version too, not just `--version`'s output.
- `docs/RELEASE.md`'s "Versioning" section rewritten: the `VERSION` file is
  **not** the source of truth for what a real release ships (CI's
  `-DVW_VERSION` override, derived from the pushed tag, wins over it for
  both CPack's package version and every binary's `--version` output) — it
  only controls a local/dev build's fallback and `PROJECT_VERSION`.
  Documented as a manual bump-before-tagging step rather than a CI-enforced
  mismatch check: a stale `VERSION` file has no user-visible effect on an
  actual release artifact, so a hard CI gate would be enforcing a
  constraint the release doesn't need.
- `cmake/Packaging.cmake`'s stale comment ("No PROJECT_VERSION exists")
  corrected — a `PROJECT_VERSION` now exists (from the `VERSION` file) but
  `CPACK_PACKAGE_VERSION` still needs `VW_VERSION` set explicitly since
  that's the one CI actually overrides with the tag.

**Testing**:
- Fresh configure (no prior cache), no `-DVW_VERSION` override: confirmed
  `VW_VERSION` defaults to the `VERSION` file's `0.3.0`, and a built
  `vapourwaultd --version` prints `vapourwaultd 0.3.0+<realgitshorthash>`.
- Fresh configure with `-DVW_VERSION=0.2.0` (simulating `release.yml`'s
  tag-derived override): `vapourwaultd --version` prints
  `vapourwaultd 0.2.0+<hash>` — confirms the CI override still wins and a
  stale `VERSION` file can't ship a wrong version in a real release.
- Full rebuild of the existing WSL/GCC (`build-gw-e2e`) and MSVC
  (`build-msvc-105`) dev build directories: both succeed clean (their
  cached `VW_VERSION` predates this change and stayed `"0.0.0-dev"`,
  which is correct, expected CMake cache behavior, not a bug — a cached
  variable's default doesn't change retroactively; a fresh configure
  above confirmed the new default is picked up).
- `--version` verified by actually running the built binary (not just read
  from source) for all 8: `vapourwaultd`, `vapourwault-server-cli`,
  `vapourwault-daemon`, `vapourwault-cli`, `vwdump`,
  `vapourwault-web-gateway` on both WSL/GCC and MSVC; `vapourwault-gui`/
  `vapourwault-server-gui` on WSL/GCC only — the MSVC-built GUI binaries
  can't run at all in this dev environment (missing `SDL2.dll` next to the
  built `.exe`, a pre-existing environment gap unrelated to this change,
  consistent with this project's already-documented GUI-testing
  limitations). Traced the code path instead: the `--version` check is the
  first thing in `main()`, before `SDL_Init`, identical in structure to
  the WSL/GCC binary that was actually run and confirmed working.
- `ctest --test-dir build-gw-e2e`: 19/19 passed, no regression from the
  `CMakeLists.txt`/`project()` changes.
