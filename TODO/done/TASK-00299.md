New IPC message pairs in `src/client/vw_ipc.h`, next free codes after
`VW_IPC_SHARED_FOLDER_LIST_RESP = 0x8050`:

```c
VW_IPC_UPDATE_STATUS_REQ     = 0x8051, /* C→D: query current update state */
VW_IPC_UPDATE_STATUS_RESP    = 0x8052, /* D→C: available(u8) + server_version + manifest_version + install_kind(u8) */
VW_IPC_UPDATE_APPLY_REQ      = 0x8053, /* C→D: user clicked "Update Now" */
VW_IPC_UPDATE_APPLY_ACK      = 0x8054, /* D→C: error_code (daemon will restart itself on success) */
VW_IPC_UPDATE_POLICY_SET_REQ = 0x8055, /* C→D: policy(u8: notify|auto) */
VW_IPC_UPDATE_POLICY_SET_ACK = 0x8056, /* D→C: error_code + policy echoed back */
```

Document full payload layouts in the existing big comment block
(`vw_ipc.h:238-710` style), matching the project's convention.

`vapourwault-cli` gains a new `update status`/`update apply`/`update policy`
subcommand group wrapping these, following the existing CLI-wraps-IPC pattern
(`vw_client_cli.c`).

## Acceptance criteria

- IPC round-trip tested: status query reflects real daemon state, apply
  triggers the `TASK-00298` pipeline, policy set persists to `daemon.conf`
  and is reflected in a subsequent status query.
- CLI subcommands documented in `--help` output.

## Notes

**CLI.02, 2026-09-16**: Implemented as designed, with one deviation from
the original IPC layout sketch and an extensive test-reliability
investigation that surfaced two real, previously-undiscovered bugs
elsewhere in the daemon.

**Implementation**: `VW_IPC_UPDATE_STATUS_REQ/_RESP`,
`VW_IPC_UPDATE_APPLY_REQ/_ACK`, `VW_IPC_UPDATE_POLICY_SET_REQ/_ACK` added
at `0x8051`-`0x8056` per the design. `vw_daemon.c`'s "Client auto-update
integration" section (statics + `vw_daemon_get_update_status`/
`vw_daemon_apply_update_now`/`handle_update_hint`/
`maybe_run_daily_auto_check`, all originally added by `TASK-00298`) was
relocated to before `handle_ipc_client()` in the file — the new
`VW_IPC_UPDATE_*_REQ` cases inside that function need them declared
first; they were previously declared after it, which compiled fine only
because nothing there referenced them yet. New `persist_update_policy()`
helper rewrites `daemon.conf`'s `update_policy` key in place (same
read-whole-file/replace-or-append-one-line/atomic-write idiom as
`vw_update_manifest.c`'s `write_update_sequence`, deliberately duplicated
per that module's own module-boundary comment) — `vw_daemon_cfg_write_
defaults` only ever writes a *new* file, so it couldn't be reused for a
live runtime change. `vapourwault-cli` gained the `update status`/`update
apply`/`update policy notify|auto` subcommand group, documented in
`--help`.

**Deviation**: the design's `VW_IPC_UPDATE_STATUS_RESP` layout
(`available` + `server_version` + `manifest_version` + `install_kind`)
had no field for the daemon's *current policy* — but this task's own
acceptance criterion ("policy set... reflected in a subsequent status
query") requires one. Added a trailing `u8 policy` field, same
append-only convention every other `_RESP` in `vw_ipc.h` already uses for
this exact situation.

**Extensive test-reliability investigation (the bulk of this task's real
effort)**: `test_ipc_update.c` spawns the real `vapourwault-daemon` +
`vapourwault-cli` binaries and drives them end-to-end — no server/account
needed, since every `UPDATE_*` message is daemon-global. Getting this to
pass *reliably* surfaced two genuine bugs, neither in this task's own new
code:

1. **`TASK-00305`** (filed separately): switching `update_policy` to
   `auto` makes the daemon's next main-loop tick attempt a real network
   fetch (`TASK-00298`'s `maybe_run_daily_auto_check`); `src/core/vw_net.c`'s
   `connect_with_timeout()` calls `getaddrinfo()` with no timeout at all,
   only bounding the connect phase *after* DNS resolution already
   completed — in this dev sandbox that stalled requests by anywhere from
   ~16s to over two minutes.
2. **`TASK-00306`** (filed separately, the more significant of the two):
   `vw_watcher_wait()` (`vw_watch_windows.c`/`vw_watch_linux.c`) blocks
   for the *entire* wait timeout whenever there are zero watched roots —
   exactly the state of any daemon with no configured accounts, which
   this test deliberately uses. With the real 30-second `sync_interval_ms`
   default, a second IPC request issued moments after an earlier one
   (exactly what this test's own TC-1/TC-2 do) could non-deterministically
   wait up to 30 real seconds for the daemon's main loop to cycle back to
   its IPC-accept step.

Both were only found because this task tried to actually exercise the
daemon live and repeatedly, rather than mocking it — the failure symptom
(intermittent multi-minute hangs specifically when the test binary was
launched via `ctest`, never under direct invocation) was initially
misdiagnosed at length as ctest-launch-specific sandbox behavior before a
debug build with instrumented output traced it to #2 directly. Fixed in
this test by pinning its own `daemon.conf`'s `sync_interval_ms` to `200`
instead of the real default — a test-only mitigation; the underlying
daemon behavior is `TASK-00306`'s to fix. 8+ consecutive clean runs
confirmed on both `build-msvc-105` and WSL `build-wsl-werror` after the
fix, both standalone and under `ctest` (including the full parallel
suite), each completing in ~1-2 seconds.
