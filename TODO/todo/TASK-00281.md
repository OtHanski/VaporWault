## Corrected finding (2026-09-11)

Read `effective_permission()`/`vw_share_resolve_permission()`
(`vw_file_handlers.c`/`vw_share.c`) and `FILE_LIST`'s existing
`dir_file_id` field before assuming a protocol change was required, per
this task's own acceptance criteria. Found the wire protocol already
fully supports this:

- `FILE_LIST`'s `dir_file_id` field (`TASK-106`) already lets an
  authenticated grant-holder list any directory by `file_id`, not just
  their own owner-namespaced paths.
- `vw_share_resolve_permission`'s `is_file_or_ancestor()` walks the full
  `parent_dir_id` chain (up to 2048 hops), so permission correctly
  inherits down a shared folder's subtree to **unbounded depth** — a
  grant on a folder already covers everything inside it, nested folders
  included. This isn't unused/theoretical: `vw_sync.c`'s shared-folder
  sync already relies on exactly this via `vw_client_file_list_by_id`,
  which client-core has had since `TASK-106`.
- The permission model needs no per-sub-item override: `TASK-106`'s
  design (a grant's permission level extends to everything inside the
  granted folder, no finer-grained override) is already the shipped
  behavior, not a new decision to make.

The **actual** gap was one layer up: no **daemon IPC** message ever
exposed this live, non-cache lookup to a GUI/CLI caller.
`VW_IPC_FILE_LIST_REQ` only ever queries the local sync *cache*, which
has no entries for a shared folder the user hasn't explicitly added as a
sync target (`VW_IPC_FOLDER_ADD_SHARED_REQ`) — `vw_view_shared.cpp`'s own
comment ("no IPC message lists a folder's children by id") was accurate
about the IPC layer specifically, just attributed to the wrong layer by
the review that filed this task.

## What shipped in this task

- `src/client/vw_ipc.h`: new `VW_IPC_SHARED_FOLDER_LIST_REQ`/`_RESP`
  (0x804F/0x8050) — full payload spec written (same shape as
  `VW_IPC_VERSION_LIST_BY_ID_REQ`'s existing "thin passthrough to an
  already-existing client-core function" pattern). A live remote listing
  in `vw_file_entry_t`'s own field shape (`entry_type`, `file_id`,
  `size_bytes`, `mtime_unix`, `version_id`, `name`, `vault_id`) — not
  `VW_IPC_FILE_LIST_RESP`'s cache-entry shape, which carries fields
  (`virtual_path`, `local_path`, `sync_state`, `local_mtime`) that don't
  exist for something never added to the local cache.

## Acceptance criteria (implementation, this task)

- `vw_daemon.c` dispatch handler for `VW_IPC_SHARED_FOLDER_LIST_REQ`:
  resolve the account, call `vw_client_file_list_by_id(sess, dir_file_id,
  recursive, &entries, &count)`, encode the response per the spec above.
- No new client-core code needed — `vw_client_file_list_by_id` already
  exists and is already used elsewhere (`vw_sync.c`).
