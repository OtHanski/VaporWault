Full-project review (`TASK-00269`) confirmed a disclosed limitation from
`TASK-00139`: browser uploads/downloads don't survive a page refresh. Both
native clients (desktop daemon, Android) already resume interrupted
transfers via the existing chunked-upload/resumable-download protocol
primitives — the gap is purely in the browser frontend's own state
handling, not a missing wire capability.

## Acceptance criteria

- On reload, an in-progress upload/download resumes from its last
  completed chunk rather than restarting from zero, using the existing
  `CHUNK_QUERY`-style "which chunks does the server already have"
  mechanism the native clients rely on (`vw_client_core.c`'s upload path
  is the reference implementation to follow, not a new browser-side
  scheme).
- State needed to resume (in-flight transfer id, target vault_id if
  encrypted, chunk progress) persisted client-side in a way that survives
  a reload (e.g. `IndexedDB`/`localStorage`) — no server-side change
  should be needed since the protocol already supports resumability.
- Explicitly handle the E2EE vault case: an in-progress encrypted upload's
  DEK/vault key material must never be persisted unencrypted across a
  reload — flag this to SEC.07 if the natural implementation would
  otherwise do so.
