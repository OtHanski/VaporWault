`TASK-00287`'s investigation concluded GPG signing for `.deb`/`.rpm`
packages is approved: low cost (a self-issued key), standard practice for
these formats.

## Acceptance criteria

- A GPG key generated for this project (implementer's call on key
  algorithm/size — a current-generation default, e.g. ed25519 or
  RSA-4096, is fine; document the choice and why).
- `release.yml`'s `build-linux` job signs the `.deb` and `.rpm` artifacts
  (or the repository metadata, if this project ever stands up a real
  `apt`/`dnf` repo — implementer's call on which is more valuable now vs.
  deferred) before upload.
- The public key published somewhere a downloader can actually find it
  (e.g. committed to the repo, linked from `docs/RELEASE.md` and/or the
  GitHub Release notes) — a signature nobody can verify against a known
  public key provides no real assurance.
- Private key material lives only in GitHub Actions secrets, never
  committed, never logged (check `release.yml`'s existing job output for
  accidental echo of secret values during signing).
- `docs/RELEASE.md`'s "These packages are unsigned today" section
  updated to describe the real signing process once implemented (key
  fingerprint, where to fetch the public key, how to verify).
- SEC.07 review before `done`, per the `security-sensitive` tag: key
  storage, scoping (does this secret need access from every workflow or
  only `release.yml`?), and a rotation story if the key is ever
  suspected compromised.
