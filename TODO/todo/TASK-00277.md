Full-project review (`TASK-00269`) found `ARCHITECTURE.md`'s
Implementation Phases table has drifted stale from actual `TODO/` state
three separate times (`2026-07-29` initial review, `TASK-00118`,
`TASK-00204`) — each time caught only by a manual backfill audit weeks
later, sometimes finding entire shipped phases missing a row entirely.
`ARCHITECTURE.md`'s own closing note (2026-08-26) already proposes the
real fix: add the phase row when the design task closes, not on a
periodic backfill pass. That proposal has never been formalized anywhere
agents would actually see it before closing a design task.

Separately, the same review's domain-density read found GUI.03 (22 tasks)
and WEB.09 (22 tasks) both mid-pack relative to SRV.01 (65) despite being
full UI surfaces, and that GUI audit-log/search/version-history views have
repeatedly landed *after* the corresponding protocol/server work rather
than in step. Worth naming as a scheduling pattern for future protocol-
touching phases, not a quality problem.

## Acceptance criteria

- `CLAUDE.md`'s "Step 8 — Milestone closure (ARCH.00)" (or a more
  appropriate step — implementer's call after re-reading the workflow
  section) gains an explicit instruction: update `ARCHITECTURE.md`'s
  Implementation Phases table in the same change that marks a design task
  `done`, not as a separate later pass.

  Workflow's Step 5 GUI integration section) that a protocol-touching

  alongside the SRV.01/CLI.02 ones, not as a reactive follow-up once a gap
  is later noticed — matching how `TASK-00185`'s breakdown already did
  this correctly (protocol → server → client → GUI → web, filed together).
- No change to the actual Status Lifecycle or TODO-folder rules — this is
  additive process guidance, not a rewrite of the existing protocol.
