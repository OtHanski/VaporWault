Discovered while building and testing `TASK-00299`'s IPC round-trip test
against a real `vapourwault-daemon` binary in this dev sandbox: switching
`update_policy` to `auto` makes the daemon's main loop call
`maybe_run_daily_auto_check()` (`TASK-00298`), which attempts a real,
un-test-hooked network fetch via `vw_update_net.c` -> `vw_net_connect_generic`
-> `src/core/vw_net.c`'s `connect_with_timeout()`. That single fetch attempt
stalled the entire daemon (and every IPC request queued behind it, since
this daemon is single-threaded by design) anywhere from ~16 seconds to
over 120 seconds across repeated runs in this same sandbox — wildly
inconsistent, and far longer than `VW_UPDATE_CONNECT_TIMEOUT_MS` (10000ms,
`vw_update_net.c`) would suggest is possible.

Root cause, read directly in `connect_with_timeout()`
(`src/core/vw_net.c:223-240`):

```c
if (getaddrinfo(host, port_str, &hints, &res) != 0 || !res)
    return MBEDTLS_ERR_NET_UNKNOWN_HOST;
```

`getaddrinfo()` is called with **no timeout at all** — the `timeout_ms`
parameter this function takes is only ever applied to the `select()` call
*after* DNS resolution has already completed (bounding the TCP connect
phase alone, via the non-blocking-connect-then-select pattern below it).
When DNS resolution itself is slow or the resolver can't reach a
nameserver (exactly this dev sandbox's networking), the OS resolver's own
internal retry/timeout behavior — which can run well past a minute
depending on platform and how many configured nameservers it retries —
runs to completion before this function's own bounded phase ever begins.
Every caller that believes "I passed a `connect_timeout_ms`, so this call
is bounded" is wrong when the target is a hostname (not a raw IP) and DNS
is slow: `vw_net_connect_generic()` is used both by the regular
client-server connection (`vw_client_core.c`, when `server_host` is
configured as a hostname) and by the update feature's outbound HTTPS
client (`vw_update_net.c`).

This is a real, if narrow, gap in the "bounded outbound connection"
property `TASK-00296`'s own SEC.07 review relied on (that review confirmed
the connect-phase timeout and TLS verification are both real and
enforced, but did not specifically test DNS-resolution slowness/failure —
neither should be read as having claimed this case was covered).

## Acceptance criteria

- `connect_with_timeout()`'s total wall-clock time (DNS resolution +
  connect) is bounded by (approximately) `timeout_ms`, not just the
  connect phase alone — verified with a real, slow/unresponsive DNS
  scenario in a test, not just by inspection.
- No behavior change for the fast/normal case (DNS resolves quickly).
- Consider whether a portable bounded-DNS approach (e.g. resolving on a
  helper thread with a timed wait, detaching it if the bound is hit —
  accepting a rare leaked/orphaned resolution as the cost of a hard
  bound) is warranted, or whether a narrower fix (e.g. skipping
  resolution entirely for the update feature's fixed, well-known hosts by
  trying literal-IP fast paths first) better fits this codebase's
  "minimal external dependencies" constraint — ARCH.00/CLI.02 to decide
  once the options are actually written out, not assumed here.
- SEC.07: confirm this doesn't reopen any DNS-rebinding/SSRF-shaped angle
  the fix's own approach might introduce (e.g. a background thread racing
  a cancellation).

## Notes

**CLI.02, 2026-09-16**: Found while implementing `TASK-00299`'s
integration test (`test_ipc_update.c`) — not fixed there; that test was
instead redesigned to never trigger this real code path in a way its own
pass/fail depends on (see that task's own notes for the workaround and
why). Filed here per the out-of-domain discovery routing rule rather than
fixed inline, since it's a pre-existing `TASK-00296`/core-`vw_net.c` issue
outside `TASK-00299`'s own scope, not something introduced by that task.

**CLI.02, 2026-09-16 — implementation**: Went with the detached-helper-thread
approach (the acceptance criteria's first option), matching this
codebase's existing detached-thread convention (e.g. `vw_cluster.c`'s
per-replica accept threads, `vw_server_main.c`'s worker pool) rather than
the narrower fixed-known-host fast path — `connect_with_timeout()` is
shared by both the update feature's fixed GitHub host and the regular
client-server connection when `server_host` is configured as an arbitrary
hostname, so a general fix was preferable to one scoped only to the
update feature.

Added `dns_resolve_bounded()` in `src/core/vw_net.c`: spawns a detached
thread that runs the real `getaddrinfo()` call and reports back through a
mutex/condvar-guarded context (`CRITICAL_SECTION`/`CONDITION_VARIABLE` on
Windows, `pthread_mutex_t`/`pthread_cond_t` with a `CLOCK_REALTIME`
absolute deadline on POSIX — this project targets Linux + Windows only,
see memory note on macOS being deferred, so no `CLOCK_MONOTONIC`
condattr portability concern). `connect_with_timeout()` now calls this
instead of calling `getaddrinfo()` inline. On timeout, the wait is
abandoned (`ctx->abandoned = 1`) rather than freed; the orphaned worker
thread frees its own context and any resolved `addrinfo` once (if ever)
`getaddrinfo()` itself returns — the accepted "rare leaked thread" cost
the acceptance criteria called out. The two sides never race on `ctx`
because both only touch it under the same lock: whichever side reaches
the lock first (the waiter timing out and setting `abandoned`, or the
worker finishing and setting `done`) determines which of the two mutually
exclusive cleanup paths runs.

No behavior change for `timeout_ms == 0` (unbounded — unchanged,
delegates to `mbedtls_net_connect` as before) or for the fast/normal case
where DNS resolves quickly (same connect-phase `select()` logic
afterward, untouched).

Added a test-only hook (`VW_NET_DNS_TEST_HOOK`, `vw_net_test_set_dns_resolver()`
in `vw_net.h`/`vw_net.c`) so a test can substitute a fake resolver — same
convention as `VW_UPDATE_NET_TEST_HOOKS`. New regression test
`tests/integration/test_net_dns_timeout.c` (target `test_net_dns_timeout`,
compiles `vw_net.c` directly with the hook macro rather than linking
`vw_core`'s un-hooked build of it):
- TC-1: a resolver that sleeps 3000ms before returning a valid address —
  `vw_net_connect_generic()` with `connect_timeout_ms=300` returns well
  under 2000ms (asserted), proving the wait itself is bounded, not just
  that resolution eventually succeeds.
- TC-2: a resolver that fails immediately — fails promptly, no timing
  regression.
- TC-3: no hook installed — the real `getaddrinfo()` fast path (numeric
  loopback address, refused port) is unaffected, same case as
  `test_vw_net.c`'s TC-6.

Verified locally (WSL, gcc, `-DVW_WERROR=ON`): full test suite (35/35,
unit + integration) passes, including `integration_net_dns_timeout` and
`integration_ipc_update` (TASK-00299/TASK-00306's own test, which
exercises this same code path via the daemon's real auto-check —
confirms no regression there either).

Left for SEC.07/CQR.08 review per this task's own acceptance criteria:
confirm the abandon/detach approach doesn't reopen a DNS-rebinding/SSRF
angle (it doesn't change *what* gets resolved or *how* the result is
validated — only *how long* the caller waits for it — but flagging for
independent confirmation per the task's own ask), and general
correctness review of the mutex/condvar lifecycle and platform code.
