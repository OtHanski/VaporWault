Found during the CQR.08/SEC.07 review pass on `TASK-00275` (`VAULT_DELETE`).
Disclosed as a known limitation there rather than fixed, since a correct
fix needs real cross-module lock design, not a rushed same-session patch.

`handle_file_commit`'s vault validation (`vw_file_handlers.c` ~line 1157)
reads and releases `vw_vault_store_t`'s lock via `vw_vault_get_by_id`,
then commits the version under a *different* lock
(`vw_file_store_t.versions_lock`, via `vw_store_version_create`) — no lock
is held across both steps. A concurrent `VAULT_DELETE` on the same vault
can land in that window: the vault gets marked deleted after `FILE_COMMIT`
already validated it but before the version record referencing it is
written, permanently stranding that version's `wrapped_dek` — the exact
data-loss mode `VAULT_DELETE`'s not-empty check (`TASK-00275`) exists to
prevent, just reached via a race instead of the ordinary path.

**Not a cross-user attack**: both operations require the *same* account's
ownership (`VAULT_DELETE` checks `owner_id`; `FILE_COMMIT`'s vault check
requires `vault_rec.owner_id == file_rec.owner_id`), so this needs two
operations from one account (e.g. two devices, or a daemon and a
concurrent CLI session) racing each other — not an attacker with no
relationship to the vault. Tagged `security-sensitive` for the
crypto/data-integrity angle (a stranded `wrapped_dek` is permanent,
unrecoverable data loss of encrypted content), not because it's
exploitable cross-account.

## Design considerations for the fix

- `vw_vault.c` is deliberately kept free of any `vw_store_files.h`
  dependency (its own header comment) — a fix that makes `vw_vault.c`
  directly aware of `vw_file_store_t` internals would break that
  separation. Consider instead: a lock/coordination point that lives in
  `vw_file_handlers.c` (which already has both handles) rather than
  pushing the dependency into either storage module.
- Two independently-locked modules (`vw_vault_store_t`'s lock,
  `vw_file_store_t`'s `versions_lock`) means any fix that holds both
  locks simultaneously must pick a strict, consistent acquisition order
  used everywhere both are held together, or introduces deadlock risk —
  this is the reason this task exists separately rather than a quick
  same-session patch during `TASK-00275`.
- One plausible direction: an in-memory "vault currently being written
  to" refcount/pin on the vault record (incremented by `FILE_COMMIT`
  before its vault check, decremented after the version write commits or
  aborts), with `VAULT_DELETE`'s not-empty check treating a nonzero pin
  count the same as `VW_ERR_VAULT_NOT_EMPTY`. Sketch only — verify this
  doesn't just move the race (e.g. a pin taken after `VAULT_DELETE`'s
  check but before its own delete-write) before implementing.

## Acceptance criteria

- A real fix, or a well-reasoned decision that the risk is acceptable to
  leave disclosed permanently (recorded in `ARCHITECTURE.md` if so, not
  left as a task forever) — either outcome closes this task, but "closed
  by writing a fix that turns out to have the same race under a different
  name" does not.
- A regression test that actually exercises the race (e.g. via a test
  hook or artificial delay at the vulnerable window) if a fix is
  implemented — asserting the fix's absence of the race by inspection
  alone is not sufficient for a data-loss-shaped bug.
- SEC.07 sign-off given the `security-sensitive` tag and the
  wrapped_dek-permanence angle.

## Notes

SRV.01 [2026-09-11]: Filed from the `TASK-00275` review pass. Disclosed,
not fixed, in that task — see its own notes for the full reasoning on
why a same-session fix was judged too risky (deadlock potential) to

SRV.01 [2026-09-14]: Fixed, following this task's own "in-memory pin
count" sketch, with the deadlock risk it flagged designed out rather
than just avoided by luck.

**Design**: `vw_vault_store_t` gains an in-memory-only `pin_counts`
array, dense-indexed by `vault_id` in lockstep with its existing
`vid_to_slot` (same capacity, grown/freed/swapped together everywhere —
`vid_to_slot_ensure`, `vw_vault_store_close`, `vw_vault_store_reload`).
Two new public functions:

- `vw_vault_pin_if_exists(vs, vault_id, out_rec)` — a single critical
  section (one write-lock acquisition) that replaces what used to be a
  separate `vw_vault_get_by_id` check: confirms the vault exists and
  isn't deleted, and increments its pin count, atomically. This is what
  actually closes the TOCTOU — the old code's "check exists" and "the
  caller does something based on that" were two separate steps with no
  lock held across both.
- `vw_vault_unpin(vs, vault_id)` — releases one pin; safe no-op if none
  outstanding.

`vw_vault_delete` gained one new check, under the SAME lock as the
existing owner/deleted checks and the delete write itself: refuses with
`VW_ERR_VAULT_NOT_EMPTY` if `pin_counts[vault_id] > 0`. Since pinning
and this check share one lock, there is no window for a new pin to land
between "check pin count" and "mark deleted," and no window for
`vw_vault_pin_if_exists` to succeed against a vault that
`vw_vault_delete` just marked deleted — both directions of the race are
closed by the same single lock, not by timing.

`handle_file_commit` (`vw_file_handlers.c`) now calls
`vw_vault_pin_if_exists` instead of `vw_vault_get_by_id` where it
validates a commit's `vault_id`, and unpins on every exit path from
that point until `vw_store_version_create` returns (both its own
`is_new`/`vw_store_file_create` failure branch, and unconditionally
right after `vw_store_version_create` itself returns, success or
failure) — the version record's durability is exactly the moment
`vw_store_version_vault_in_use`'s ordinary scan takes over as the
vault's protection, so the pin's job ends there.

**No deadlock risk, verified by construction, not just inspection**:
`vw_vault.c` never became aware of `vw_file_store_t` (the pin/unpin API
is generic — "protect this vault_id for a while," no version/file
concept crosses the boundary), and `vw_vault_store_t`'s lock is never
held at the same time as `vw_file_store_t`'s `versions_lock` — each of
`vw_vault_pin_if_exists`/`vw_vault_unpin`/`vw_vault_delete` is its own
brief, self-contained critical section, with ordinary (lockless w.r.t.
the vault store) `vw_file_store_t` work happening in between. There is
exactly one lock in play at any instant from this fix's perspective.

**Regression test** (`tests/unit/test_vw_vault.c`, 4 new cases, 19 new
assertions): directly drives the race deterministically rather than
relying on real thread timing — `vw_vault_pin_if_exists` then
`vw_vault_delete` and assert `VW_ERR_VAULT_NOT_EMPTY`, then `vw_vault_
unpin` then `vw_vault_delete` and assert success; a second case checks
the pin count is a real counter (two pins need two unpins); plus
NOT_FOUND/no-op edge cases. Verified these tests actually catch the
regression by temporarily short-circuiting `vw_vault_delete`'s new pin
check (`if (0 && ...)`) — confirmed 5 assertions fail exactly as
expected (vault gets deleted while pinned) — then reverted and confirmed
a clean pass again. Full suite green afterward: `ctest` 26/26,
`test_vault.py` 18/18 (gateway-dependent cases correctly skipped in this
particular build, which wasn't configured with `VW_BUILD_WEB_GATEWAY`;
not exercised by this fix anyway).

No wire/protocol change (in-memory-only fix on both sides of the pin);
`docs/PROTOCOL.md` untouched. `ARCHITECTURE.md`: no new row needed — an
internal race-condition fix, not a design decision surfacing a new
tradeoff.

Moving to `review` for SEC.07 + CQR.08 per the `security-sensitive` tag.
