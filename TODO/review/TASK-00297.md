New files `src/client/vw_update_manifest.c`/`.h`.

## Manifest schema (`update-manifest.json`, published by `TASK-00301`)

```json
{
  "schema_version": 1,
  "sequence": 7,
  "release_version": "0.4.2",
  "min_client_protocol_version": 6,
  "published_at": 1757900000,
  "assets": [
    { "platform": "linux",   "arch": "x86_64", "dist_kind": "portable", "filename": "vaporwault-v0.4.2-linux-x86_64.tar.gz",   "sha256": "..." },
    { "platform": "windows", "arch": "x86_64", "dist_kind": "portable", "filename": "vaporwault-v0.4.2-windows-x86_64.zip",     "sha256": "..." }
  ]
}
```

## Parser

Hand-rolled, scoped to exactly these 6 fields (not `vw_json.c` — see
`ARCHITECTURE.md`'s "Client auto-update: manifest parser" row for why). No
general-purpose JSON semantics needed: fixed key set, no nesting beyond the
one flat `assets` array, no need to handle arbitrary input shapes gracefully
beyond rejecting anything that doesn't match.

## Verify-then-parse pipeline

```c
vw_err_t vw_update_manifest_fetch_and_verify(vw_update_manifest_t *out);
```

Mandatory order, never reversed:
1. `vw_update_https_get("github.com", ".../update-manifest.json", ...)`
   (small cap, e.g. 64 KiB).
2. `vw_update_https_get(..., "update-manifest.json.sig", ...)` — the
   detached ECDSA signature (raw bytes, small cap).
3. `vw_crypto_ecdsa_p256_verify()` over `SHA256(manifest_bytes)` against
   `VW_UPDATE_MANIFEST_PUBKEY` — **fail closed** on any error.
4. Only then parse the now-trusted bytes with the hand-rolled parser.
5. Rollback check: read `update_last_seen_sequence` from
   `{state_dir}/daemon.conf`. If `manifest.sequence < persisted`, return
   `VW_ERR_UPDATE_MANIFEST_ROLLBACK` and do nothing further. Else,
   **immediately** persist `manifest.sequence` as the new ratchet value
   (before evaluating whether an update is actually relevant) — the ratchet
   only needs a validly-signed manifest to have been seen.

`published_at` is informational only — never used in a trust decision (no
clock-based logic anywhere in this pipeline, deliberately, to avoid
clock-skew bug classes).

## Acceptance criteria

- Unit tests: valid manifest+sig verifies and parses correctly; tampered
  manifest bytes (signature no longer matches) rejected before parsing ever
  runs; malformed JSON-shaped-but-wrong-schema payload rejected by the
  parser; a validly-signed manifest with `sequence` below a pre-seeded
  ratchet value rejected with `VW_ERR_UPDATE_MANIFEST_ROLLBACK`; ratchet
  correctly advances on a validly-signed higher-sequence manifest even when
  the caller never proceeds to install anything.
- Fuzz target for the hand-rolled parser (it will see attacker-influenced
  bytes, even though those bytes are signature-verified first — defense in
  depth, matches the project's existing fuzz-testing practice for protocol
  parsers).
- SEC.07 review: confirm verify-before-parse ordering is actually enforced
  in code, not just documented; confirm no path exists where parsed-but-
  unverified data is ever acted on.

## Notes

CLI.02 [2026-09-15]: Implemented as designed, with one API addition beyond
the brief and one design decision found necessary for the ratchet's
storage.

- New `src/client/vw_update_manifest.{c,h}`: `vw_update_manifest_fetch_and_verify()`
  implements the mandatory order exactly as specified (fetch manifest →
  fetch detached `.sig` → SHA-256 + ECDSA verify over the raw bytes →
  *only then* parse → rollback check → persist ratchet). Deviates from the
  brief's literal signature by taking `state_dir` as a parameter — the
  function cannot locate `daemon.conf` to read/persist the ratchet
  without it, and the original sketch omitted any way to pass it in.
- **New public entry point beyond the brief**: exposed the parser itself
  as `vw_update_manifest_parse(data, len, out)`, separate from the fetch
  pipeline, specifically so `tests/fuzz/fuzz_update_manifest.c` (this
  task's own acceptance criterion) can fuzz the parser in isolation
  without needing a real network fetch. Documented in the header as
  never performing signature verification itself and never to be called
  on unverified bytes outside a test/fuzz harness.
- **Ratchet storage**: `daemon.conf`'s own key=value format
  (`vw_daemon.c`) is deliberately *not* reused via a shared struct/API —
  `vw_daemon_cfg_t` is private to that module, matching this project's
  existing module-boundary discipline (`vw_vault.c`'s own header comment
  on staying free of `vw_store_files.h`). Instead, `vw_update_manifest.c`
  does its own minimal, self-contained read/rewrite of exactly the
  `update_last_seen_sequence` key, preserving every other line in the
  file untouched (read via `vw_fs_read_file`, written via
  `vw_fs_atomic_write` for crash-safety — stronger durability than
  `vw_daemon.c`'s own plain `fopen("w")` for its keys, a pre-existing,
  separate, out-of-scope concern).
- Parser: hand-rolled, key-order-independent (loops reading `"key": value`
  pairs and dispatching by name, rather than assuming the CI generator's
  exact field order) — costs little extra code over strict-order parsing
  and avoids coupling the parser to `TASK-00301`'s generator internals.
  Unknown top-level or asset-level fields are rejected outright, not
  silently ignored. `sha256` hex strings are validated to be exactly 64
  characters and hex-decoded into raw 32-byte form for direct comparison
  against `vw_crypto_sha256_file`'s output (`TASK-00298`'s job).

**Real debugging note, for the record**: while writing the integration
test, two of five hand-typed test-manifest fixtures initially failed with
`VW_ERR_UPDATE_MANIFEST_INVALID` in a way that looked exactly like a
production signature-verification bug. Traced end-to-end (wire-byte
capture + independent `openssl dgst -verify`, confirming the fetched
bytes and signature were byte-identical to what was actually signed, and
a temporary debug print showing `vw_crypto_ecdsa_p256_verify` itself
returning `VW_OK`) to the *test fixtures themselves*: two hand-typed
`sha256` hex strings had 62 `c`/`d` characters instead of 64, which the
parser's own length check correctly rejected — i.e., this was the
parser's schema validation working exactly as designed, not a bug in it
or in the crypto layer. Regenerated both fixtures with the real
update-manifest private key (still in local scratch from `TASK-00293`,
verified against the real compiled-in `VW_UPDATE_MANIFEST_PUBKEY`, not a
test substitute) and fixed the byte counts; all temporary diagnostics
removed before finalizing. Noted here since it's exactly the kind of
"looked like a real finding, verify before reporting" moment worth
recording, not because it reflects a production defect.
