Full-project review (`TASK-00269`) confirmed a disclosed limitation from
`TASK-00205`: there is no real signal for "N accounts are currently
running against a fallback replica" — only an approximate `replica_lag`
proxy alert. The client-side automatic fallback feature (`TASK-00169`–178,
`ARCHITECTURE.md`'s "Client-side automatic fallback" decision row) has no
mechanism today for a fallback-connected client or gateway session to
report that state back to the primary or to an admin view.

## Design

- Decide the reporting path: does a client/gateway session report its
  fallback state to the *replica* it's connected to (which then needs to
  relay it to the primary somehow — no such replica→primary channel
  exists today outside the cluster's own `NODE_HELLO` session), or does
  the primary infer it indirectly? Read `vw_cluster.c`'s existing
  primary↔replica message set (§7.7) before proposing a new one — reusing
  the existing authenticated cluster session (like `TASK-00170`'s
  `CLUSTER_RECORD_FETCH` and `TASK-00257`'s `CLUSTER_CHUNK_REPAIR_FETCH`
  both did) is the established pattern here, not a new credential.
- Decide what "currently on fallback" means precisely for a session that
  reconnects to the primary mid-session versus one that stays parked —
  avoid designing a signal that's stale the instant it's read.
- Published in `docs/PROTOCOL.md`, following the existing "purely
  additive, no version bump unless an existing byte layout changes"
  convention wherever possible.

## Acceptance criteria

- Design published; no implementation in this task (`TASK-00285`).

## Notes

ARCH.00 [2026-09-10]: Filed from the full-project review (`TASK-00269`).

PRT.04 [2026-09-11]: Design published (`docs/PROTOCOL.md` revision 34).

- Reporting path: piggybacked a new `client_conn_count` (uint32) field
  onto the existing `OPLOG_ACK` (replica → primary), reusing the
  authenticated `NODE_HELLO` cluster session already established for
  this exact purpose by `TASK-00170`/`TASK-00259` — no new message pair,
  no new credential.
- Read `vw_conn_registry.h` before designing: a replica's connection
  registry already tracks every live `vw/1` client connection (used
  today by the admin `CONN_LIST` query) and — confirmed — never includes
  admin-socket connections, which are a separate `AF_UNIX` path
  entirely. Combined with this project's fallback design (one primary +
  optional one fallback per account, `ARCHITECTURE.md`'s "Client-side
  automatic fallback" row), a live connection to a replica's normal
  listener *is* a fallback-parked client by construction — no new
  session-tagging needed to tell fallback and non-fallback connections
  apart on a replica.
- Staleness handled explicitly: bounded by `replica_poll_interval_secs`
  (default 5s), same freshness bound `lag_entries` already carries — not
  designed to be instantaneous, an admin gauge not a correctness signal.
- `CLUSTER_STATUS_RESP`'s per-node entry gains the same field, sourced
  from the primary's most recently received `OPLOG_ACK` per node.
- Purely additive, no protocol version bump — old/new replica and
  primary combinations degrade to "field absent/zero," never misread.

No implementation in this task — `TASK-00285` (already filed, blocked on
this one) covers threading `vw_conn_registry_t` into `vw_cluster_open`
(a new borrowed-handle parameter, same pattern as the existing
`store`/`file_store`/`chunks`/`share_store`/`vault_store` params — no
init-ordering change needed, `vw_server_main.c` already opens the
registry first) and surfacing the count in an admin view.
