Implements `TASK-00274`'s `VAULT_DELETE`/`_ACK` design.

## Changes

- `src/server/vw_vault.h`/`.c`: `vw_vault_record_t` gains a `deleted`
  flag (carved from the old `_pad[32]` → `_pad[31]`, struct still exactly
  96 bytes; a record written before this field existed reads back
  `deleted == 0` for free, same zero-fill-compat reasoning as every prior
  `_reserved`-repurposing in this codebase — no migration needed). New
  `vw_vault_delete(vs, vault_id, caller_user_id)`: in-place `pwrite` of the
  flag (mirrors `vw_share_revoke`'s exact pattern), owner-checked,
  oplog-recorded. `vw_vault_get_by_id`/`vw_vault_scan` updated to treat a
  deleted vault as gone (`VW_ERR_NOT_FOUND` / excluded from scan
  respectively).
- `src/server/vw_oplog.h`: new `VW_OPLOG_VAULT_DELETE` (0x0B) — a
  **distinct** op type from `VW_OPLOG_VAULT_WRITE`, not a reused one;
  reusing one ambiguous op type for two different operations is exactly
  the mistake `VW_OPLOG_FILE_WRITE`'s own retirement (`TASK-122`)
  documents and this avoids repeating.
- `src/server/vw_store.h`/`vw_store_files.c`: new
  `vw_store_version_vault_in_use(fs, vault_id, &out_in_use)` — full
  version-table scan (same accepted O(n) tradeoff as `vw_vault_scan`/
  `vw_share_scan` at this project's scale) backing the not-empty check.
- `src/server/vw_file_handlers.c`: new `handle_vault_delete()`, wired into
  the dispatch table and into `is_write_shaped_msg()` (so
  `VW_ERR_READ_ONLY_REPLICA` rejects it on a replica, matching
  `VAULT_CREATE`'s existing treatment).
- `src/gui/server/views/vw_view_audit.cpp`: audit-log label/filter
  plumbing for the new `VW_OPLOG_VAULT_DELETE` op type (label, filter
  dropdown entry, owner-id payload decode) — small, necessary so the new
  audit event doesn't silently show as "Unknown"; the actual GUI *action*
  to trigger a delete is `TASK-00279`'s separate scope.
- `src/core/vw_proto.h`: `VW_MSG_VAULT_DELETE`/`_ACK`,
  `VW_ERR_VAULT_NOT_EMPTY`.
- `ARCHITECTURE.md`: new Architectural Decisions row ("Vault deletion").
- `tests/unit/test_vw_vault.c`: new cases — delete removes a vault from
  `get_by_id`/`scan`; delete rejects a non-owner with `PERMISSION`; delete
  on an unknown/already-deleted vault returns `NOT_FOUND`; plus a
  `test_vw_store_files`-shaped case in the same file for
  `vw_store_version_vault_in_use` (finds a live reference, ignores
  unrelated `vault_id`s).

## Acceptance criteria

Deliberately conservative on the not-empty check: it refuses deletion if
*any* version (current or superseded) still references the vault, not
just the current version. A client must ensure every file under the
vault's folder is actually deleted (and, once trash-retention exists for
vault content, purged past that window) before `VAULT_DELETE` succeeds.

**Correction, found by SRV.01 while implementing `TASK-00280` [2026-09-11]:**
`handle_vault_delete`'s not-empty rejection originally called the generic
`send_error(conn, VW_ERR_VAULT_NOT_EMPTY)` — sending a `VW_MSG_ERROR`
(8-byte payload: code + a zero message length, via
`vw_proto_encode_error`) instead of embedding the code in a
`VAULT_DELETE_ACK` (4-byte `error_code` payload), unlike
`handle_share_or_link_revoke`'s pattern this task's own comment claimed
to follow. This broke `vw_client_core.c`'s `revoke_common()` — its
4-byte `rbuf[4]` (sized for the ACK it expected) was too small for the
8-byte `VW_MSG_ERROR` payload, so `vw_proto_recv` failed with
`VW_ERR_PROTO_TOO_LARGE` (202) before the real error code was ever read.
The unit tests here (calling `vw_vault_delete`/`vw_store_version_vault_in_use`
directly) and the wire-level Python test (`vw_client.py`'s `_recv()` uses
a generic large buffer with no such size assumption) both passed anyway —
neither exercises the actual C client path a real desktop/gateway client
uses. Only `test_gateway.py`'s real end-to-end test (`TASK-00280`, using
`vw_client_core.c` for real, the way the gateway and desktop client both
do) caught it — the response the browser client actually saw was a
generic 500 that would have logged the browser out on every rejected
delete, not the intended 409 `vault_not_empty`.

Fixed by folding the not-empty check and `vw_vault_delete`'s result into
the same single ACK-embedding return path the truncation/not-implemented
checks already didn't use `send_error` for — see the updated function
comment in `vw_file_handlers.c`. Re-verified: full `-Werror` rebuild,
`test_vw_vault` (98/98), `test_vault.py` (17/17), and `test_gateway.py`
(40/40, including 3 new `VAULT_DELETE` gateway tests) all pass. Lesson
recorded for future review: a unit test exercising the storage function
directly and a wire-level test using a generic buffer are not a
substitute for one real end-to-end test through the actual client
library a real consumer uses.

**SEC.07/CQR.08 review pass [2026-09-11], second finding — fixed:**
`handle_vault_delete()` originally called `vw_store_version_vault_in_use()`
(no caller identity) before checking ownership via `vw_vault_delete()`,
so any authenticated user could enumerate small `vault_id` integers and
learn whether another user's vault currently holds live encrypted
content, before any permission check ran. Fixed by checking ownership
first (`vw_vault_get_by_id` + owner compare, matching `VAULT_KEY_FETCH`'s
pattern) — see `495c365`. New test:
`test_vault_delete_ownership_checked_before_not_empty_leaks_nothing`.

**Disclosed limitation, not fixed in this pass — TOCTOU race between
`VAULT_DELETE` and `FILE_COMMIT`:** `handle_file_commit`'s vault
validation (`vw_vault_get_by_id`, line ~1157) reads and releases
`vw_vault_store_t`'s lock, then commits the version under a *different*
lock (`vw_file_store_t.versions_lock`, `vw_store_version_create`) with no
lock held across both steps. A concurrent `VAULT_DELETE` on the same
vault can land in that window: the vault gets marked deleted after
`FILE_COMMIT` already validated it but before the version record
referencing it is written, permanently stranding that version's
`wrapped_dek` — the exact data-loss mode the not-empty check exists to
prevent, just reached via a race instead of the ordinary path. **Not a
cross-user attack**: both `VAULT_DELETE` and `FILE_COMMIT`'s vault check
require the *same* account's ownership, so this needs two operations
from one account (or account+device pair) racing each other, not an
attacker with no relationship to the vault. Deliberately not fixed here:
a correct fix needs real cross-module lock-ordering design between
`vw_vault.c` and `vw_store_files.c` (two independently-locked modules,
`vw_vault.c`'s own header comment states it's kept deliberately free of
any `vw_store_files.h` dependency) — attempting a same-session fix risked
introducing a deadlock, a worse outcome than a narrow, same-account race
window. Filed as `TASK-00290` for a properly-designed fix rather than
rushed. Not blocking this task's `done` transition: the risk is bounded
(self-inflicted, narrow timing window, no cross-user exposure), and
recording a disclosed-but-unfixed limitation matches this project's own
established practice (e.g. Phase 21's disclosed vault/sharing
cross-client interop gap) rather than either silently shipping it or
blocking review indefinitely on a fix that deserves its own design pass.

**Advisory, not fixed — code duplication found by CQR.08, deferred as
follow-up rather than refactoring already-shipped, unrelated code in this
pass:** `vw_vault_delete()` re-implements `vw_vault_get_by_id()`'s
slot-resolution/read/validate sequence instead of sharing it; the
gateway's `handle_vault_delete()`/`handle_share_revoke()`/
`handle_link_revoke()` triplicate the same
require_session/reject_if_read_only/error-mapping skeleton. Both are real
duplication, but factoring either out touches already-shipped
`share`/`link` code paths beyond this task's scope — worth a dedicated
consistency pass across all three id-action handlers/lookups at once
rather than piecemeal. Not filed as a task yet; flagging here so it isn't
lost.

**Advisory, accepted as-is — `vw_store_version_vault_in_use`'s full linear
scan:** CQR.08 correctly noted this scans every version slot ever
allocated (unboundedly growing, append-only, never compacted), a
different scale class than `vw_vault_scan`/`vw_share_scan`'s own accepted
O(n) tradeoff (bounded by vault/share count). Accepted rather than fixed:
`VAULT_DELETE` is a rare, low-frequency administrative action, not a hot
path, and this project's existing scans already accept O(n) tradeoffs at
its stated self-hosted-personal-scale target. Worth revisiting only if
this store's version count ever grows large enough for a real user to
notice `VAULT_DELETE` latency — not a reason to add an index preemptively.
