Discovered out-of-domain while getting Phase 22's PR (#2,
`phase22-corruption-detection-repair`) green: CI's "Integration / Linux /
gcc / Release" job failed on
`tests/integration/test_notify_alerts.py::test_user_category_quota_warning_edge_triggers_and_rearms`
with `assert len(smtp.messages) == 1` actually getting 2 — i.e. the
`quota_warning` admin/user alert fired twice for what the test expects to
be a single 90%-threshold crossing.

Confirmed **not** a Phase 22 regression: `git diff main` for this PR
touches nothing in `vw_notify.c`'s `quota_debounce_entry_t`/
`debounce_find_or_add`/`vw_notify_quota_hook` (Phase 22 only *adds* a new,
separate `chunk_unrepairable` category and its own independent debounce
ring — no shared state, no shared code path with the quota debounce
logic). Re-ran the exact same test locally 3/3 times against a real WSL
build with no failure. Re-running the failed CI job itself (`gh run
rerun --failed`) is the immediate unblocking step for the PR; this task
is to actually root-cause the underlying flake rather than just letting
the re-run paper over it.

**Working hypothesis, not yet confirmed**: the failing run's daemon log
showed `sync cycle for '<user>' had 1 action error(s)` right around the
same window as the double-fire — `vw_daemon.c`'s own comment on this
counter ("fold in per-action failures (e.g. quota rejections) that
vw_sync_run itself treats as non-fatal") suggests the upload of the
test's `big1.bin` (9500 of a 10000-byte quota) needed two attempts: one
that failed non-fatally after **partially** charging quota (e.g. a
chunk successfully `PUT` and ref-counted, crossing the 90% threshold and
firing the debounce's first email, followed by a `FILE_COMMIT` failure
that's never retried at the chunk level but leaves the file unmarked as
synced in the client cache), then a full retry on the next ~200ms sync
cycle that re-uploads from scratch. If that retry path causes the
chunk's reference (and therefore `used_bytes`) to be released and
re-acquired rather than reused, that would be a **second, genuine**
90%-threshold crossing — the debounce firing twice would then be
correct behavior for two real crossings, not a bug in the debounce logic
itself; the actual defect (if this hypothesis holds) would be an
asymmetric charge/release around a failed `FILE_COMMIT` retry, unrelated
to `vw_notify.c` entirely.

This has not been seen in the CI history sampled while triaging PR #2
(checked several dozen recent `main`-branch runs of this same
`integration` job; no prior occurrence of this specific test/assertion
in the failure logs found) — so either genuinely rare (a CI-runner-load-
dependent timing window that essentially never reproduces locally, per
the 3/3 local pass above) or newly exposed by unrelated recent change.
Worth checking `git log` on `vw_sync.c`/`vw_client_core.c`/the server's
`FILE_COMMIT`/quota-charge path for anything landed since the last time
this exact CI job is known to have run clean, in case something already
shipped narrowed the timing window that makes this reproducible.

## Acceptance criteria

- Root cause identified: either (a) a real asymmetric quota charge/
  release bug around a retried `FILE_COMMIT` (fix it, plus a regression
  test that deliberately forces the retry path), or (b) confirmation
  that two crossings really can legitimately happen for one logical
  upload under retry, in which case `test_user_category_quota_warning_
  edge_triggers_and_rearms`'s assertion (`len(smtp.messages) == 1`) is
  measuring an invariant the system never actually promised, and should
  be relaxed (e.g. assert `>= 1` for the crossing, keep the existing
  re-arm-then-recross assertions as-is) rather than left flaky.
- Either way: a regression test that reliably exercises whichever
  behavior is confirmed correct, not just a hope that CI stays fast
  enough to avoid the timing window.
- No unrelated behavior change to `vw_notify.c`'s debounce logic itself
  unless investigation actually finds a bug there (current reading is
  that it's correct — see this task's own analysis above).

## Notes

SRV.01 [2026-09-14]: Root-caused. Outcome (a) — two real bugs found and
fixed in `vw_storage.c`, both in `chunk_put_impl`/`vw_storage_gc_run`,
nothing in `vw_notify.c`'s debounce (confirmed correct, as this task's
own prior analysis predicted). `docs/PROTOCOL.md` untouched — neither
bug is wire-visible.

**Bug 1 — permanent quota double-charge on a retried/racing chunk_put.**
`chunk_put_impl`'s `entry && entry->ref_count == 0` branch (reached after
releasing the lock for disk I/O and re-acquiring it) was labeled
"previously GC'd entry — reuse its slot" and charged quota again
unconditionally. That label was wrong: `vw_storage_gc_run`'s Phase A
fully erases a collected hash from the in-memory table
(`memset(hash, 0)`), so `ht_find` can never return a non-NULL entry for
a genuinely GC'd hash — a GC'd-and-reused hash always takes the "truly
new" append path with a fresh slot instead. The only way to reach this
branch is a second `chunk_put_impl` call for a hash whose first call
already inserted a `ref_count == 0` entry (a real upload sits at
`ref_count == 0` between `CHUNK_UPLOAD` and its `FILE_COMMIT` addref,
per TASK-180) — i.e. a client retry or a race against the SAME in-flight
upload. Charging quota there double-charged a single logical upload,
permanently (nothing ever rolled it back). Fixed by making this branch
behave exactly like the sibling `ref_count > 0` race branch: a no-op
presence-check for a real upload, a bump for the replicated path
(which never actually reaches this branch — a replicated write always
inserts at `ref_count == 1`).

**Bug 2 — GC racing a legitimate, merely-slow in-flight upload.** Even
with bug 1 fixed, `vw_storage_gc_run`'s Phase A was free to collect a
chunk sitting at `ref_count == 0` awaiting `FILE_COMMIT` the moment GC
next ran, safe only so long as `gc_interval_secs` comfortably exceeds
every real upload round trip (TASK-180's own stated assumption).
`test_notify_alerts.py`'s shared `_notify_conf` sets `gc_interval_secs =
2` (needed by the `disk_capacity` admin tests, and — I initially
missed this — also needed by this very test itself, since quota is
only ever freed when GC deletes a zero-ref chunk from disk, so the
delete-then-recross phase depends on a prompt GC pass too; first
attempted a fix that widened `gc_interval_secs` for this test alone and
it deadlocked the *second* crossing instead, since quota was then never
reclaimed after the delete — reverted, see below). Under real CI load, a
`FILE_COMMIT` delayed past 2s let GC collect the still-wanted chunk,
decrementing quota (silent re-arm) and failing the pending addref with
`NOT_FOUND` — confirmed directly: server log showed the real upload
sequence (`CHUNK_UPLOAD` → `FILE_COMMIT`, both `rc=0`) succeed once,
then a continuous `WARN sync cycle ... had 1 action error(s)` every
200ms cycle thereafter once I (mis-)widened the interval, which is the
client retrying a commit that can never succeed once its chunk keeps
getting collected — the same shape as the real CI failure's `1 action
error(s)` log line, just persistent instead of a single crossing.
Fixed with an explicit, in-memory-only grace period
(`gc_grace_entry_t`, default 30s) independent of `gc_interval_secs`:
a real upload is protected from Phase A until the grace deadline, the
deadline is cleared the moment `vw_storage_chunk_addref` gives it a
real reference (so a genuine delete afterward is immediately
GC-eligible again — the quota_warning test's delete-then-recross step
still completes within its 20s wait), and an upload that's genuinely
abandoned (never committed) is still collected once its grace expires.
Test-only override: `vw_storage_set_gc_grace_secs_for_test`.

**Verification**: both bugs confirmed to actually matter by temporarily
reverting each fix in isolation and watching the corresponding new unit
test fail (double-charge branch reverted → `q.used_bytes` assertion
failed with the double amount; grace check disabled →
`vw_storage_chunk_get` after `vw_storage_gc_run` returned
`VW_ERR_NOT_FOUND` instead of `VW_OK`), then re-applying the real fix
and confirming a clean pass. New regression suite
`tests/unit/test_vw_storage_gc.c` (50 assertions, registered as
`unit_vw_storage_gc` in `tests/unit/CMakeLists.txt`) covers: no
double-charge on a retried `chunk_put`; a not-yet-committed chunk
survives a GC pass within its grace window and its pending addref still
succeeds; a genuinely abandoned upload is still collected once grace
expires and its quota reclaimed; a real committed-then-deleted chunk is
collected on GC's very next pass regardless of a long grace period.
`test_notify_alerts.py::test_user_category_quota_warning_edge_triggers_and_rearms`
itself: 8/8 clean runs locally against a real WSL build (previously
observed failing in real CI logs at exactly the first
`assert len(smtp.messages) == 1`, i.e. two emails from one logical
90%-crossing). Full existing suite unaffected: `ctest` 26/26,
`test_notify_alerts.py` 10/10, `test_gc.py`/`test_quota.py`/
`test_file_ops.py` 15/15, `test_shared_sync*`/`test_cli_*sync*` 5/5, all
against a `-Werror` clean full rebuild.

`docs/PROTOCOL.md`/wire format untouched (`refcount_record_t`'s on-disk
48 bytes unchanged — the grace deadline is in-memory only, lost and
irrelevant across a server restart, matching the existing tolerance for
that edge case already accepted by TASK-180). No `ARCHITECTURE.md`
decision row needed — this is an internal implementation-detail fix,
not a design decision.
