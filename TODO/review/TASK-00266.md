Discovered out-of-domain while getting Phase 22's PR (#2,
`phase22-corruption-detection-repair`) green: CI's "Integration / Linux /
gcc / Release" job failed on
`tests/integration/test_notify_alerts.py::test_user_category_quota_warning_edge_triggers_and_rearms`
with `assert len(smtp.messages) == 1` actually getting 2 — i.e. the
`quota_warning` admin/user alert fired twice for what the test expects to
be a single 90%-threshold crossing.

Confirmed **not** a Phase 22 regression: `git diff main` for this PR
touches nothing in `vw_notify.c`'s `quota_debounce_entry_t`/
`debounce_find_or_add`/`vw_notify_quota_hook` (Phase 22 only *adds* a new,
separate `chunk_unrepairable` category and its own independent debounce
ring — no shared state, no shared code path with the quota debounce
logic). Re-ran the exact same test locally 3/3 times against a real WSL
build with no failure. Re-running the failed CI job itself (`gh run
rerun --failed`) is the immediate unblocking step for the PR; this task
is to actually root-cause the underlying flake rather than just letting
the re-run paper over it.

**Working hypothesis, not yet confirmed**: the failing run's daemon log
showed `sync cycle for '<user>' had 1 action error(s)` right around the
same window as the double-fire — `vw_daemon.c`'s own comment on this
counter ("fold in per-action failures (e.g. quota rejections) that
vw_sync_run itself treats as non-fatal") suggests the upload of the
test's `big1.bin` (9500 of a 10000-byte quota) needed two attempts: one
that failed non-fatally after **partially** charging quota (e.g. a
chunk successfully `PUT` and ref-counted, crossing the 90% threshold and
firing the debounce's first email, followed by a `FILE_COMMIT` failure
that's never retried at the chunk level but leaves the file unmarked as
synced in the client cache), then a full retry on the next ~200ms sync
cycle that re-uploads from scratch. If that retry path causes the
chunk's reference (and therefore `used_bytes`) to be released and
re-acquired rather than reused, that would be a **second, genuine**
90%-threshold crossing — the debounce firing twice would then be
correct behavior for two real crossings, not a bug in the debounce logic
itself; the actual defect (if this hypothesis holds) would be an
asymmetric charge/release around a failed `FILE_COMMIT` retry, unrelated
to `vw_notify.c` entirely.

This has not been seen in the CI history sampled while triaging PR #2
(checked several dozen recent `main`-branch runs of this same
`integration` job; no prior occurrence of this specific test/assertion
in the failure logs found) — so either genuinely rare (a CI-runner-load-
dependent timing window that essentially never reproduces locally, per
the 3/3 local pass above) or newly exposed by unrelated recent change.
Worth checking `git log` on `vw_sync.c`/`vw_client_core.c`/the server's
`FILE_COMMIT`/quota-charge path for anything landed since the last time
this exact CI job is known to have run clean, in case something already
shipped narrowed the timing window that makes this reproducible.

## Acceptance criteria

- Root cause identified: either (a) a real asymmetric quota charge/
  release bug around a retried `FILE_COMMIT` (fix it, plus a regression
  test that deliberately forces the retry path), or (b) confirmation
  that two crossings really can legitimately happen for one logical
  upload under retry, in which case `test_user_category_quota_warning_
  edge_triggers_and_rearms`'s assertion (`len(smtp.messages) == 1`) is
  measuring an invariant the system never actually promised, and should
  be relaxed (e.g. assert `>= 1` for the crossing, keep the existing
  re-arm-then-recross assertions as-is) rather than left flaky.
- Either way: a regression test that reliably exercises whichever
  behavior is confirmed correct, not just a hope that CI stays fast
  enough to avoid the timing window.
- No unrelated behavior change to `vw_notify.c`'s debounce logic itself
  unless investigation actually finds a bug there (current reading is
  that it's correct — see this task's own analysis above).
